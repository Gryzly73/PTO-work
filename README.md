# PDF → Markdown для русской проектной документации

Бэкенд, который превращает многосотстраничный комплект проектной документации
(текст, таблицы, строительные чертежи в PDF) в машиночитаемый Markdown — так, чтобы
по нему можно было задавать вопросы модели и сверять проект с техническим заданием.

Работать с ним можно двумя способами, оба самодостаточны и не требуют ничего извне:

| Способ | Кому | Точка входа |
| --- | --- | --- |
| **CLI** | исследование качества, замеры, отладка промптов | `python hf_api_bench.py ...` — [раздел 5](#5-быстрый-старт) |
| **HTTP-сервис** | интерфейс и любые внешние клиенты | `python -m service` — [раздел 6](#6-http-сервис-бэкенд-поверх-конвейера) |

Оба используют один и тот же конвейер и пишут прогоны в одном формате.
Фронтенд живёт в отдельном репозитории и для работы бэкенда не нужен.

Подробное объяснение «на пальцах», без кода — **[`docs/КАК_ЭТО_РАБОТАЕТ.md`](docs/КАК_ЭТО_РАБОТАЕТ.md)**.

---

## 1. Зачем это

Строители получают заказ (например, склад), пишут ТЗ и отдают его в проектировочную
компанию. Обратно приходит проектная документация — **~1000 страниц PDF**. ПТО заказчика
должен проверить, соответствует ли проект исходному ТЗ, выписать замечания и отправить
на правку. Цикл «проверка → замечания → правки» занимал **1–1.5 месяца**. Задача —
сжать его, автоматизировав чтение документации.

**Что здесь реализовано:** первый и обязательный слой — извлечение содержимого PDF
в Markdown. **Модуля сверки требований ТЗ с проектом здесь пока нет** — извлечение
это не проверка, и путать их нельзя.

Инженерное ограничение (средство, а не цель): не зависеть от дорогого облачного
Gemini Flash/Pro, а работать на модели, которую можно поднять локально на сервере
**4×A16 (~61 GB VRAM, TP=4)** — см. [`docs/SERVER_HARDWARE.md`](docs/SERVER_HARDWARE.md).
Локальный запуск = данные заказчика не уходят наружу и стоимость на 1000 страниц
не кусается.

Принцип качества: приоритет — **корректный контекст** (точный текст + словесное описание
листа), а не pixel-perfect вёрстка таблиц. **Пропуск лучше галлюцинации**: выдуманную
марку оборудования не отличить глазами от настоящей.

---

## 2. Главная идея: текстовый слой PDF — не подсказка, а основной источник

Проектная документация приходит не сканами, а векторными PDF из CAD. Значит текст
на листе **уже есть внутри файла** — его не нужно «распознавать», его можно прочитать
точно и бесплатно. Отсюда три следствия, на которых держится весь конвейер:

1. **Текст и таблицы берутся из слоя** (`pdf_tables.py`): сетка таблицы находится
   по линиям (`page.find_tables()`), значения — по координатам слов. Ноль шансов
   на галлюцинацию. Замер (стр. 45 ИОС2): 190 чисел в 20 строках при точности **100%**
   против 182 чисел в 51 строке и 96.7% у модели.
2. **Битый ToUnicode лечится, а не обходится** (`deglyph.py`). У CAD-PDF слой часто
   выглядит кракозябрами («ǜодерǱаǸие» вместо «Содержание»), потому что шрифт отдаёт
   неверную таблицу символов. Чинится в два приёма. Первый — точный: подменена
   только таблица, а сам шрифт лежит в PDF целиком, и его cmap хранит, какой букве
   принадлежит глиф; MuPDF отдаёт номер глифа и помечает те коды, которые не смог
   сопоставить, — по ним и правим (на ИОС2 это 4744 символа, включая «№», кавычки
   и подстрочные индексы). Второй — кроссворд: отображение «глиф → буква»
   подбирается по читаемым страницам **того же документа**; он добирает знаки,
   которых в cmap нет. Там, где оба знают ответ, они **не расходятся ни разу**.
   Результат на ИОС2: нечитаемых листов было 7 из 49, стало **0 из 49**.
   Сверх подстановки готовый текст проходит санацию: приватные глифы Symbol,
   управляющие коды и математические алфавитные символы формул Word («𝐻» → «H»)
   до инженера доходили закорючками.
3. **Слой — бесплатный эталон** (`score_vs_pdftext.py`). Сравнивая выгрузку со слоем,
   получаем полноту и — главное — **точность чисел**: доля чисел выгрузки, которых
   в документе нет. Это прямой детектор выдумок, без ручной разметки и без Gemini.

Нейросеть (VLM) остаётся там, где слоя не хватает: **описать чертёж словами** — что
изображено, где стоит, как связано. Плюс листы-сканы и повреждённые страницы.

Режим `--layer-aware` включает эту логику: при исправном слое тайловый проход VLM
не запускается. Вызовов API — в 7.3 раза меньше, токенов в 2.5, времени в 2.3,
и точность чисел при этом **выросла** (95.4% → 98.5%): модель не вычитывает цифры,
значит и не перевирает их.

## 3. Какие модели используются

Все VLM вызываются через **HuggingFace Inference Providers** (`featherless-ai`,
`novita`, `deepinfra`). Каталог зашит в `hf_api_bench.py` (`CATALOG`), список —
`python hf_api_bench.py --list`.

### Рабочие

| id | HF id | Провайдер | Роль |
|---|---|---|---|
| **`qwen3vl-32b`** | `Qwen/Qwen3-VL-32B-Instruct` | featherless-ai | **основная**: dense 32B, сильнее прочих на сложных чертежах |
| `qwen3vl-30b-a3b` | `Qwen/Qwen3-VL-30B-A3B-Instruct` | novita | запасная: MoE, дешевле и быстрее |
| `qwen36-35b-a3b` | `Qwen/Qwen3.6-35B-A3B` | deepinfra | главный кандидат на замену: лучший key-hit (73–74%), но слабее на чертежах |
| `qwen36-27b` | `Qwen/Qwen3.6-27B` | deepinfra | dense 27B: точность чисел 100% на повреждённых листах, но ×15 дороже |
| `qwen3vl-8b`, `gemma3-4b` | — | featherless-ai | быстрый smoke-тест конвейера |

Qwen3.6 — thinking-гибриды: без `enable_thinking: false` (`NO_THINK_HF_IDS` в раннере)
контент приходит пустым.

### Потолок качества (для сравнения, не для прода)

| id | Замер | Почему не в прод |
|---|---|---|
| `kimi-k3` | лучший: 59.0 / 74.7 | ~100× дороже Qwen ($2.85/$14.25 за 1M) |
| `qwen3vl-235b` | 49.5 / 64.0 | MoE 235B — на 4×A16 не влезает, только API |
| `glm-45v` | — | MoE 108B-A12B, на 4×A16 не влезает |

### Дисквалифицированы (проверено, не возвращаться)

`gemma4-26b-a4b` и `gemma3-27b` — выдумывают штампы и таблицы («ООО КИРПРОЕКТПРОЕКТ»
вместо реальной организации), латинизируют шифры. `glm-46v-flash` — искажает фразы.
`qwen2.5-vl-72b` — тотальная латинизация кириллицы (В1 → B1, ИГЭ → IGE).
`llama4-scout` — выдумывает марки оборудования. `deepseek-ocr` через HF API — уходит
в петли и греческий мусор. История отбора моделей и журнал отрицательных результатов
ведутся локально и в репозиторий не входят.

### Не-нейросетевые компоненты

- **PyMuPDF (fitz)** — рендер страниц, текстовый слой, поиск таблиц.
- **Tesseract OCR** (`rus+eng`) — угол штампа (шифр документа, который VLM часто теряет)
  и OSD-определение поворота листа. Полностраничный Tesseract проверен и признан тупиком.
- **Текстовые LLM** (`--role synth`, `qwen25-32b` и др.) — исторический рычаг «пересобери
  черновик». Отключён по умолчанию: измерено, что LLM-synth поверх union **не улучшает,
  а сжимает** результат. Объединение делается детерминированно, кодом.

## 4. Установка

```powershell
pip install -r requirements.txt
copy .env.example .env   # вписать HF_TOKEN
```

Требуется:

- Python 3.10+ и зависимости из `requirements.txt` (PyMuPDF, Pillow, pytesseract, huggingface_hub);
- Tesseract OCR с языковыми пакетами `rus+eng` — **не обязателен**: он нужен для OCR
  угла штампа (`--stamp-crop`) и определения поворота листа. Без него конвейер
  работает, просто не вращает повёрнутые листы. Путь резолвится автоматически
  в `local_ocr.py:resolve_tesseract_cmd()`, проверка: `python -c "import local_ocr; print(local_ocr.ocr_healthcheck())"`;
- `HF_TOKEN` в `.env` (читается самописным `load_dotenv()` в `hf_api_bench.py`).
  `HF_PROVIDER=auto` **ломается** (`model_not_supported`) — раннер сам подставляет
  провайдера из каталога.

**Windows:** в скриптах много кириллицы, консоль по умолчанию cp1251 → `UnicodeEncodeError`.
Запускать `python -X utf8 ...` либо перенаправлять вывод в файл.

## 5. Быстрый старт

```powershell
# каталог моделей и флагов
python hf_api_bench.py --list

# основной режим: опора на текстовый слой, VLM только на описание
python hf_api_bench.py --model qwen3vl-32b --layer-aware --sheet-aware `
  --pdf "документ.pdf" --pages 1-49 --no-zone-hints --no-compare

# лист-таблица: PASS-T «перенеси таблицу как в исходнике» вместо тайлов
python hf_api_bench.py --model qwen3vl-32b --pdf "документ.pdf" --pages 45 --table-pages 45

# сложный чертёж: высокий DPI, зональные кропы, 2 прогона с union
python hf_api_bench.py --model qwen3vl-32b --pages 2,4 --high-dpi --zone-crop --runs 2

# сборка читаемого итогового Markdown по прогону
python build_ios2_md.py --run hf_runs/<run_dir> --pdf "документ.pdf" -o итог.md

# бесплатный скоринг против текстового слоя PDF (--vlm-only обязателен:
# иначе метрика меряет сама себя на секциях, собранных из слоя)
python score_vs_pdftext.py итог.md --pdf "документ.pdf" --vlm-only

# скоринг против ручного эталона (маппинг страниц — page_map.json)
python compare_to_etalon.py hf_runs/<run_dir>/out.md --pages 1,3,5

# union выводов двух разных моделей
python build_model_union.py --base <runA>/out.md --extra <runB>/out.md `
  --extra-label qwen3vl-32b --reclean -o union.md
```

Страницы задаются списком и диапазонами: `--pages 35-41,44-49`.
`--no-zone-hints` обязателен для любого PDF не из тест-сета (иначе подмешиваются
подсказки, выверенные по конкретным листам эталона).

## 6. HTTP-сервис: бэкенд поверх конвейера

Конвейер выше — библиотека и CLI. Поверх него живёт `service/` — HTTP-слой,
через который с конвейером работает интерфейс (или любой другой клиент).
Сервис **самодостаточен**: ему не нужен фронтенд, он поднимается из этой папки
и принимает PDF напрямую.

```powershell
pip install -r service/requirements.txt   # конвейер ставится из ../requirements.txt
python -m service                          # http://127.0.0.1:8000
```

Проверка: <http://127.0.0.1:8000> — страница статуса, `/docs` — интерактивная
документация API, `/health` — состояние в JSON.

Полностью без интерфейса, одним curl:

```bash
# поставить документ в очередь
curl -X POST http://127.0.0.1:8000/jobs -F "file=@документ.pdf"

# следить за прогрессом
curl http://127.0.0.1:8000/jobs/<id>

# забрать готовый markdown
curl http://127.0.0.1:8000/jobs/<id>/markdown -o итог.md
```

### Зачем HTTP-слой, если есть CLI

CLI считает документ одной командой и блокирует консоль на часы. Интерфейсу
и стороннему клиенту нужно другое: поставить документ в очередь, видеть, какой
лист считается сейчас, забирать готовые листы **по мере готовности**, а не в
конце, и переживать перезапуск. Это и делает сервис.

| Возможность | Как устроено |
| --- | --- |
| Очередь | документы считаются по одному, новые можно добавлять в любой момент |
| Прогресс по листам | `run_vlm()` вызывается на **один лист за вызов**, готовый лист сразу доступен |
| Возобновление | посчитанные `pages/page_NNNN.md` не пересчитываются: после перезапуска сервис досчитывает остаток |
| Отмена | `POST /jobs/{id}/cancel`, срабатывает между листами |
| Устойчивость к ошибкам | упавший лист попадает в `pageErrors`, документ продолжает считаться |
| Расход | `usage` по задаче: вызовы, токены, ретраи |

Артефакты прогона складываются в те же `hf_runs/<stamp>_<model>_svc-<id>/`
и соблюдают контракт разбиения, поэтому прогон, запущенный через сервис,
читается `compare_to_etalon.py`, `build_ios2_md.py` и остальными инструментами
так же, как запущенный из CLI.

### Режимы

| `PTO_PIPELINE_MODE` | Что делает |
| --- | --- |
| `real` (по умолчанию) | настоящий прогон VLM через HF Inference Providers |
| `mock` | лист за ~1.5 с без обращения к модели, вывод помечен `[MOCK]` |

`mock` нужен для отладки клиента и интеграции: проверять очередь и потоковую
выдачу листов, не тратя часы и токены. Принять его вывод за работу модели
нельзя — каждая страница помечена.

### Основные маршруты

| Метод | Путь | Назначение |
| --- | --- | --- |
| `GET` | `/health` | режим, профиль прогона, счётчики очереди |
| `POST` | `/jobs` | поставить в очередь: multipart с файлом либо JSON `{path, pages, projectId, documentId}` |
| `GET` | `/jobs` | очередь; фильтры `projectId`, `documentId`, `status`, `active` |
| `GET` | `/jobs/{id}` | статус, текущий лист, `pagesDone`, `usage` |
| `GET` | `/jobs/{id}/pages` | готовые листы; `after=N` — дельта, `pages=1,5,7` — выборочно |
| `GET` | `/jobs/{id}/pages/{n}/raw` | сырой вывод листа: PASS-0 / PASS-A / PASS-B без обработки |
| `GET` | `/jobs/{id}/markdown` | весь документ одним markdown |
| `POST` | `/jobs/{id}/cancel` | остановить прогон |
| `POST` | `/jobs/{id}/retry` | досчитать недостающие листы; `?reset=true` — с нуля |

`pages` принимает тот же формат, что CLI: `1,3,5`, `35-41,44-49`, `all`.

Лист отдаётся в готовом для интерфейса виде — `{pageNumber, kind, markdown,
extractedText, fragments}`, где `kind` — тип листа из `sheet_aware`,
`extractedText` — текстовый слой, но только если он читаемый.

**Извлечение по фрагментам (PASS-B) в `markdown` не попадает.** На чертеже это
16 подробных описаний кусков листа — до 100 тыс. символов, читать невозможно,
и браузеру такой markdown тяжело рисовать. Данные не теряются: они в поле
`fragments`, в файле прогона и в `/pages/{n}/raw`. Замер на тест-сете из
6 сложных листов: 495 тыс. символов → 206 тыс. (на листах с обычным описанием
сокращение впятеро, на листах с разросшимся PASS-A — вдвое).
Вернуть в интерфейс: `PTO_INCLUDE_FRAGMENTS=1`.

Настройки (порт, модель, режим, флаги качества, каталоги) задаются переменными
окружения и читаются из того же `.env`; полный список — `service/README.md`.
Там же — Docker и подключение интерфейса.

### Как подключить интерфейс — инструкция разработчику фронтенда

Отдельным файлом, который можно просто переслать: **[`docs/ДЛЯ_ФРОНТЕНДА.md`](docs/ДЛЯ_ФРОНТЕНДА.md)**
— там же чек-лист проверки, справочник API и разбор типичных ошибок. Ниже —
то же самое коротко.

Текущие задачи на доработку интерфейса — **[`docs/ПРАВКИ_ФРОНТЕНДА.md`](docs/ПРАВКИ_ФРОНТЕНДА.md)**:
семь пунктов с файлами, строками и готовыми диффами. Отдельно от справочника
намеренно — список правок живёт до их выполнения, справочник постоянен.

Меняется **один файл**: `src/lib/process-document.ts`. Всё остальное — компоненты,
маршруты, типы, стили — остаётся как есть.

**Почему только один.** Интерфейс уже умеет всё, что нужно для потоковой
загрузки: показывает «готово N из M», процент, текущий лист и шаг, держит
состояние в `db.json` (переживает F5), опрашивает статус, позволяет добавлять
файлы во время работы очереди. Менять UI не требуется — достаточно подменить
источник страниц. Готовый файл экспортирует ту же функцию `processDocument(id)`,
что и оригинал, поэтому `api/documents/route.ts` и
`api/documents/[id]/process/route.ts` править не нужно.

**Что делает оригинал и почему его меняем.** Родной `process-document.ts` берёт
текстовый слой PDF через `unpdf` и раскладывает регулярками, а для чертежа
вставляет заглушку «_на следующем этапе его пишет модель_». Пока файл не заменён,
фронт работает мимо конвейера: внешне всё крутится, но описаний чертежей нет.

**Применение** (в форке, обычным коммитом):

```bash
git checkout -b pto-backend-integration
git apply ../backend/service/frontend-patch/process-document.patch
git commit -am "Брать разбор PDF из конвейера ПТО вместо текстового слоя"
```

**Запуск связки.** Два процесса на одной машине:

```powershell
# 1) бэкенд, с доступом к папке загрузок фронта
cd backend
$env:PTO_ALLOWED_PDF_ROOTS = "<путь>\frontend\pto-drawings\uploads"
python -m service

# 2) фронтенд
npm install
npm run dev            # http://localhost:8080
```

**Как это работает:**

```
интерфейс: загрузка PDF → uploads/ → processDocument()
    ↓ POST /jobs {path, documentId}     файл не пересылается — общая папка
бэкенд: очередь → лист за листом → pages/page_NNNN.md
    ↓ клиент опрашивает /jobs/{id} раз в 3 с и забирает новые листы
интерфейс: db.json → инженер видит листы по мере готовности
```

PDF между процессами не копируется: фронт кладёт файл в свой `uploads/`, сервис
читает его оттуда по пути. Поэтому `PTO_ALLOWED_PDF_ROOTS` обязателен — без него
сервис ответит `403` на попытку взять файл извне разрешённых каталогов. Адрес
бэкенда задаётся `PTO_BACKEND_URL` (по умолчанию `http://127.0.0.1:8000`).

**Четыре вещи, которые стоит знать до того, как что-то сломается:**

1. **Шапка листа обязана содержать `**Файл:**`.** `storage.ts:listDocuments()`
   перегенерирует markdown заглушкой из `extractedText`, если этой подстроки нет,
   и молча затирает результат многочасового прогона. Бэкенд её всегда ставит —
   поэтому `storage.ts` править не пришлось. Если будете менять формат страницы,
   не потеряйте эту строку.
2. **Ретраи обязательны.** Прогон идёт часами, клиент делает тысячи запросов,
   и обрыв keep-alive неизбежен. В патче: три попытки на запрос, сдаёмся только
   после 20 неудач подряд. Без этого один `fetch failed` роняет весь цикл —
   бэкенд досчитывает документ, а интерфейс показывает ошибку и половину листов.
3. **Перезапуск Next не теряет прогон.** Клиент находит идущую задачу по
   `documentId` и подхватывает её. Готовые листы конвейер не пересчитывает,
   так что «Обработать заново» на завершённом документе просто заберёт результат.
4. **Отмена показывается как ошибка.** В `DocumentStatus` нет статуса «отменён»,
   поэтому `canceled` отображается как `error` с пояснением в тексте.

**Что проверить после подключения:** загрузите PDF (документ встаёт в `queued`,
затем `processing`) → листы появляются по одному, счётчик растёт → обновите
страницу браузера в середине прогона (прогресс не теряется) → загрузите второй
файл, пока считается первый (встаёт в очередь) → перезапустите бэкенд на середине
(прогон продолжится, готовые листы не пересчитываются). Для этих проверок
поднимайте бэкенд в режиме `PTO_PIPELINE_MODE=mock` — лист считается за полторы
секунды, без обращения к модели и без трат.

**Чего в интерфейсе пока нет** (API готово, нужны правки UI): кнопка отмены
(`POST /jobs/{id}/cancel`), показ расхода токенов (`usage` в задаче) и
предупреждение, что в режиме `real` страницы уходят стороннему провайдеру.

**Четыре вещи, без которых сервер работать будет, а жить — нет.**

## 7. Как работает конвейер

Одна страница проходит следующие шаги (`hf_api_bench.py` — сердце проекта, ~2600 строк):

1. **PASS-0 — паспорт листа** (`sheet_aware.py`, флаг `--sheet-aware`).
   По геометрии PDF и текстовому слою определяется тип листа
   (`text / table / plan / scheme / mixed`), выписываются CAD-метки, диаметры,
   заголовки. Паспорт идёт и в промпт (как якоря «не выдумывай сверх этого»),
   и в итоговый Markdown. От типа листа зависит бюджет рендера:
   план — до 3200 px, текст — 1800–2000 px.
2. **Текстовый слой** — если слой исправен (проверка `is_garbled_pdf_text()`,
   при поломке — починка через `deglyph.py`), текст и таблицы берутся из него
   точно и бесплатно; `normalize_pdf_text()` схлопывает спам одинаковых меток
   (метка `В1` на каждом сегменте трубы → сотни повторов).
3. **PASS-A — описание всего листа**: один вызов VLM на страницу целиком, подробный
   словесный рассказ. Это главный артефакт для последующего Q&A. На выходе
   quality-gate `pass_a_quality_ok()` (слишком коротко / петля повторов / потерянные
   якоря) → при провале повторный вызов зональным промптом.
4. **PASS-B — тайлы** (пропускается при `--layer-aware` на чистых листах): лист режется
   на ≤6–8 фрагментов плюс семантические зоны под тип листа (легенда, основная таблица,
   штамп, правая полоса, углы). Каждый фрагмент — отдельный вызов. Мусорные тайлы
   (голые «1..N») отбрасываются.
5. **PASS-T — лист-таблица** (`--table-pages`): вместо тайлов один вызов «перенеси
   таблицу как в исходнике», с предварительным запросом контекста вне таблицы
   и авторотацией повёрнутых листов через Tesseract OSD.
6. **Anti-loop чистка.** VLM на плотных чертежах уходит в петли, без чистки выхлоп
   бесполезен: схлопывание повторов построчно и **внутри строки**, дедуп, срез
   арифметических прогрессий-галлюцинаций, циклов из 2–6 строк, пустых ячеек,
   склейка разорванных пар «параметр — значение».
7. **Table-rescue.** Тайл с петлёй пустых ячеек перечитывается с двойным DPI,
   а если строк данных всё ещё нет — целиком горизонтальная полоса листа;
   побеждает вариант с лучшим `table_text_score`.
8. **`--runs N`** — N независимых прогонов PASS-B с объединением уникальных фактов
   (борьба с недетерминизмом моделей, повышает полноту).

Артефакты прогона складываются в `hf_runs/<UTC_stamp>_<model>_<tag>/`:
`meta.json` (полный конфиг + расход токенов), `out.md`, `pages/page_NNNN.md`.

### Чертежи DWG и DXF — путь без модели (в проверке)

Начиная с 24.08 конвейер принимает не только PDF, но и сам чертёж AutoCAD.
Формат обрабатывается принципиально иначе, и это не оптимизация, а другой
источник данных: в PDF текст приходит через отрисовку, а в DWG он лежит
внутри файла вместе со слоями, размерами и масштабом. Поэтому **модель на
векторном пути не вызывается вовсе** — ни в режиме `real`, ни в `mock`, и
`HF_TOKEN` для него не нужен.

```bash
# отдельно, без сервиса: список листов
python dwg_sheets.py "Жуковский 1_ПЗУ.dwg"

# markdown по всему файлу или по одному листу
python dwg_sheets.py "чертёж.dwg" -o out.md
python dwg_sheets.py "чертёж.dwg" --sheet 22 -o лист22.md
```

Через сервис — тот же `POST /documents`, что и для PDF: расширение `.dwg`
или `.dxf`, число листов приходит в `pageCount`, разметка листа та же
(`PASS-0` / `PASS-A` / `PASS-B`), так что инструменты поверх markdown
работают без переделки.

**Что даёт лист.** `PASS-A` — состав по слоям: имя слоя, число объектов,
суммарная длина в метрах и место на листе. Имена слоёв в комплекте — это
марки систем («!!!В1», «!!!К1»), то есть ровно то, что VLM на PDF вычитывал
глазами и путал. `PASS-B` — весь текст листа дословно, включая штамп,
выноски и размеры.

**Что решено внутри** (подробности — в шапке `dwg_sheets.py`):

* листы берутся из layout'ов, а если их нет — по рамкам в модели: у листа
  ISO соотношение сторон √2, и ничего другого такой формы на чертеже нет;
* формат A4 в 1:100 и A2 в 1:50 геометрически неотличимы, различает шрифт:
  при верном масштабе высоты ложатся на ряд ГОСТ 2.304;
* единицы берутся из `$INSUNITS`, а не из размера рамки: ПЗУ и ПОС одного
  комплекта вычерчены в метрах, остальное — в миллиметрах;
* масштаб листа считается по самому большому окну, а не по частому: врезок
  на листе больше, чем основных видов;
* блоки разворачиваются и в тексте, и в геометрии: больше половины чертежа
  лежит внутри вставок;
* длинные подписи в DXF разрезаны по границе 255 байт (тег 3 + тег 1), и
  ezdxf отдаёт только последний кусок — `merge_split_text()` склеивает их
  обратно на байтах, заодно собирая разорванную пополам букву;
* «####» — заглушка невычисленного поля AutoCAD — в вывод не идёт;
* юникод, записанный escape-последовательностью AutoCAD, раскрывается: иначе
  вместо «1-1 (Опалубка)» в тексте стоит цепочка кодов;
* окно вьюпорта иногда настроено мимо чертежа. Если ни одно окно не поймало
  ни одной подписи, текст не теряется: при единственном листе он идёт на него
  целиком, при нескольких — отдельным листом в конце. На стройгенплане ПОС это
  разница между 7% и 99% перенесённого текста;
* частые повторы меток схлопываются, как `normalize_pdf_text()` делает это для
  текстового слоя PDF;
* подписи, оказавшиеся на одной высоте, но в разных концах листа, в одну
  строку не склеиваются: на листе фундаментов КР1 так склеивалось 63% пар
  соседей, и в текст уходили несуществующие строки вроде «750 -0.800».

**Как проверять разбор.** `python dwg_check.py <файл или папка>` сверяет
разбор числами: какие поля DXF заданы в чертеже и не доехали до листа, какой
мусор остался в подписях, какие величины невозможны, у каких листов не
прочитана основная надпись. `--baseline файл.json` кладёт слепок числа находок
и при следующем прогоне ругается, если стало хуже; `--twice` дополнительно
конвертирует чертёж дважды и сравнивает текст.

Слепок по всему комплекту «Жуковский» лежит в `dwg_check_baseline.json`: 94
чертежа, ошибок нет, сигналов — 2338, из них 2265 «подписи без листа» (почти
все — сети связи ИОС5, где окно вида смотрит мимо чертежа: сами подписи не
теряются, они уходят служебным листом). Полный обход идёт около двадцати
минут, поэтому по ходу правки удобнее гонять раздел:
`python dwg_check.py "1. Стадия П DWG/7 - ПОС"`.

Проверка нужна потому, что ошибки разбора до сих пор ловились глазами на
превью: ширина подписи читалась не из того поля DXF, и это увидели только по
наехавшим друг на друга буквам. Картинка — не то, ради чего делается
конвейер, и на неё этот контроль опирать нельзя.

**Чего этот путь пока не делает.**

1. **Размерные числа идут вперемешку с подписями.** На чертёжном листе они
   составляют от 58 до 76% всего текста (на листе фундаментов КР1 — 442 подписи
   из 585), и в тексте листа выглядят так: «Фундамент сборный Ф-3.1 / 1-1
   (Опалубка) / 600 / 300 600 300 / 200». Какое число к какому виду относится,
   по такому тексту не понять. Вынести их отдельным блоком внутри зоны — можно,
   но при этом теряется слабая привязка «число рядом с заголовком разреза»,
   поэтому решение отложено.
2. **Внешние ссылки не читаются.** Если лист собран из xref (весь ПЗУ
   комплекта «Жуковский» — такой), содержимое лежит в отдельных файлах, и
   заказчик их обычно не присылает. Лист об этом честно пишет строкой в
   `PASS-A`, а не притворяется, что на нём пусто.
3. **Окно вида иногда указывает мимо** чертежа (LibreDWG или сам файл).
   Когда лист в файле один, берётся весь текст модели, и в паспорте
   появляется строка «разбор листа неполон»; когда листов несколько, текст
   к листу не привязывается.
4. **Полнота LibreDWG не сверена с ODA File Converter** — сверку стоит
   сделать до того, как на векторный путь будут опираться в работе.
5. **Невоспроизводимость `dwg2dxf` портит не только структуру, но и текст.**
   Что выход конвертера не детерминирован, было известно: каждый прогон даёт
   другой файл, и часть из них структурно битая — от этого стоит ретрай в
   `to_dxf()`. Чего не было видно, так это тихого случая: файл читается, а
   три блока MTEXT из 1894 на листе фундаментов КР1 каждый раз выходят с
   разным хвостом — то целиком «2-2 (Опалубка)», то обрубок «2-2 (», то с
   чужими байтами. То есть markdown одного и того же чертежа от прогона к
   прогону разный. Видно по `dwg_check.py --twice` и по находке «подпись
   обрезана конвертером» (13 штук на комплект). Целая подпись у нас есть — её
   видит прямое чтение DWG (`dwg_direct.py`), — но подставлять её вместо
   обрубка разбор пока не умеет.

   Заодно померено, сколько нужно ретраев: у «9.Жуковский1_Блок 9 (КР3)_
   Фундаменты» два прогона из десяти дают DXF, который ezdxf не читает вовсе
   («код группы не число» — длинный MTEXT вылез туда, где ожидается число).
   При трёх попытках такой чертёж терялся целиком раз на 125 прогонов;
   попыток теперь шесть.

**Ограничение на сервере.** В образе есть только чтение DXF: `dwg2dxf` в
Debian пакетом не поставляется, и как его туда класть (сборка LibreDWG из
исходников или AppImage ODA), пока не решено. Локально DWG читается — путь к
конвертеру ищется в `PTO_DWG2DXF`, в `PATH` и в `backend/tools/`.

**Проверено** на комплекте «Жуковский», стадия П: ИОС5 «Состав проекта» — 5
листов, КР1 «Фундаменты» — 4, ПОС — 2, ПЗУ — 12, КР1 «Планы» и «Разрезы» — по
1, ТБЭ «Состав проекта» — 6, СПИС — 1. Сквозной HTTP-прогон сервиса: DXF —
12 проверок из 12, DWG напрямую — 12 из 12, PDF не сломался — 12 из 12.

### Лист собирается в порядке исходника

Страница отдаётся не фиксированными секциями, а так, как она свёрстана:
заголовок, текст, таблица на своём месте между абзацами, текст под таблицей,
штамп в конце. Порядок берётся из координат блоков текстового слоя и рамок
таблиц (`service/flow.py`), а не выводится моделью, поэтому структура ответа
совпадает с документом, а не пересказывает его. Раньше примечание, стоящее в
исходнике под таблицей, уезжало на экран за десяток абзацев от неё.

Вместе с этим:

* **описание листа больше не пересказывает таблицы.** Если таблица собрана
  скриптом из текстового слоя, её markdown-строки из описания VLM вырезаются
  (`drop_tables_from_description`): рядом с точной таблицей второй, менее
  надёжный экземпляр тех же чисел инженеру только мешает;
* **карта листа «Что где на листе»** выводится только у листа-чертежа, и
  пока пустой заготовкой (`service/flow.py`, `empty_sheet_map`): её должен
  заполнять разбор чертежей. У листов текста и таблиц секции нет вовсе —
  строки «текст — север — 1 стр.» по координатам текстового слоя лишь
  повторяли то, что и так видно в потоке. Сборка карты по блокам PDF
  (`sheet_map_markdown`) сохранена как готовый инструмент, но сервисом не
  вызывается. У DWG/DXF то же правило: текстовый лист (состав проекта,
  спецификация — `dwg_sheets.sheet_kind`) без карты, чертёж — с пустой
  заготовкой; сборка по зонам (`dwg_sheets.sheet_map`) сохранена для разбора
  чертежей.

### Предпросмотр листа чертежа

`GET /jobs/{id}/pages/{n}/preview?format=svg|png` (`dwg_render.py`). PDF
интерфейс рисует сам через pdf.js, а DWG браузер не открывает — без картинки у
чертежа рядом с расшифровкой пустое место. SVG для показа (зум без потери
качества), PNG для ленты миниатюр. Картинка считается один раз и лежит рядом с
прогоном.

Отрисовка ezdxf на выходе LibreDWG потребовала трёх поправок, без которых
выходит чёрный лист или точка посреди пустоты: обмен чёрного и белого (цвета
чертежа рассчитаны на тёмный фон модели), пропуск WIPEOUT и IMAGE (заливают
лист сплошным) и пропуск DIMENSION — у размеров после конвертации битые точки,
и рисовальщик уводит вид на 10¹² единиц. Размерные числа при этом не теряются:
они есть в тексте листа.

Замечание для интерфейса: Chrome с принудительной тёмной темой инвертирует
SVG вместе с подложкой, и лист выглядит чёрным. PNG этому не подвержен — если
у инженеров включён такой режим, показывать лучше PNG.

### Один лист из двух источников: DWG + PDF

По разделу приходит и чертёж, и альбом PDF — это не дубль, а два неполных
чтения одного документа, и неполны они по-разному:

* **в чертеже текст лежит данными** — точен до знака, с координатами, таблицы
  собираются из настоящей сетки линий. Но чертёж приходит **без внешних
  ссылок**: весь ПЗУ комплекта «Жуковский» собран из xref-файлов, которых
  заказчик не присылает, и в разборе от листа остаются рамка со штампом;
* **в PDF лист отпечатан целиком**, включая содержимое внешних ссылок, — зато
  текст восстанавливается по отрисовке, а на сканах моделью. И только PDF
  даёт словесное описание начерченного: из геометрии его взять неоткуда.

Поэтому источники не выбираются, а складываются (`fuse.py`, зовётся из
`bundle.py`). Листы связываются по основной надписи — имена файлов и номера
страниц для этого не годятся (`stamp.py`). У сведённого листа появляются
четыре блока сверх содержимого чертежа:

| Блок | Что в нём |
|---|---|
| `Сверка источников` | сколько слов и чисел совпало, сколько есть только в чертеже, сколько только в PDF |
| `Добор из PDF` | строки, несущие хоть один токен, которого нет в чертеже и который не обрывок уже известного слова |
| `Таблицы, найденные только в PDF` | таблица переносится целиком, когда её сетки в чертеже нет |
| `Описание листа` | пересказ модели по картинке — единственное, чего из чертежа не взять; помечен как работа модели |

Модель в самом сведении не участвует: сложение идёт по нормализованным
токенам, тем же приёмом, каким `merge_vlm_ocr.py` добирает OCR к выводу VLM.
Обрезка добора (120 строк) не молчаливая — сколько строк не показано, сказано
прямо в отчёте.

**Что показала проверка на паре из раздела ПЗ** (`1 - ПЗ`: чертёж и печатный
альбом того же документа, титульный лист). У этого PDF **нет текстового слоя
вовсе** — ноль знаков и ноль шрифтов на всех восьми страницах, текст переведён
в кривые при печати, — поэтому PDF-сторону читала модель `qwen3vl-32b`, та же,
что стоит в `PTO_MODEL`:

| | из DWG | из PDF (Qwen3-VL-32B) |
|---|---|---|
| текст листа | дословно, 111 слов и чисел | 241, из них 71 совпало с чертежом |
| фамилии под печатью | `П.И.Авдулов`, `А.О.Сальников` | «подпись неразборчива, рядом с фамилией "НИКОВ"» |
| реквизиты печати | нет вовсе | ИНН и ОГРН — **выдуманы**, причём в описании и в тайлах разные |
| описание листа | нет и быть не может | есть |

Фамилии — самый наглядный случай: в PDF они физически закрыты печатью, и это
не лечится ни моделью, ни разрешением. В чертеже они лежат данными.

Отсюда три правила, заложенных в `fuse.py`:

1. **В добор идёт только то, что модель прочитала** с листа (`PASS-B`), а не
   то, что она о листе рассказала (`PASS-A`): иначе пересказ задваивается с
   блоком описания, а вместе с ним как факты уезжают выдуманные номера.
2. **Обрывки не идут.** Строка, все новые слова которой оказались кусками уже
   известных («дской комплекс» от «складской», `СА-1/25-ПЗ` от
   `28-ХСА-1/25-ПЗ`), выбрасывается: лист режется на фрагменты, и слово на
   границе куска приходит половиной.
3. **Перечтения не идут.** Если строка на 60% и больше состоит из слов ОДНОЙ
   строки чертежа — это она же, прочитанная с ошибками, а не новый факт.
   Именно это опаснее всего: `ООО "ХОЛДИНГ СТРОИТЕЛЬНЫЙ КОМПЛЕКС-1"` вместо
   `АЛЬЯНС-1` и «Российская Федерация, Москва» вместо «Московская область»
   читаются как ещё один заказчик и ещё один адрес.

Что отсеять детерминированно нельзя — ошибку там, где модель уверенно
прочитала не то на месте, которого в чертеже нет вообще (реквизиты печати).
Поэтому раздел добора подписан прямо: прочитано с картинки, чертежом не
подтверждено.

Сравнение моделей на этом же листе: `qwen3vl-8b` дополнительно путал название
объекта («Индустриал Сити "Учхозовский 1"»), у `qwen3vl-32b` описание целой
страницы верное. Но **фрагментный проход перевирает у обеих** — 32B выдаёт
свой набор ошибок («КУКОВСКИЙ», `28-ХСА-1/25-П3`, выдуманное
`ООО "ТурбоРесурсПроект"`). Размер модели этот класс ошибок не убирает,
убирают правила 2 и 3.

Отдаётся сведённый отчёт маршрутом `GET /projects/{id}/report`
(`bodies=false` — только состав и расхождения, без содержимого листов).
Проверки: `python test_fuse.py` и `python test_bundle.py`.

**Печатный альбом без текстового слоя.** Связать лист с его двойником можно
только по основной надписи, а у печатного PDF её негде прочитать: у альбома
раздела ПЗ комплекта «Жуковский» во всех восьми страницах ноль знаков текста.
Без запасного пути такие листы остаются без шифра — то есть не связываются
именно там, где сведение нужнее всего. Поэтому у страниц без слоя шифр берётся
из **уже посчитанного** разбора листа (`bundle.code_from_body`): к тому времени
по картинке прошлась модель, и обозначение стоит в тексте. Разбор ради этого не
запускается, а кандидат проверяется тем же правилом, каким шифр опознаётся в
надписи, — иначе в отчёт поедет «ГОСТ 14098-2014».

### Контракт разбиения — не ломать

Все скрипты режут markdown по `## Страница N`, внутри страницы — по
`### PASS-0 / ### PASS-A / ### PASS-B`. Это API между инструментами: на заголовки
завязаны `compare_to_etalon.py`, `build_ios2_md.py`, `merge_vlm_ocr.py`,
`build_best_of.py`, `build_quality_viewer.py`, `patch_page_into_run.py`,
`build_model_union.py`.

## 8. Метрики — их три, не смешивать

| Метрика | Инструмент | Что считает |
|---|---|---|
| **против текстового слоя PDF** | `score_vs_pdftext.py` | полнота слов/чисел/кодов + **точность чисел** (детектор галлюцинаций). Бесплатно, детерминированно, на любом документе. Основная. |
| rough recall / key | `compare_to_etalon.py` | token_recall + key_phrase_hit против ручного эталона (`page_map.json`). Быстрая, но грубая; только для тест-сета из 6 страниц. |
| checklist % | `new_files/pto_scoring_kit/score_real_testset.py` | исторический чек-лист токенов, матчеры `contains/any_contains/all_contain`. Потолок ~64%. |

Цифры разных шкал несравнимы — в отчётах всегда указывать, какая именно.
`score_real_testset.py --self-check` должен давать ~100%, иначе сломан матчер.

**Дисциплина измерений** (выведена болью):

- модели недетерминированны, на сложных страницах разброс между прогонами доходил
  до **55 пунктов** — вывод только по медиане из ≥4 прогонов, отчитываться медианой
  **и** худшим значением;
- прежде чем верить скору — проверить вывод на `[Error` и подозрительно короткий текст
  (был случай: 3 из 6 страниц = `[Error 413]` → фальшивые «6%»);
- каждое изменение должно иметь механизм, работающий на **невиданном** чертеже:
  не подглядывать в разметку тест-сета, чтобы подогнать промпт.

## 9. Текущее состояние

Проверено на реальном комплекте «Раздел ПД №5 Подраздел №2 (ИОС2)», 49 страниц
(сверка по 39 страницам с текстом и таблицами):

| Показатель | Сейчас | Было до 15.08 |
|---|---|---|
| Полнота итогового документа | **99.6%** | 92.0% |
| Достоверность чисел | **97.5%** | — |
| Страниц, сошедшихся полностью | **36 из 39** | 29 из 39 |
| Нечитаемых листов | **0 из 49** | 7 из 49 |

Отдельно только описание от VLM: полнота 50.9% при достоверности 95.2% — низкая
полнота здесь не дефект, данные берутся из слоя, а от модели нужен смысл и связи.

Скорость и стоимость: в режиме `--layer-aware` — **~28 секунд на страницу**,
один запрос к модели; 1000 страниц последовательно ≈ **8 часов**;
**$1–3 за 1000 страниц** по API и $0 при локальном запуске.

**Это оценка для листов с исправным текстовым слоем.** Когда слой битый и починить
его не удаётся, `--layer-aware` срезать путь не может, и лист идёт полным проходом.
Замеры через сервис на тест-сете из 6 сложных страниц (слой нечитаемый):

| Что мерялось | Результат |
| --- | --- |
| 6 листов подряд | **2 ч 15 мин**, 121 вызов к модели, 536 405 токенов, 0 ошибок |
| один лист чертежа | **15,6 мин**, 17 вызовов: PASS-A (211 с) + 9 тайлов + 7 семантических зон |
| один лист с читаемым слоем | **~2,3 мин**, 1 вызов (PASS-B пропущен) |

Разброс в 7 раз определяется не «текст или чертёж», а **числом вызовов модели
на лист**, то есть тем, сработал ли `--layer-aware`. Планируя время на комплект,
сначала посмотрите, читается ли текстовый слой.

### Чего ещё нет

1. **Сверки с ТЗ** — второй слой задачи, не начат. На выходе аккуратный Markdown,
   а не список замечаний.
2. **Локального развёртывания** — модель выбрана с оглядкой на 4×A16, но пока
   работает через платный API, то есть данные уходят на сторонний сервис.
3. **Параллельной обработки по умолчанию** — листы идут по порядку
   (`PTO_PAGE_CONCURRENCY=1`). Провайдер держит 3 потока и это вдвое быстрее
   (замерено, без единого отказа), но параллельный счёт теряет порядок листов,
   а страницы документа бывают связаны между собой. Переключатель ручной.
4. **Роутинга по типу листа** — идея отправлять текстовые листы в одну модель,
   а чертежи в другую; механика («паспорт листа») уже есть, роутинг не написан.
5. **Скоринга на других документах** — все цифры выше по одному комплекту.

## 11. Что изменилось в этой версии

Раньше репозиторий был **только конвейером**: скрипты, которые запускаются руками,
считают документ и складывают Markdown в `hf_runs/`. Теперь это **бэкенд**: тот же
конвейер плюс HTTP-слой, через который с ним работает интерфейс.

**Конвейер не менялся.** `hf_api_bench.py`, `sheet_aware.py`, промпты, чистка,
контракт разбиения — всё как было; сервис вызывает `run_vlm()` как библиотеку.
Качество извлечения этой версией не затронуто.

Что появилось:

| Что | Зачем |
| --- | --- |
| `service/` — HTTP-сервис | интерфейсу нужны очередь, прогресс по листам и выдача результата по мере готовности, а не одна блокирующая команда |
| Вызов конвейера **полистно** | точный прогресс, отмена между листами и возобновление после перезапуска: готовые листы не пересчитываются |
| Очередь на диске | прогон живёт часами; перезапуск сервиса не должен стоить суток работы |
| Режим `mock` | отлаживать клиента и интеграцию, не тратя часы и токены |
| `Dockerfile` | воспроизводимый запуск, в образе Tesseract с `rus+eng` |
| Лог в файл | `service/state/service.log`: разбирать многочасовой прогон по памяти невозможно |
| `PTO_PAGE_CONCURRENCY` | переключатель параллельного счёта листов (по умолчанию `1`) |

Чего эта версия **не** меняет: качество извлечения, набор моделей, метрики,
формат прогонов. Прогон из сервиса и прогон из CLI читаются одними и теми же
инструментами.

## 12. Что не входит в репозиторий

Исходные PDF заказчика, эталоны, прогоны (`hf_runs/`), собранные выгрузки
(`*_итог.md`, `union*.md`), HTML-отчёты и вьюеры, внутренние рабочие документы,
`.env` с токеном — см. `.gitignore`. Всё это либо конфиденциально, либо
пересобирается запуском конвейера.
