# Автодеплой бэкенда — что готово и что нужно от вас

Ответ на запрос по трём пунктам. Коротко: **workflow написан и проверен**,
от вас нужны только доступы и один сервисный пользователь на сервере.

Деплой бэкенда полностью независим от фронта: свой репозиторий, свой workflow,
свой контейнер. Пересекаются они только общей папкой `uploads` и сетью.

---

## 1. Workflow — готов

| Файл | Что делает |
| --- | --- |
| `.github/workflows/deploy-backend.yml` | доставка: заходит по SSH и передаёт скрипт |
| `deploy/deploy.sh` | сам деплой на сервере: код → сборка → перезапуск → проверка |

Специфика проекта намеренно вынесена в `deploy.sh`, а не в workflow: там
есть вещи, которые со стороны не видны (раздел 4). Если решите переписать
доставку под свой вкус — переписывайте workflow, а скрипт вызывайте как есть.

Что делает `deploy.sh` по шагам:

1. смотрит `/health` — не считается ли документ прямо сейчас;
2. `git fetch` + `git reset --hard origin/main`;
3. проверяет, что `.env` на сервере на месте (иначе выходит с ошибкой);
4. `docker compose --profile real up -d --build`;
5. ждёт, пока `/health` ответит, сверяет режим;
6. `docker image prune -f`.

**Проверено на живом стенде:** первый деплой с нуля, повторный деплой поверх
работающего сервиса, поведение при недоступном реестре образов. После деплоя
прогнана самопроверка сервиса — 12 из 12.

## 2. Что нужно от вас

### Секреты репозитория

`Settings → Secrets and variables → Actions → Secrets`:

| Имя | Что это |
| --- | --- |
| `DEPLOY_HOST` | адрес сервера |
| `DEPLOY_USER` | пользователь для деплоя — **не root** |
| `DEPLOY_SSH_KEY` | приватный ключ этого пользователя целиком, вместе со строками `-----BEGIN...` |

`Settings → Secrets and variables → Actions → Variables` (не секреты, просто
чтобы не хардкодить):

| Имя | По умолчанию |
| --- | --- |
| `DEPLOY_PORT` | `22` |
| `DEPLOY_PATH` | `/opt/pto/backend` |

Доступ в репозиторий: достаточно **collaborator с правом push** либо deploy key
на чтение — код тянет сам сервер, Actions только даёт команду.

Пока этих секретов нет, workflow не падает, а **пропускает деплой** и пишет в
сводку запуска, чего не хватает. Так вкладка Actions не краснеет на каждый
коммит до того, как всё настроено.

### Что должно быть на сервере

```bash
# 1. Пользователь под деплой, в группе docker (чтобы не sudo)
sudo adduser --disabled-password pto-deploy
sudo usermod -aG docker pto-deploy

# 2. Клон репозитория, владелец — этот пользователь
sudo mkdir -p /opt/pto && sudo chown pto-deploy:pto-deploy /opt/pto
sudo -u pto-deploy git clone git@github.com:Sorryprod/PTO-work.git /opt/pto/backend

# 3. Настройки. Файл НЕ в репозитории и деплоем не затирается.
sudo -u pto-deploy cp /opt/pto/backend/.env.example /opt/pto/backend/.env
# вписать HF_TOKEN (ключ Hugging Face) и PTO_API_TOKEN (пароль к нашему API)

# 4. Публичный ключ пользователя — в ~/.ssh/authorized_keys, приватный — в секрет
```

Нужен Docker с `compose` версии 2.24 и выше.

## 3. С main или с тега — наше предложение

**Предлагаем main.** Вы просили «чтобы обновления просто пушились», а тегами
это превращается в ритуал: каждый фикс придётся ещё и релизить.

Риск у main один: бэкенд перезапускается на каждом коммите, а он в это время
может считать документ **часами**. Мы его сняли двумя способами:

- в workflow стоит `paths-ignore` на `**.md` и служебные файлы — правка
  документации службу не трогает;
- деплой не роняет сервис: образ собирается **до** остановки контейнера.
  Замеренный простой — **около 3 секунд** при бюджете клиента ~60 секунд
  (интерфейс терпит 20 неудачных опросов раз в 3 секунды, потом показывает
  ошибку). То есть обновление проходит незаметно даже во время прогона.

Если понадобится обновиться, дождавшись конца прогона, — есть ручной запуск
`workflow_dispatch` с параметром `wait_for_idle` в секундах.

Теги имеет смысл добавить позже, когда появится прод и стенд одновременно.
Тогда: `main` → стенд, тег `v*` → прод. Сейчас это лишняя сущность.

## 4. Четыре вещи, которые ломают именно этот бэкенд

Если будете переписывать деплой — это то, чего не видно со стороны.

### `docker compose down -v` стирает результаты

Флаг `-v` удаляет тома. В томах лежат очередь и результаты прогонов, каждый из
которых стоил часов работы модели и живых денег. Восстановить нельзя — только
пересчитать заново за те же деньги. В `deploy.sh` `down` не вызывается вовсе:
`up -d --build` сам пересоздаёт контейнер.

### Профиль обязателен, иначе «успешный» деплой без сервиса

`docker compose up -d` **без** `--profile` ничего не поднимет и выйдет с кодом
0. Деплой отрапортует успех, а сервиса не будет. Всегда
`--profile real` (рабочий режим) или `--profile mock` (имитация без модели и
без денег).

### `.env` живёт на сервере и не должен затираться

Там `HF_TOKEN` (доступ к модели, привязан к деньгам) и `PTO_API_TOKEN` (пароль
к API). В репозитории его нет и быть не должно. `git reset --hard` его не
трогает, потому что файл не отслеживается — но если решите деплоить через
`rsync --delete`, он исчезнет.

### Прогон переживает перезапуск, но не бесплатно

Очередь и посчитанные листы лежат на диске: после перезапуска сервис вернёт
задачу в очередь и досчитает остаток, ничего не пересчитывая. Теряется только
лист, который считался в момент перезапуска, — вместе с потраченными на него
токенами (до 70 тысяч). Не катастрофа, но и не ноль.

## 5. Как проверить, что деплой отработал

```bash
curl http://сервер:8000/health          # открыт всегда, даже когда API закрыт токеном
```

Глубже — самопроверка, которая ставит документ в очередь по-настоящему,
ждёт листы и проверяет результат:

```bash
ssh pto-deploy@сервер
cd /opt/pto/backend
docker compose --profile mock up -d          # имитация: без модели и без денег
python3 -m service.smoke_test
docker compose --profile mock down
```

13 проверок, ноль зависимостей сверх тех, что уже нужны бэкенду. На сервисе в
режиме `real` скрипт остановится и попросит `--yes-real`, чтобы проверка не
стоила денег случайно.

## 6. Если что-то пойдёт не так

| Симптом | Причина |
| --- | --- |
| Actions завис на шаге SSH | не добавлен `known_hosts` или ключ не тот. В workflow это делает `ssh-keyscan`, проверьте `DEPLOY_PORT` |
| `permission denied` при `docker compose` | пользователь не в группе `docker` |
| Деплой прошёл, но сервиса нет | забыт `--profile` |
| `НЕТ .env на сервере` | скрипт остановился намеренно: без настроек сервис поднимется пустым |
| Сборка упала, сервис работает | так и задумано: образ собирается до остановки контейнера, неудачная сборка старый контейнер не трогает |
| `/health` отвечает, но режим не тот | `PTO_PIPELINE_MODE` в `.env` перекрыт значением из compose — профиль главнее |

## 7. Что ещё стоит знать про сервер

- **Порт 8000 наружу лучше не пускать.** Наружу — только интерфейс. Если всё
  же нужен снаружи, `PTO_API_TOKEN` обязателен: без него любой прохожий
  поставит документ в очередь и потратит деньги у провайдера моделей.
- **Бэкапы.** `state` (очередь) и `runs` (результаты прогонов) — единственное,
  что нельзя восстановить бесплатно.
- **Место.** Комплект в 1000 страниц — сотни мегабайт текста, не считая
  исходных PDF в `uploads`.
- **Общая папка `uploads`.** Фронт кладёт туда PDF, бэкенд читает оттуда по
  пути — файл между частями не пересылается. Путь задаётся переменной
  `PTO_UPLOADS_HOST_DIR` в `backend/.env`, а разрешение читать оттуда —
  `PTO_ALLOWED_PDF_ROOTS`. Подробности в `ДЛЯ_ФРОНТЕНДА.md`, раздел 4.
