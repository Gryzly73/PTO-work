# Что нужно сделать на фронтенде, чтобы заработал наш бэкенд

Документ для разработчика `pto-drawings`. Короткий ответ: **меняется один файл
и добавляется одна переменная окружения**. Компоненты, маршруты, типы и стили
трогать не надо.

Бэкенд — это конвейер `PDF → Markdown` для проектной документации (текст,
таблицы, словесное описание чертежей) плюс HTTP-слой над ним: очередь
документов, прогресс по листам, выдача листов по мере готовности,
возобновление после перезапуска.

---

## 1. Почему хватает одного файла

Интерфейс уже умеет всё, что нужно для потоковой обработки: показывает
`готово N из M`, процент, текущий лист и шаг, держит состояние в `db.json`
(переживает F5), позволяет докидывать файлы в очередь во время работы.

Не хватало только источника страниц. Родной `src/lib/process-document.ts`
разбирал PDF своим текстовым слоем через `unpdf`, а для чертежа вставлял
заглушку «_на следующем этапе его пишет модель_» — то есть был написан ровно в
расчёте на подстановку конвейера.

Замена экспортирует ту же функцию `processDocument(id)` с той же сигнатурой,
поэтому `src/app/api/documents/route.ts` и
`src/app/api/documents/[id]/process/route.ts` править не нужно.

---

## 2. Шаг 1 — заменить `src/lib/process-document.ts`

Файл лежит в нашем репозитории: `backend/service/frontend-patch/`. Там же —
готовый патч.

```bash
cd <ваш pto-drawings>
git checkout -b pto-backend-integration
git apply <путь до PTO>/backend/service/frontend-patch/process-document.patch
git commit -am "Брать разбор PDF из конвейера ПТО вместо текстового слоя"
```

Если патч не ложится (файл у вас уже изменился) — просто скопируйте
`backend/service/frontend-patch/process-document.ts` поверх своего
`src/lib/process-document.ts`. Это законченный файл, а не фрагмент.

Что делает новая версия:

1. ищет уже идущую задачу по `documentId` — после перезапуска Next прогон
   подхватывается, а не начинается заново;
2. если задачи нет — создаёт: `POST /jobs` с **путём** к файлу в `uploads/`;
3. раз в 3 секунды опрашивает `GET /jobs/{id}`, забирает новые листы
   пачками по 40 и пишет их в `db.json` через ваш `updateDocument`;
4. пишет в базу только при изменении статуса — иначе на многочасовом прогоне
   `db.json` переписывался бы каждые 3 секунды без причины;
5. держит ретраи (см. раздел 5).

## 3. Шаг 2 — переменные окружения фронтенда

| Переменная | По умолчанию | Зачем |
| --- | --- | --- |
| `PTO_BACKEND_URL` | `http://127.0.0.1:8000` | адрес бэкенда. В docker-compose — `http://backend:8000` |
| `DATA_ROOT` | `process.cwd()` | корень данных; папка загрузок вычисляется как `DATA_ROOT/uploads` — так же, как в вашем `persist.ts` |
| `PTO_POLL_MS` | `3000` | как часто спрашивать статус |
| `PTO_MAX_FAILURES` | `20` | сколько подряд неудачных опросов терпеть, прежде чем признать прогон упавшим |

## 4. Обязательное условие: общая папка `uploads`

**PDF между частями не пересылается.** Фронт кладёт файл в свою
`DATA_ROOT/uploads`, а бэкенду отдаёт только путь — бэкенд читает файл оттуда
сам. На гигабайтных комплектах это экономит и время, и диск.

Отсюда единственное требование к развёртыванию: **бэкенд должен видеть ту же
папку `uploads`, что и фронт**, и она должна быть в его белом списке:

```bash
PTO_ALLOWED_PDF_ROOTS=<...>/pto-drawings/uploads
```

Без этого бэкенд ответит `403` — «Путь вне разрешённых каталогов». Это не
ошибка интеграции, а защита: сервис не берёт файлы откуда попало.

В `docker-compose.yml` из корня проекта это уже сделано — обе части монтируют
один том `app-data:/data`.

## 5. Три вещи, которые нельзя сломать

### 5.1 Строка `**Файл:**` в шапке листа

`src/lib/storage.ts`, функция `listDocuments()`: если markdown страницы **не
содержит** подстроки `**Файл:**`, она перегенерирует его заглушкой из
`extractedText`.

На практике это значит: результат многочасового прогона молча затирается
текстовым слоем PDF. Мы обошли это тем, что шапка каждого листа от бэкенда эту
строку содержит, — и `storage.ts` править не пришлось.

**Просьба:** если будете трогать `listDocuments()`, не завязывайтесь на эту
подстроку сильнее, чем сейчас. Лучше — убрать саму перегенерацию: она была
нужна для старого пути через `unpdf`, а теперь работает как мина.

### 5.2 Ретраи в клиенте

Прогон документа идёт **часами** (один лист чертежа — до 16 минут), клиент за
это время делает тысячи запросов. Обрыв keep-alive неизбежен.

Реальный случай из отладки: бэкенд честно досчитал 6 листов из 6, а интерфейс
показал `fetch failed` и три листа — клиент отвалился в 20:00, бэкенд работал
до 20:52. Поэтому в новой версии: три попытки на запрос, сдаёмся только после
20 неудач подряд, одиночная ошибка не роняет прогон.

Если будете переписывать сетевой слой — ретраи обязаны остаться.

### 5.3 Уже полученные листы не стираются при ошибке

При падении клиент ставит документу статус `error`, но **не трогает** уже
загруженные страницы, и в сообщение добавляет подсказку про «Обработать
заново». Повторный запуск найдёт ту же задачу на бэкенде и заберёт остаток —
ничего не пересчитывая.

## 6. Что API уже умеет, а интерфейс пока не показывает

Это задачи на доработку UI. Бэкенд для всех готов.

| Что показать | Откуда брать |
| --- | --- |
| **Кнопка «Отменить»** | `POST /jobs/{id}/cancel`. Отмена срабатывает между листами, посчитанное сохраняется |
| **Расход токенов и время** | поля `usage`, `elapsedSec` в `GET /jobs/{id}` |
| **Предупреждение про провайдера** | `profile.mode == "real"` означает, что страницы уходят стороннему провайдеру (сейчас `featherless-ai`). Пока интерфейс доступен коллегам по ссылке, реальные проекты заказчика через него гонять нельзя — баннер об этом нужен в UI, а не только в документации |
| **Какие листы не удались** | `pageErrors` — словарь `{ "12": "текст ошибки" }`. Документ считается ошибочным, только если не вышел **ни один** лист |
| **Пометка `[MOCK]`** | в режиме `mock` каждая страница помечена. Стоит показывать явно, чтобы имитацию не приняли за работу модели |
| **Полное извлечение по фрагментам** | `GET /jobs/{id}/pages/{n}/raw` — сырой вывод конвейера. В обычный markdown он не попадает: на чертеже это до 100 тыс. символов на лист, читать невозможно, а браузер рисует такое тяжело |

## 7. Справочник API

Все ответы — JSON, кроме помеченных как текст. Интерактивная документация
живёт на самом сервисе: `/docs`.

| Маршрут | Что делает |
| --- | --- |
| `GET /health` | жив ли сервис |
| `GET /` | страница статуса в браузере |
| `POST /jobs` | поставить документ в очередь: JSON `{path, originalName, projectId, documentId}` либо multipart с файлом |
| `GET /jobs?documentId=...` | найти задачу по документу — этим клиент подхватывает прогон после перезапуска |
| `GET /jobs/{id}` | статус, прогресс, ошибки, расход |
| `GET /jobs/{id}/pages?pages=1,2,3` | забрать листы пачкой |
| `GET /jobs/{id}/pages/{n}` | один лист |
| `GET /jobs/{id}/pages/{n}/raw` | сырой вывод конвейера по листу (текст) |
| `GET /jobs/{id}/markdown` | весь документ одним markdown (текст) |
| `POST /jobs/{id}/cancel` | остановить между листами |
| `POST /jobs/{id}/retry` | пересчитать неудавшиеся листы |
| `DELETE /jobs/{id}` | убрать задачу из очереди |

Ответ `GET /jobs/{id}` — то, на чём держится прогресс:

```jsonc
{
  "id": "…",
  "documentId": "…",           // ваш id документа, по нему ищется задача
  "status": "processing",       // queued | processing | done | error | canceled
  "pageCount": 49,
  "pagesRequested": [1, 2, 3],
  "pagesDone": [1, 2],          // номера готовых листов
  "pagesDoneCount": 2,
  "pagesTotal": 49,
  "percent": 4,
  "processingPage": 3,          // какой лист считается прямо сейчас
  "processingStep": "drawings", // queued | text | drawings | done — совпадает с вашим ProcessingStep
  "pageErrors": {},
  "errorMessage": null,
  "usage": {},                  // токены
  "profile": {},                // модель, режим, флаги прогона
  "elapsedSec": 128.4
}
```

Лист (`GET /jobs/{id}/pages/{n}`) приходит в форме вашего `DocumentPage`:
`{pageNumber, kind, markdown, extractedText}`, где `kind ∈ drawing | text |
table | mixed`. Есть ещё поля `fragments`, `fragmentsRemovedLines`, `schema` —
они служебные, клиент их не сохраняет, на типы не влияют.

## 8. Как поднять бэкенд у себя

Нужен Docker. Из папки `backend/`:

```bash
cp .env.example .env

# 1) Имитация: лист считается ~1,5 секунды, модель не вызывается, денег не тратит.
#    Этого достаточно, чтобы проверить очередь, прогресс и поведение UI.
docker compose --profile mock up --build

# 2) Настоящий прогон. Нужен HF_TOKEN в .env.
docker compose --profile real up --build
```

Профиль обязателен. Без него compose ответит «no service selected» — это не
поломка, а защита: `real` тратит деньги и отправляет страницы наружу, поэтому
режим выбирается осознанно.

Чтобы бэкенд видел вашу папку загрузок, укажите её в `backend/.env`:

```bash
PTO_UPLOADS_HOST_DIR=<путь до вашего pto-drawings>/uploads
```

Обе части сразу (бэкенд + интерфейс) — `docker compose --profile mock up
--build` из корня `PTO/`, там всё смонтировано заранее.

Проверка: <http://localhost:8000/health> отвечает, на
<http://localhost:8000> — страница статуса.

### Грабли с правами на общий том

Ваш образ работает под пользователем `node` (uid 1000), а named volume Docker
создаёт от root. При первом же запросе Next падает:

```
Error: EACCES: permission denied, mkdir '/data/data'
```

В корневом `docker-compose.yml` это решено init-контейнером, который готовит
том до старта фронта:

```yaml
  data-init:
    image: busybox:1.36
    command: sh -c "mkdir -p /data/uploads /data/data && chown -R 1000:1000 /data"
    volumes:
      - app-data:/data
```

Фронт ждёт его через `depends_on: {data-init: {condition:
service_completed_successfully}}`. Бэкенд работает от root и эти файлы читает
без вопросов.

Если будете собирать свой compose — либо повторите этот приём, либо создайте
`/data` прямо в своём `Dockerfile` с владельцем `node`. Второе чище, но это
уже правка вашего репозитория, поэтому мы её не делали.

## 9. Чек-лист «заработало»

Гоняйте в режиме `mock` — быстро и бесплатно.

1. Загрузили PDF — документ встал в `queued`, затем `processing`.
2. Листы появляются **по одному**, счётчик `n/N` и процент растут.
3. Обновили страницу браузера на середине — прогресс не потерялся.
4. Загрузили второй файл, пока считается первый — он ждёт очереди, интерфейс
   не блокируется.
5. Перезапустили бэкенд на середине — прогон продолжился, готовые листы **не**
   пересчитываются.
6. В `db.json` у страниц лежит markdown с шапкой `**Файл:**` — значит,
   `listDocuments()` его не затрёт.

## 10. Если что-то не так

| Симптом | Причина |
| --- | --- |
| `403` при создании задачи | папки `uploads` нет в `PTO_ALLOWED_PDF_ROOTS` бэкенда |
| `404` на `POST /jobs` с путём | бэкенд не видит файл по этому пути — значит, папка `uploads` у частей разная |
| `fetch failed` и прогон встал | бэкенд не поднят или недоступен по `PTO_BACKEND_URL`; проверьте `/health` |
| Листы пришли, а потом markdown «схлопнулся» в текстовый слой | сработала перегенерация в `listDocuments()` — см. 5.1 |
| `no service selected` у docker compose | не указан `--profile mock` или `--profile real` |
| `EACCES: permission denied, mkdir '/data/data'` | named volume принадлежит root, а Next работает под `node` — см. «Грабли с правами на общий том» |
| Все страницы помечены `[MOCK]` | бэкенд поднят в режиме имитации, переключите профиль на `real` |

Вопросы по бэкенду — к нам. Детали сервиса и все переменные окружения:
`backend/service/README.md`. Как устроен сам конвейер простыми словами:
`backend/КАК_ЭТО_РАБОТАЕТ.md`.
