# HTTP-сервис конвейера

Веб-лицо конвейера `PDF → Markdown`. Сам `hf_api_bench.py` не менялся —
сервис вызывает его как библиотеку, по одному листу за вызов.

Зачем именно постранично: так виден точный прогресс, прогон можно остановить
между листами, а после перезапуска — продолжить с того места, где оборвался.
На 1000 страниц (~30 часов) это принципиально.

## Запуск

Три способа, логика у всех одна: настройки читаются из `backend/.env`,
переменные окружения их перекрывают, пути задаются снаружи.

```powershell
# 1. Напрямую
pip install -r service/requirements.txt   # конвейер ставится из ../requirements.txt
cd backend
python -m service

# 2. Локальный батник: ставит зависимости, создаёт папки, ждёт /health,
#    по флагу поднимает и фронтенд. Личный файл, в git не входит.
run-local.bat mock all
run-local.bat stop

# 3. Только бэкенд в контейнере (из backend/). Режим — профиль:
docker compose --profile mock up --build   # имитация, без модели и денег
docker compose --profile real up --build   # настоящий прогон через HF

# 4. Обе части в контейнерах (из корня PTO), те же профили
docker compose --profile mock up --build
```

Профиль обязателен. Без него compose скажет «no service selected»: `real`
тратит деньги и отправляет страницы стороннему провайдеру, поэтому режим
выбирается осознанно. У `mock` свои тома под прогоны и очередь — имитация не
подмешивается к настоящим результатам, и документ, «посчитанный» за полторы
секунды, не выглядит готовым после переключения на `real`.

Проверка: <http://127.0.0.1:8000/health>, интерактивная документация — `/docs`.

Батник и compose делают одно и то же в одном порядке: зависимости → папки
(в контейнере это тома) → бэкенд → ожидание `/health` → фронтенд. Отличаются
только пути: локально это папки проекта, в контейнере — `/data`, `/runs`,
`/state`. Порт батник спрашивает у самого `config.py`, а не разбирает `.env`
отдельно — иначе завелась бы вторая логика, которая разойдётся с первой.

### Режимы

| `PTO_PIPELINE_MODE` | Что делает |
| --- | --- |
| `mock` (дефолт на localhost) | лист за ~1.5 с без обращения к модели, вывод помечен `[MOCK]` |
| `real` (дефолт при `PTO_ENV`/`NODE_ENV=production`, и в compose `--profile real`) | настоящий прогон VLM через HF Inference Providers |

`mock` нужен, чтобы проверять интеграцию с интерфейсом — очередь, потоковую
выдачу листов, поведение при перезагрузке страницы — не тратя часы и деньги.
Принять его вывод за работу модели нельзя: каждая страница помечена.

Приоритет выбора: `PTO_PIPELINE_MODE` → `USE_MOCK_PROCESSOR` → `PTO_ENV`/`NODE_ENV`
→ иначе `mock`.

**Данные уходят наружу.** В режиме `real` страницы отправляются стороннему
провайдеру (сейчас `featherless-ai`). До перехода на локальную модель через
веб-интерфейс стоит гонять только тестовые PDF.

### Переменные окружения

| Переменная | По умолчанию | Смысл |
| --- | --- | --- |
| `PTO_PIPELINE_MODE` | `real` / `mock` | явный выбор обработчика |
| `USE_MOCK_PROCESSOR` | `1` / `0` | алиас, если `PTO_PIPELINE_MODE` не задан |
| `PTO_ENV` / `NODE_ENV` | `production` → real, иначе mock | автовыбор окружения |
| `PTO_MODEL` | `qwen3vl-32b` | id из каталога `python hf_api_bench.py --list` |
| `PTO_PROVIDER` | — | провайдер HF; `auto` не использовать |
| `PTO_SERVICE_HOST` / `PTO_SERVICE_PORT` | `127.0.0.1` / `8000` | адрес сервиса |
| `PTO_API_TOKEN` | — | общий секрет; пусто — сервис открыт. Задан — все маршруты кроме `/health` требуют `X-PTO-Token` |
| `PTO_STATE_DIR` | `service/state` | очередь (`jobs.json`) и загруженные PDF |
| `PTO_RUNS_DIR` | `../hf_runs` | папки прогонов |
| `PTO_UPLOADS_DIR` | `<state>/uploads` | куда класть файлы, пришедшие по multipart |
| `PTO_ALLOWED_PDF_ROOTS` | `<uploads>` | каталоги, из которых можно брать PDF по пути (разделитель `;`) |
| `PTO_PAGE_CONCURRENCY` | `1` | листов одновременно; 3 замерено (вдвое быстрее), но теряется порядок листов |
| `PTO_INCLUDE_FRAGMENTS` | `0` | выводить ли PASS-B в markdown интерфейса |
| `PTO_SHEET_AWARE` / `PTO_TWO_PASS` / `PTO_LAYER_AWARE` | `1` | флаги качества |
| `PTO_ZONE_HINTS` | `0` | тест-сетовые подсказки по номеру страницы — на чужих PDF вредны |
| `PTO_MAX_UPLOAD_MB` | `400` | лимит загрузки |

`HF_TOKEN` берётся из `backend/.env` тем же `load_dotenv`, что и в CLI.

## API

| Метод | Путь | Назначение |
| --- | --- | --- |
| `GET` | `/health` | режим, профиль прогона, счётчики очереди, `currentJobs` — что считает каждая полоса (`model`, `vector`) |
| `POST` | `/jobs` | поставить документ в очередь: multipart с файлом либо JSON `{path, originalName, projectId, documentId, pages}` |
| `GET` | `/jobs` | очередь; фильтры `projectId`, `documentId`, `status`, `active` |
| `GET` | `/jobs/{id}` | статус, текущий лист, `pagesDone`, `usage` |
| `GET` | `/jobs/{id}/pages` | готовые листы; `after=N` — дельта, `pages=1,5,7` — выборочно |
| `GET` | `/jobs/{id}/pages/{n}` | один лист |
| `GET` | `/jobs/{id}/pages/{n}/raw` | сырой вывод конвейера по листу (PASS-0/A/B) |
| `GET` | `/jobs/{id}/markdown` | весь документ одним markdown |
| `POST` | `/jobs/{id}/cancel` | остановить (сработает после текущего листа) |
| `POST` | `/jobs/{id}/retry` | досчитать недостающие листы; `?reset=true` — с нуля |
| `DELETE` | `/jobs/{id}` | убрать задачу; `?purge=true` — вместе с артефактами |
| `GET` | `/jobs/{id}/pages/{n}/geometry` | геометрия листа чертежа в CSV: линии, полилинии, подписи с координатами |
| `GET` | `/jobs/{id}/pages/{n}/preview` | картинка листа чертежа; `?format=svg\|png` |
| `GET` | `/projects/{id}/sections` | состав проекта по разделам: листы, источники, расхождения |
| `GET` | `/projects/{id}/report` | сводный отчёт по проекту одним markdown; `?bodies=false` — только состав |

`pages` принимает тот же формат, что CLI: `1,3,5`, `35-41,44-49`, `all`.

### Чертёж: геометрия и картинка

Оба маршрута отвечают только для DWG и DXF; на PDF они дают 404 — страницу PDF
интерфейс рисует сам через pdf.js.

Основной путь — `geometry`: интерфейс получает лист первичными данными и рисует
его сам, поэтому работают зум без потери качества, поиск по тексту и привязка
замечания к координатам чертежа. `preview` — запасной путь и миниатюры.

Картинка строится из тех же примитивов, что уходят в CSV, поэтому совпадает с
геометрией точка в точку. Имя файла в кэше содержит версию отрисовки: без неё
прогоны, сделанные до её смены, до конца жизни отдавали бы старые картинки.

### Сводный отчёт по разделу

По разделу проекта приходит не один файл: графика — десятком DWG, текстовая
часть — отдельным PDF, а часто ещё и весь альбом в PDF. Два эндпоинта проекта
сводят это в один документ: листы раскладываются по разделам и документам
комплекта — по шифру и номеру листа из основной надписи (`stamp.py`), а не по
именам файлов и не по порядку страниц.

Где один лист пришёл из двух источников, **истина — DWG**: там текст лежит
данными, тогда как в PDF он восстанавливается по отрисовке. Версия из PDF не
выбрасывается — если наименования листа разошлись, это попадает в раздел
«Расхождения между источниками»: обычно так видно, что альбом печатали с
другой редакции чертежа.

Реквизиты читаются из самих файлов, без вызова модели, поэтому состав проекта
доступен сразу после загрузки — ещё до того, как конвейер дойдёт до последнего
листа. Тексты листов подставляются те, что уже посчитаны; остальные помечены
как необработанные.

Лист отдаётся в том виде, в каком его ждёт фронтенд:

```json
{ "pageNumber": 1, "kind": "drawing", "markdown": "# Лист 1…", "extractedText": "…" }
```

`kind` — из `sheet_aware` (`plan`/`scheme` → `drawing`), `extractedText` —
текстовый слой PDF, но только если он читаемый: у CAD-PDF часто сломан
`ToUnicode`, такой слой отдаётся пустым.

## Что лежит в папке прогона

```
hf_runs/<stamp>_<model>_svc-<id>/
  pages/page_NNNN.md      ← вывод конвейера, PASS-0 / PASS-A / PASS-B
  frontend/page_NNNN.json ← тот же лист в формате фронта (кэш)
  out.md                  ← сборка «## Страница N», пересобирается в конце
```

`out.md` соблюдает контракт разбиения, поэтому прогон, запущенный через
сервис, читается `compare_to_etalon.py`, `build_ios2_md.py` и остальными
инструментами бэкенда так же, как запущенный из CLI.

## Поведение под нагрузкой

- **Очередь.** Две полосы. PDF идут через модель по одному документу за раз,
  остальные ждут в `queued`. DWG и DXF считаются из данных без модели и идут
  отдельным потоком: чертёж не ждёт за PDF без текстового слоя, у которого
  один лист занимает до 15 минут. Новые файлы можно добавлять в любой момент.
- **Перезапуск.** Задачи в статусе `processing` возвращаются в очередь и
  досчитываются — готовые `page_NNNN.md` не пересчитываются.
- **Ошибка листа.** Лист попадает в `pageErrors`, документ продолжает
  считаться. Документ становится `error`, только если не вышел ни один лист.
- **Лист с дырами.** Если модель не прочитала часть фрагментов (keep-going
  при отказе провайдера) или у листа нет текстового слоя и всё читалось по
  картинке, лист считается готовым, но попадает в `pageWarnings`, а в его
  markdown и JSON идут `trust` (уровень доверия: `dwg | layer | vlm | none`),
  `warnings` и `numbers` — числа описания, которых нет в документе. Сырой
  текст исключения провайдера в лист не попадает: на месте дыры пометка
  «фрагмент не прочитан».
- **Отмена.** Проверяется между листами: текущий лист досчитается (в режиме
  `real` это до пары минут), уже готовые сохраняются.
