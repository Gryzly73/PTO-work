# Исследование улучшения распознавания графического содержания чертежей

**Статус:** целевая архитектура Scene Graph. Базовый Markdown-first контур частично реализован; координатная модель объектов и граф — без реализации.
**Дата:** август 2026.  
**Область:** `PTO-work`, графическое понимание схем, планов, разрезов и узлов.  
**Не входит:** обычный текст, табличное извлечение, паспорт документа и сверка с ТЗ стройки.

Связанные документы:

- [ДЛЯ_ЗАКАЗЧИКА_ПЛАН_УЛУЧШЕНИЙ.md](./ДЛЯ_ЗАКАЗЧИКА_ПЛАН_УЛУЧШЕНИЙ.md)
- `УСЛОВНЫЕ_ОБОЗНАЧЕНИЯ_В_ИДЕАЛ.md` — локальный справочный файл, может отсутствовать в git
- `hf_runs/.../SVERKA_S_IDEAL.md` — локальный артефакт контрольного прогона, не версионируется

---

## 1. Цель

Целевой результат — не подробный пересказ картинки, а структурированная модель чертежа:

```text
графические области
  → объекты
  → подписи и марки
  → линии и соединения
  → условные обозначения
  → пространственные и инженерные связи
  → явные пропуски и конфликты
```

По результату должны поддерживаться вопросы:

- что изображено;
- где находится конкретный элемент;
- какая подпись к нему относится;
- с чем он соединён;
- куда идёт линия;
- какой знак легенды использован;
- что система не смогла подтвердить.

---

## 2. Scope

### Входит

- качество рендера графики;
- multi-scale анализ;
- выделение смысловых зон;
- поиск объектов и графических примитивов;
- связь подписи с объектом;
- распознавание условных обозначений;
- привязка легенды к экземплярам;
- трассировка линий;
- построение пространственного графа;
- объединение целого листа и локальных зон;
- межстраничные графические ссылки;
- provenance, confidence и конфликты;
- измерение объектной и реляционной точности.

### Не входит

- распознавание пояснительных записок;
- полнотекстовый OCR;
- извлечение таблиц и ячеек;
- формирование паспорта и штампа документа;
- улучшение общих PDF-text метрик;
- автоматическая проверка соответствия ТЗ стройки.

Короткие подписи, позиции, марки сетей, DN и ИГЭ используются только как атрибуты графических объектов.

---

## 3. Что происходит сейчас

Текущий конвейер:

```text
PASS-0 (sheet-aware) → PASS-A (lean: смысл и связи)
  → PASS-B (тайлы + фиксированные зоны)
    либо пропуск PASS-B при пригодном слое (layer-aware / text-only)
  → Markdown + таблицы из PDF в HTTP-сервисе
```

Основные проблемы:

1. PASS-A видит общий сюжет, но теряет мелкие связи.
2. PASS-B видит детали, но ломает контекст целого листа.
3. Координаты после текстового ответа почти не используются.
4. Один объект, попавший в несколько фрагментов, не имеет устойчивого ID.
5. Линия и подпись могут оказаться в разных тайлах.
6. Пересечение линий может быть ошибочно принято за соединение.
7. Легенда существует как список, но не как словарь распознанных экземпляров.
8. Нет промежуточной структуры объектов и отношений.
9. Recall/Key оценивают слова, но не понимание графики.
10. Рабочий HTTP-профиль (`sheet-aware + lean + layer-aware`) отличается от CLI без явно переданных флагов.
11. При пригодном текстовом слое плотного CAD-чертежа PASS-B пропускается, поэтому графику анализирует главным образом PASS-A.
12. Объединение наблюдений выполняется по текстовым строкам, а не по `object_id`.

Уже реализованы как базовые механизмы: адаптивный бюджет рендера по типу листа, фиксированные зоны, грубый поворот, quality-gate PASS-A и отдельные повторные попытки. Они не заменяют Visual Layout и Scene Graph.

## 4. Целевая архитектура

```text
PDF page
  → Render Policy
  → Visual Layout
  → Region Router
  → Object / Line / Symbol detectors
  → Local VLM/OCR observations
  → Drawing Scene Model
  → Conflict Resolver
  → Drawing Graph
  → Client description / Q&A / audit overlay
```

### Drawing Scene Model

```text
DrawingRegion
  id, kind, bbox, confidence

DrawingObject
  id, class, bbox, label, attributes, sources

DrawingLine
  id, polyline, style, endpoints, direction, sources

LegendEntry
  id, name_from_sheet, symbol_template

SymbolInstance
  id, legend_id, bbox, confidence

DrawingRelation
  subject, predicate, object, confidence, sources

UnresolvedItem
  variants, bbox, reason
```

Главное отличие от Markdown-first подхода: текст становится представлением структурированной модели, а не единственным результатом распознавания.

## 5. Render Policy для чертежей

### 5.1. Native raster profile

Для страниц с большим встроенным изображением:

- определить native width/height;
- вычислить покрытие страницы растром;
- не увеличивать изображение безусловно;
- для схем и планов тестировать коэффициенты 1,5× / 2× / 2,5× native;
- сохранять профиль в метаданных прогона.

Зачем:

- чрезмерный upscale не добавляет деталей;
- увеличивает число тайлов;
- повышает стоимость и разброс;
- ухудшает повторное масштабирование.

Ограничение: нельзя переносить табличный 1× cap на чертежи — прошлые эксперименты показывали потерю мелких обозначений.

**Текущий main:** разрешение рассчитывается из общего `page_max`; native-размер и покрытие встроенного изображения в политику рендера не входят.

### 5.2. Direct clip rendering

Вместо crop уменьшенной полной страницы:

```text
region bbox in PDF coordinates
  → page.get_pixmap(clip=region, target DPI)
  → recognizer
```

Преимущества:

- мелкие подписи получают реальное разрешение;
- не нужно рендерить гигантский полный лист;
- каждая зона имеет собственный pixel budget.

**Текущий main:** сначала рендерится полная страница, затем зона вырезается из изображения. Прямой `page.get_pixmap(clip=...)` не используется.

### 5.3. Формат изображения

- PNG: тонкие линии, штриховки, условные знаки, короткие коды;
- JPEG: общее изображение листа;
- обязательный byte/pixel cap;
- shrink-retry при HTTP 413 — **не реализован**.

### 5.4. Orientation и deskew

- грубый поворот 0/90/180/270 через Tesseract OSD — **реализован**;
- fine deskew по доминирующим линиям — **не реализован**;
- применять коррекцию только при достаточном confidence;
- не ориентироваться по одной вертикальной подписи.

## 6. Visual Layout

### 6.1. Задача

Разделить лист не равномерной сеткой, а по смысловой структуре.

### 6.2. Искомые зоны

- основная схема или план;
- легенда;
- экспликация объектов;
- узлы;
- разрезы;
- блоки выносок;
- зоны плотных обозначений;
- пустые поля;
- графические продолжения за границу зоны.

### 6.3. Сигналы

- connected components;
- плотность линий;
- плотность коротких текстовых меток;
- повторяющиеся небольшие «знак + подпись»;
- замкнутые контуры;
- длинные линии;
- whitespace separation;
- цветовые слои;
- локальные особенности векторной геометрии PDF.

### 6.4. Выход

```json
{
  "id": "region_network_north",
  "kind": "network",
  "bbox": [0.05, 0.10, 0.72, 0.55],
  "confidence": 0.82,
  "recognitionPolicy": "spatial"
}
```

Зоны не должны зависеть от номера страницы тестового набора.

## 7. Multi-scale распознавание

Предлагается три масштаба.

### Scale 1 — целый лист

Назначение:

- общий сюжет;
- крупные области;
- приблизительные направления;
- контекст назначения объектов.

### Scale 2 — смысловая зона

Назначение:

- группа оборудования;
- участок сети;
- геологический разрез;
- узел;
- легенда.

### Scale 3 — локальный элемент

Назначение:

- условный знак;
- позиция;
- короткая марка;
- стрелка;
- место соединения;
- подпись рядом с выноской.

Наблюдения разных масштабов должны ссылаться на общие `object_id`, а не просто конкатенироваться.

---

## 8. Тайлы

### 8.1. Overlap

Для схем и планов использовать перекрытие порядка 10–18%.

Цель:

- линия и подпись чаще находятся вместе;
- объект не обрезается ровно по границе;
- можно сопоставить экземпляры между соседними зонами.

**Текущий main:** тайлы смежные и не перекрываются.

### 8.2. Ограничение

Два соседних тайла видят одни и те же пиксели. Совпадение их ответов не является независимым подтверждением.

### 8.3. Keep-better rerun

Повторять зону при:

- ошибке API;
- явной петле;
- конфликте целого листа и зоны;
- высокой визуальной плотности при почти пустом результате;
- незакрытой линии на обоих краях зоны.

Новый вариант принимается только при улучшении структурного score, а не по длине.

## 9. Объекты и подписи

### 9.1. Object candidates

Источники:

- замкнутые контуры;
- connected components;
- повторяющиеся формы;
- VLM grounding;
- локальные подписи;
- векторные блоки PDF;
- цвет и стиль линий.

### 9.2. Label association

Подпись связывается с объектом по совокупности:

- расстояния;
- направления выноски;
- общей зоны;
- совпадения марки в нескольких масштабах;
- положения относительно линии;
- отсутствия другого более близкого кандидата.

### 9.3. Неоднозначность

Если одна подпись может относиться к двум объектам:

```text
status = needs_review
candidates = [object_17, object_18]
```

Система не должна выбирать ближайший объект без дополнительных признаков.

## 10. Линии, соединения и трассы

### 10.1. Line extraction

Возможные методы:

- PDF vector paths;
- skeletonization растра;
- probabilistic Hough;
- contour tracing;
- сегментация цветовых слоёв;
- VLM grounding для семантической проверки.

### 10.2. Junctions

Нужно различать:

- реальное Т-образное соединение;
- пересечение без соединения;
- разрыв линии под подписью;
- стрелку;
- переход за границу зоны;
- условное обозначение арматуры внутри линии.

### 10.3. Stitching

Линии соседних зон объединяются по:

- близости граничных точек;
- углу;
- цвету/стилю;
- ширине;
- марке сети;
- согласованному направлению.

### 10.4. Выход

```json
{
  "id": "line_v2_04",
  "label": "В2",
  "polyline": [[...], [...]],
  "from": "pump_N1",
  "to": "external_network",
  "direction": "outgoing",
  "confidence": 0.74
}
```

## 11. Условные обозначения и легенда

### 11.1. Legend parsing

1. найти область легенды;
2. выделить строки;
3. отделить изображение знака от подписи;
4. сохранить template crop;
5. не заменять знак Unicode-символом как единственным идентификатором.

### 11.2. Instance matching

Методы:

- ORB/SIFT для контрастных знаков;
- multi-scale template matching;
- connected components;
- сравнение локальных дескрипторов;
- VLM grounding как проверка кандидата.

### 11.3. Первый набор

- пронумерованные кружки ИГЭ;
- позиции арматуры;
- повторяющиеся марки оборудования;
- стрелки направления;
- простые символы колодцев/камер.

### 11.4. Поздний набор

- штриховки грунтов;
- визуально похожая арматура;
- знаки, различающиеся одной чертой;
- символы, перекрытые линиями.

### 11.5. Выход

```text
legend entry → symbol instances[]
unmatched legend entries[]
unclassified instances[]
confusion pairs[]
```

## 12. Scene Graph

### 12.1. Базовая схема

```text
Node
  id, type, label, bbox, attributes, sources

Edge
  subject, relation, object, geometry, confidence, sources
```

### 12.2. Схема

```text
резервуар → соединён_с → всасывающая линия
линия → проходит_через → затвор NO
линия → входит_в → насос Н1
насос Н1 → подаёт_в → сеть В2
```

### 12.3. Генплан

```text
объект 1ш2 → подключён_к → сеть В1
сеть К1 → проходит_вдоль → проезд
ветвь В1 → входит_в → блок 4
```

### 12.4. Геологический разрез

```text
скважина 17 → пересекает → ИГЭ-2
фундамент → опирается_над → ИГЭ-4
ось IV → относится_к → разрез IV–IV
```

### 12.5. Узел

```text
панель → крепится_к → профиль
профиль → имеет_размер → L160×10
утеплитель → расположен_между → панель/основание
```

## 13. Fusion и provenance

Каждое наблюдение должно сохранять:

```text
source:
  full_page
  semantic_region
  local_crop
  vector_geometry
  local_label_reader

bbox
confidence
run_id
```

Правила:

- геометрия определяет положение;
- локальный crop уточняет атрибут;
- целый лист задаёт контекст;
- ни один текстовый ответ не должен удалять геометрически подтверждённый объект;
- конфликт остаётся в модели до разрешения или ручной проверки.

---

## 14. Межстраничный граф

После стабилизации одного листа:

```text
sheet_graph
  nodes
  edges
  references

document_graph
  page → referenced page
  network → continuation pages
  node mark → detail sheets
  section → related plans/schemes
```

Примеры:

- «см. узел 3» связывается с листом узла;
- сеть В2 продолжается между планом и схемой;
- разрез IV–IV связывается с линией разреза на плане;
- марка оборудования связывает план расположения и схему подключения.

Источник каждой межстраничной связи обязателен.

---

## 15. Специализированная маршрутизация

Не использовать один backend одинаково для всех зон:

```text
общий лист
  → VLM context

графический узел
  → high-resolution VLM + object grounding

линии
  → vector/CV tracing

условный знак
  → template/descriptor matching

короткая локальная подпись
  → OCR/VLM consensus

легенда
  → row segmentation + symbol extraction
```

Модельный ансамбль оправдан только для сложных зон, а не для повторной обработки всего листа.

## 16. Измерение качества

### 16.1. Object detection

- object precision/recall;
- bbox IoU для выбранной разметки;
- дубликаты одного объекта;
- пропуски важных классов.

### 16.2. Label binding

- правильная подпись у правильного объекта;
- число неоднозначных привязок;
- false binding rate.

### 16.3. Symbols

- legend entry recall;
- instance precision/recall;
- confusion pairs;
- unmatched rate.

### 16.4. Lines

- полнота трассы;
- endpoint accuracy;
- junction precision/recall;
- crossing-vs-connection accuracy;
- direction accuracy.

### 16.5. Relations

- precision/recall тройки `(subject, relation, object)`;
- полнота ключевого flow path;
- unsupported relation rate.

### 16.6. Engineering Q&A

На лист размечаются 3–5 вопросов:

- куда подаёт насос;
- какой объект подключён к сети;
- какой ИГЭ расположен под фундаментом;
- какой знак соответствует позиции;
- где продолжается линия.

Ответ должен выводиться из Scene Graph, а не оцениваться только по наличию слова.

### 16.7. Run stability

- минимум четыре прогона;
- медиана;
- худший результат;
- число API errors;
- число зон и вызовов;
- стоимость и время.

## 17. Ground truth

Не требуется переписывать весь лист в «идеальный Markdown».

Минимальная разметка:

```text
objects.json
  class, bbox, label

lines.json
  polyline, endpoints, network_mark

relations.yaml
  subject, predicate, object

legend.yaml
  entry, instances

qa.yaml
  question, expected entities/relations
```

Наборы:

1. **Dev:** известные листы ПБ, ОДИ, КР1, КР3.
2. **Hold-out:** 15–25 неизвестных схем/планов/разрезов/узлов.
3. **Fresh seal:** новый комплект перед приёмкой.

Табличный лист КР5 не является основным объектом текущего этапа и должен быть исключён из KPI графического понимания.

---

## 18. Что не делать

1. Не оптимизировать только token Recall/Key.
2. Не считать длинный пересказ доказательством понимания.
3. Не подставлять ГОСТ-классы из памяти модели.
4. Не использовать page-specific zone hints на production PDF.
5. Не считать совпадение соседних тайлов независимым подтверждением.
6. Не объединять линии только по близости координат.
7. Не принимать любое пересечение за соединение.
8. Не строить связный рассказ до формирования объектов и отношений.
9. Не расширять текущий scope на таблицы, обычный текст и паспорт.
10. Не считать `crop_content_zones(page_num)` универсальным layout: эти координаты привязаны к страницам контрольного набора и должны оставаться выключенными в production.

## 19. Roadmap

### Wave D1 — Rendering

- native raster profile;
- direct clip rendering;
- подходящий формат зон;
- 413 guard;
- overlap;
- orientation/deskew.

### Wave D2 — Layout и наблюдения

- semantic regions;
- общие координаты;
- object candidates;
- label association;
- fusion целого листа и зон.

### Wave D3 — Symbols и линии

- legend parsing;
- symbol templates;
- instance matching;
- line tracing;
- junction classification;
- stitching между зонами.

### Wave D4 — Scene Graph

- node/edge schema;
- правила по типам чертежей;
- confidence/conflicts;
- блок «как связано»;
- инженерный Q&A.

### Wave D5 — Document Graph

- ссылки между листами;
- продолжение сетей;
- планы ↔ разрезы ↔ узлы;
- controlled ensemble на сложных зонах.

## 20. Рекомендуемый первый эксперимент

Цель: проверить, что геометрически осмысленные зоны лучше равномерных тайлов.

### Набор

- схема насосной ПБ;
- генплан ОДИ;
- геологический лист КР1;
- геологический лист КР3;
- один неизвестный чертёж каждого типа.

### Варианты

**Baseline:** профиль HTTP-сервиса — `sheet-aware + lean + layer-aware`, без page-specific zone hints. Для CLI эквивалентные флаги передаются явно.

**Experiment:**

1. direct clip rendering;
2. overlap;
3. выделение 3–6 смысловых зон;
4. сохранение bbox каждого наблюдения;
5. объединение по объектам, а не по строкам.

### Метрики

- recall важных объектов;
- правильность object↔label;
- полнота 5–10 relations;
- unsupported relations;
- ответы на инженерные вопросы;
- медиана и худший результат четырёх прогонов;
- стоимость и число вызовов.

### Критерий успеха

- больше правильных объектов и связей;
- меньше неподтверждённых отношений;
- улучшение сохраняется на неизвестных листах;
- стоимость не растёт непропорционально;
- обычные текстовые и табличные контуры не затронуты.

## 21. Итог

Текущая задача — не улучшить весь PDF-конвертер, а научить систему читать графическое содержание чертежа.

Фокус должен сместиться:

```text
от:
  изображение → длинный Markdown

к:
  изображение
    → зоны
    → объекты
    → линии
    → знаки
    → отношения
    → Scene Graph
    → проверяемое описание
```

Именно этот путь создаёт измеримое понимание схем, генпланов, разрезов и узлов, не смешивая задачу с текстом, таблицами и паспортом документа.
