# Спецификация каталога условных обозначений

**Статус:** проект технической спецификации  
**Область:** легенды, условные знаки и их экземпляры на отдельных листах-чертежах  
**Дата:** 24.08.2026  

## 1. Цель

Реализовать отдельный контур, который для каждого листа-чертежа формирует:

1. перечень расшифровок из легенды;
2. перечень уникальных визуальных типов знаков, найденных на чертеже;
3. перечень всех найденных экземпляров знаков с координатами;
4. список знаков, которые найдены, но не расшифрованы;
5. список строк легенды, для которых не найдено ни одного экземпляра;
6. список конфликтов, когда одному знаку подходят несколько расшифровок.

Контур не должен удалять знак только потому, что его назначение не удалось установить.

Целевой результат:

```text
легенда листа
  → расшифровки

основная графика листа
  → кандидаты условных знаков
  → уникальные визуальные типы
  → все экземпляры

расшифровки + визуальные типы + контекст
  → подтверждённые соответствия
  → вероятные соответствия
  → конфликты
  → нерасшифрованные знаки
```

## 2. Клиентский результат

Клиент должен получить ответы на три разных вопроса.

### 2.1. Что расшифровано в документе

Перечень строк легенды:

```text
позиция 3 → затвор дисковый
позиция 6 → кран шаровой
кружок ① → ИГЭ-1
```

Это сведения, явно извлечённые из текущего листа или связанного листа-легенды.

### 2.2. Какие виды знаков фактически присутствуют

Перечень уникальных визуальных типов:

```text
тип S-001 → 12 экземпляров → связан с позицией 3
тип S-002 → 4 экземпляра → расшифровка не установлена
тип S-003 → 2 экземпляра → конфликт позиций 3 и 6
```

### 2.3. Где расположен каждый экземпляр

Перечень всех появлений:

```text
SI-0001 → S-001 → страница 82 → bbox [...] → линия DN200
SI-0002 → S-001 → страница 82 → bbox [...] → состояние NO
SI-0003 → S-002 → страница 82 → bbox [...] → не расшифрован
```

## 3. Термины

### LegendEntry

Строка расшифровки из легенды: изображение знака, позиция, название и источник.

### SymbolCandidate

Графический компонент, который по форме, повторяемости или контексту может быть условным знаком. На этом этапе он ещё может оказаться текстом, пересечением линий или частью оборудования.

### SymbolType

Группа визуально сходных кандидатов. Может быть связана с одной строкой легенды, несколькими конфликтующими строками или не иметь расшифровки.

### SymbolInstance

Конкретное появление знака на конкретной странице с координатами и локальным контекстом.

### ProjectSymbolCatalog

Проверенный справочник обозначений, накопленный по нескольким PDF проекта. Он используется как источник кандидатов, но не отменяет приоритет легенды текущего листа.

## 4. Приоритет источников

При классификации знака применяется следующий порядок:

```text
1. Позиция или подпись у конкретного экземпляра
2. Легенда текущего листа
3. Связанный лист условных обозначений того же документа
4. Проверенный каталог проекта
5. Предоставленный клиентом нормативный справочник
6. Внешнее визуальное сходство или знания модели
```

Источники уровней 5–6 могут формировать кандидатов, но не должны автоматически создавать подтверждённый факт при наличии неоднозначности.

## 5. Граница первой реализации

### Входит в MVP

- поиск областей легенды;
- разделение легенды на строки;
- выделение crop знака и текста строки;
- сохранение исходного изображения знака;
- извлечение позиции и названия;
- поиск ограниченного набора кандидатов на основной графике;
- группировка визуально похожих кандидатов;
- сопоставление с легендой текущего листа;
- сохранение всех нерасшифрованных кандидатов;
- JSON-артефакты на страницу;
- краткая проекция результата в Markdown;
- ручная проверка и исправление каталога без повторного распознавания PDF.

### Не входит в MVP

- полный ГОСТ-классификатор;
- гарантированное распознавание произвольного знака;
- классификация всех штриховок грунта;
- полный граф инженерных связей;
- автоматическое продолжение обозначения между листами;
- обучение собственной нейросетевой модели;
- автоматическое принятие вероятной классификации как подтверждённой.

## 6. Начальный набор классов

Первая версия должна поддерживать классы, для которых можно получить проверяемый результат:

1. пронумерованные кружки ИГЭ;
2. позиции арматуры;
3. стрелки направления;
4. небольшие знаки, встроенные в трубопровод;
5. простые знаки колодцев и камер;
6. повторяющиеся марки оборудования;
7. повторяющиеся линейные обозначения из легенды.

Отдельно сохраняются неизвестные повторяющиеся компоненты `unclassified`.

Сложные штриховки, декоративные элементы оборудования и знаки, различающиеся одной слабой чертой, переносятся в следующий цикл.

## 8. Артефакты

Для каждой страницы:

```text
symbols/
  page_0082/
    legend_entries.json
    symbol_candidates.json
    symbol_types.json
    symbol_instances.json
    summary.json
    symbol_crops/
```

Для документа:

```text
symbols/
  document_symbol_catalog.json
  review_decisions.json
```

Артефакты создаются рядом с текущими результатами прогона, но не изменяют контракт секций `### PASS-0 / PASS-A / PASS-B`.

## 9. Общая архитектура

```text
PDF page
  → Page geometry and render policy
  → Layout masks
      → legend regions
      → drawing regions
      → text/table/stamp exclusion masks
  → Legend extractor
      → rows
      → symbol crops
      → labels and positions
  → Symbol candidate detector
      → vector candidates
      → raster candidates
      → known-template candidates
  → Candidate normalizer
  → Visual clustering
  → Legend matcher
  → Context resolver
  → Page symbol registry
  → Project catalog updater
  → Markdown projection / review overlay
```

## 10. Выделение области легенды

Нельзя полагаться только на фиксированную правую или нижнюю зону.

### Сигналы

- заголовки «Условные обозначения», «Обозначения», «Легенда»;
- повторяющиеся строки одинаковой высоты;
- структура «небольшая графика слева + текст справа»;
- вертикальное выравнивание символов;
- рамка таблицы или колоночная структура;
- компактная область с высокой плотностью коротких подписей;
- векторные блоки одинакового размера.

### Результат

```json
{
  "id": "legend-main",
  "bboxPdf": [0, 0, 0, 0],
  "detectionSources": ["heading", "row_pattern"],
  "confidence": 0.89
}
```

Если область не найдена уверенно, страница не считается страницей без обозначений. Результат должен содержать:

```text
legendStatus = not_found
```

## 11. Разделение легенды на строки

### Векторный PDF

Использовать:

- координаты слов и текстовых spans;
- горизонтальные/вертикальные линии;
- графические paths внутри полосы строки;
- повторяемость вертикальных позиций.

### Растровый PDF

Использовать:

- горизонтальную проекцию connected components;
- whitespace-разделение;
- OCR-блоки текста;
- повторяющуюся высоту строк;
- поиск области знака слева от текста.

### Контроль качества

Строка считается полной, если удалось получить:

- bbox строки;
- непустую графическую или позиционную область;
- текст либо явный статус `text_unreadable`.

Строка без читаемого текста сохраняется, а не удаляется.

## 12. Выделение изображения знака

Для каждой строки сохраняются две версии.

### Raw crop

Фрагмент исходного рендера без очистки. Используется как доказательство и для ручной проверки.

### Normalized crop

Версия для сравнения:

- перевод в grayscale;
- нормализация контраста;
- удаление пустого поля;
- центрирование;
- приведение к стандартному размеру;
- сохранение пропорций;
- мягкое подавление текста;
- опциональное подавление проходящей линии.

Нельзя сохранять только нормализованную версию: очистка может удалить значимую черту.

## 13. Поиск кандидатов на чертеже

### 13.1. Маски исключения

Перед поиском кандидатов нужно исключить или понизить приоритет:

- обычного текста;
- таблиц;
- штампа;
- рамки листа;
- размерных чисел;
- плотной штриховки;
- длинных непрерывных линий без локального символа.

### 13.2. Векторные кандидаты

Для CAD-PDF:

- небольшие группы paths;
- повторяющиеся группы с близким bbox;
- замкнутые контуры;
- окружности;
- локальные компоненты, пересекающие длинную линию;
- повторяющиеся сочетания линий и кривых.

### 13.3. Растровые кандидаты

Для сканов и полностраничного растра:

- connected components;
- контуры;
- окружности и эллипсы;
- локальные шаблоны легенды;
- повторяющиеся небольшие компоненты;
- стрелочные окончания.

### 13.4. Open-set кандидаты

Кроме поиска известных шаблонов нужен open-set режим:

```text
небольшой повторяющийся компонент
  + встречается в графической области
  + не является текстом
  → сохранить как неизвестный SymbolCandidate
```

Это обеспечивает перечень знаков, которых нет в легенде.

## 14. Группировка и дедупликация

Дедупликация выполняется в два уровня.

### Экземпляры

Один и тот же знак, найденный несколькими detectors или в перекрывающихся зонах, объединяется по:

- IoU bbox;
- расстоянию центров;
- visual signature;
- общему контексту.

### Визуальные типы

Разные экземпляры группируются по:

- perceptual hash;
- сходству контуров;
- соотношению сторон;
- числу и расположению замкнутых областей;
- локальным дескрипторам;
- векторной сигнатуре, если она доступна.

Совпадение соседних тайлов не считается независимым подтверждением.

## 15. Сопоставление с легендой

Сопоставление выполняется по совокупности признаков:

```text
score =
  visual similarity
  + position/number agreement
  + nearby text agreement
  + line context agreement
  + repeated-instance consistency
```

### Статусы результата

```text
confirmed
probable
conflicting
unresolved
rejected
```

`confirmed` разрешён только при наличии сильного источника:

- позиционного номера;
- однозначной подписи;
- высокоточного совпадения с легендой текущего листа без конкурирующей пары;
- решения человека.

Числовые пороги должны калиброваться на размеченных страницах, а не назначаться по самооценке VLM.

## 16. Контекст экземпляра

Для каждого экземпляра собирается локальный контекст:

- ближайшие подписи;
- позиционный номер;
- DN или диаметр;
- NO/NC;
- марка сети;
- объект, внутри или рядом с которым расположен знак;
- линия, которую знак пересекает;
- направление стрелки;
- смысловая зона листа.

Контекст не должен автоматически создавать инженерную связь. Он используется для классификации и сохраняется как отдельное наблюдение.

## 17. Каталог проекта

### Назначение

Каталог проекта ускоряет повторное распознавание и позволяет использовать уже проверенные обозначения на следующих листах.

### Правила

1. Новая запись создаётся из строки легенды или решения человека.
2. Каждый вариант хранит исходный документ, страницу и crop.
3. Визуально похожие записи с разными названиями не объединяются автоматически.
4. Одинаковое название с разными изображениями хранится как несколько variants.
5. Решение каталога не переписывает легенду текущего листа.
6. Все изменения каталога версионируются.

### Статусы

```text
auto_extracted
needs_review
human_confirmed
deprecated
conflicting
```

## 18. Ручная проверка

MVP должен поддерживать однократную проверку без повторного запуска VLM.

Проверяющий должен иметь возможность:

- подтвердить строку легенды;
- исправить название;
- объединить или разделить визуальные типы;
- назначить расшифровку;
- снять ошибочную расшифровку;
- пометить компонент как «не условный знак»;
- оставить знак нерасшифрованным;
- сохранить решение в `review_decisions.json`.

Решения человека имеют приоритет над автоматическими результатами.

## 19. Проекция в Markdown

JSON остаётся источником истины. В клиентский Markdown выводится краткое представление.

```text
## Условные обозначения

### Расшифровки из легенды
- Позиция 3 — затвор дисковый: найдено 4 экземпляра.
- Позиция 6 — кран шаровой: экземпляры не найдены.

### Нерасшифрованные знаки
- Тип S-007: найдено 3 экземпляра, координаты доступны.

### Конфликты
- Тип S-009 похож на позиции 3 и 6; требуется проверка.
```

Полный перечень экземпляров хранится в JSON и используется для overlay, поиска и аудита.

## 20. Интеграция с текущим кодом

Рекомендуется отдельный пакет:

```text
symbols/
  schema.py
  geometry.py
  legend_layout.py
  legend_rows.py
  crop_normalizer.py
  candidate_detector.py
  visual_signature.py
  cluster.py
  matcher.py
  catalog.py
  review.py
  markdown.py
```

### Точки подключения

1. После определения типа листа и render policy.
2. До финальной сборки клиентского Markdown.
3. Параллельно PASS-A/PASS-B, а не внутри текстовой конкатенации.
4. С сохранением bbox в координатах PDF.
5. Без изменения существующего формата `page_NNNN.md`.

### Зависимости

MVP можно начать на имеющихся `PyMuPDF` и `Pillow`:

- координаты текста;
- PDF paths;
- рендер clips;
- базовая обработка crop;
- perceptual signatures собственной реализацией.

Для устойчивых connected components, contour matching, ORB/SIFT и template matching на следующем шаге целесообразен `opencv-python-headless`. Зависимость добавляется только после отдельного прототипа, подтвердившего прирост качества.

## 21. Поэтапная реализация

### S0. Набор данных и разметка

Подготовить для ПБ, ОДИ, КР1/КР3 и одного hold-out:

- bbox легенд;
- строки легенд;
- crops знаков;
- 10–30 экземпляров ключевых классов;
- несколько заведомо нерасшифрованных знаков;
- отрицательные примеры: текст, пересечения линий, размерные засечки.

Результат:

```text
legend_ground_truth.json
symbol_instances_ground_truth.json
```

### S1. Legend Extractor MVP

Реализовать:

- ручной bbox легенды как тестовый harness;
- автоматический поиск заголовка;
- разделение строк;
- crop знака и OCR/VLM текста;
- `legend_entries.json`.

Page-specific координаты разрешены только в fixtures, не в production.

### S2. Известные шаблоны

Реализовать поиск экземпляров extracted templates:

- multi-scale matching;
- дедупликация bbox;
- сохранение unmatched entries;
- `symbol_instances.json`.

### S3. Open-set registry

Добавить:

- candidates по connected components/vector groups;
- исключение текста и таблиц;
- visual clustering;
- сохранение `unclassified` типов.

### S4. Context Resolver

Добавить:

- nearby labels;
- позиции;
- DN и NO/NC;
- связь с ближайшей линией как наблюдение;
- правила `confirmed/probable/conflicting`.

### S5. Project Catalog

Добавить:

- объединение проверенных LegendEntry по документам;
- variants;
- review decisions;
- использование каталога как вторичного источника кандидатов.

### S6. Клиентское представление

Добавить:

- краткий Markdown;
- координаты;
- overlay;
- фильтры classified/unclassified/conflicting;
- ручное подтверждение.

## 22. Контрольные листы

### ПБ

Главный лист для:

- позиций арматуры;
- похожих знаков;
- DN;
- NO/NC;
- знаков на трубопроводах;
- связи легенды с экземплярами.

### ОДИ

Главный лист для:

- линейных обозначений;
- цветовых вариантов;
- границ;
- знаков сетей;
- compass и других одиночных знаков;
- проверки, что текст экспликации не принят за символы.

### КР1/КР3

Главные листы для:

- кружков ИГЭ;
- повторяющихся номеров;
- связи кружка со слоем;
- отделения символов от штриховки.

### КР4

Hold-out для:

- выносок;
- марок деталей;
- знаков узлов;
- проверки переносимости за пределы первых трёх типов.

### КР5

Не входит в основной KPI условных знаков. Используется как отрицательный/regression-лист, чтобы ячейки таблицы и зачёркивания не создавали большой ложный каталог.

## 24. Критерии приёмки MVP

MVP принимается, если:

1. Каждая размеченная строка легенды либо извлечена, либо явно отмечена как пропущенная.
2. Для каждого LegendEntry сохранён raw crop.
3. Каждый найденный экземпляр имеет bbox и source.
4. Нерасшифрованные знаки не удаляются.
5. Один знак из перекрывающихся зон не создаёт несколько экземпляров.
6. Текст и ячейки таблиц не формируют основной объём symbol registry.
7. Подтверждённая классификация не строится только на ответе VLM.
8. Ошибочная привязка знака к расшифровке измеряется отдельно от пропуска.
9. Результат проходит hold-out без page-specific hints.
10. Текущий PASS-A/PASS-B и клиентский контракт не ухудшаются.

Числовые пороги precision/recall устанавливаются после S0, когда будет известна сложность и полнота разметки.

## 25. Основные риски

### Одинаковая форма, разные значения

Не объединять автоматически без подписи, позиции или решения человека.

### Знак пересекается с линией

Сохранять raw crop; нормализовать отдельной версией с line suppression.

### Легенда отсутствует

Формировать реестр типов и экземпляров со статусом `unclassified`.

### Легенда находится на другом листе

На первом цикле использовать только явно связанный лист или проверенный каталог проекта; автоматический Document Graph не строить.

### Растровый лист низкого качества

Использовать direct clip, PNG и несколько масштабов; сохранять `unresolved`, если деталей недостаточно.

### Каждое пересечение принимается за знак

Использовать маски, повторяемость, размерные ограничения и отрицательные fixtures.

### Каталог накапливает ошибку

Автоматические записи не получают статус `human_confirmed`; хранить source и историю решений.

## 26. Рекомендуемый первый инкремент

Первый инкремент ограничить двумя задачами:

1. извлечь строки легенды ПБ в `legend_entries.json` с raw crops;
2. найти на схеме экземпляры двух визуально различимых позиций и сохранить все unmatched/unclassified кандидаты.

На этом инкременте не требуется:

- распознавать всю арматуру;
- строить гидравлический граф;
- создавать общий ГОСТ-справочник;
- обрабатывать все документы;
- добавлять OpenCV до подтверждения недостаточности базовых средств.

Успех первого инкремента:

```text
строка легенды
  → сохранённый знак
  → один или несколько экземпляров на схеме
  → bbox и evidence crop
  → корректный статус совпадения
```

После подтверждения этого вертикального среза контур расширяется на кружки ИГЭ и линейные обозначения ОДИ.
