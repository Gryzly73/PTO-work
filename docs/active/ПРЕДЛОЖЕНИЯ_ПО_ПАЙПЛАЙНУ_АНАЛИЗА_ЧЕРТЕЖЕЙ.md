# Предложения по новому пайплайну анализа чертежей

**Статус:** самостоятельное предложение для планирования доработок  
**Область:** распознавание графического содержания отдельных листов-чертежей  
**Дата:** 24.08.2026  

## 1. Цель

Научить систему не только перечислять найденные на чертеже элементы, но и формировать проверяемое инженерное описание:

- что изображено;
- где расположен каждый существенный элемент;
- какая подпись относится к объекту или линии;
- как объекты соединены;
- куда направлен поток или трасса;
- какие выводы подтверждены;
- что не удалось прочитать или однозначно связать.

Целевой переход:

```text
изображение → длинный Markdown
```

в:

```text
изображение
  → качественный рендер
  → смысловые зоны
  → структурированные наблюдения
  → объединение фактов
  → объекты и связи
  → краткое проверяемое описание
```

Полный Scene Graph не является обязательным результатом первого цикла. Сначала нужно получить минимальную устойчивую структуру наблюдений и подтвердить улучшение на контрольных чертежах.

## 2. Граница изменений

Доработки относятся прежде всего к анализу каждого графического листа отдельно:

- планов;
- схем;
- геологических разрезов;
- строительных узлов;
- смешанных листов с существенной графической частью.

Общие функции приложения могут изменяться технически, но новое поведение должно включаться по типу листа.

```text
чертёж → зоны, объекты, обозначения, линии и связи
таблица → существующий табличный контур
текст → существующий текстовый слой/OCR
```

Текущий цикл не включает:

- межстраничный Document Graph;
- продолжение сетей между листами;
- общий паспорт комплекта;
- полнотекстовый OCR всего документа;
- улучшение табличного PASS-T;
- автоматическую проверку комплекта против ТЗ;
- общий классификатор условных обозначений по ГОСТ.

Текстовые и табличные страницы используются только как регрессионный контур: изменения анализа чертежей не должны ухудшить их текущую обработку.

## 3. Исходные ограничения

Текущий конвейер уже выполняет классификацию листа, PASS-A по целому изображению и PASS-B по тайлам и фиксированным зонам. Основные ограничения:

1. Полная страница сначала уменьшается, после чего из неё вырезаются зоны.
2. Тайлы не перекрываются.
3. Тонкие линии и короткие обозначения передаются преимущественно в JPEG.
4. Специального уменьшения запроса при HTTP 413 нет.
5. Зоны задаются фиксированными долями листа, а не его содержимым.
6. Результаты разных фрагментов объединяются как строки Markdown.
7. Объекты не имеют устойчивых идентификаторов и координатной модели.
8. При пригодном текстовом слое layer-aware может отключить PASS-B, хотя графика листа всё ещё требует локального анализа.
9. Recall/Key измеряют словарное совпадение, но не правильность инженерных связей.
10. Историческая сверка 74,0% Recall / 72,1% Key выполнена без lean и не является baseline актуального production-профиля.

## 4. Этап 0. Зафиксировать актуальный baseline

### Проблема клиента

Нельзя доказать, что новая версия действительно стала лучше: один удачный прогон может скрывать нестабильность, а высокий Recall может быть получен за счёт очень длинного и противоречивого вывода.

### Предложение

1. Повторить листы ПБ, ОДИ, КР1, КР3 и КР5 на актуальном `main`.
2. Использовать профиль `sheet-aware + lean + layer-aware` без page-specific hints.
3. Выполнить минимум четыре независимых прогона в разных каталогах.
4. Не использовать внутренний `--runs 4` для оценки устойчивости: он объединяет варианты, а не сохраняет четыре независимых результата.
5. Считать отдельно:
   - медиану;
   - худший результат;
   - полный сырой вывод;
   - PASS-A;
   - краткий клиентский результат.
6. Оставить КР5 регрессионной табличной проверкой, но исключить из основного KPI графического понимания.
7. Использовать КР4 как начальный smoke hold-out только при наличии исходного листа, а не одного `.ref.md`.
8. В дальнейшем расширить hold-out до нескольких неизвестных листов каждого целевого типа.

### Что получает клиент

Воспроизводимый отчёт: что улучшилось, что ухудшилось, насколько результат стабилен и не получен ли рост метрик за счёт увеличения объёма.

## 5. Этап 1. Улучшить рендер и локальные зоны

### Проблема клиента

Мелкие коды, подписи и тонкие линии теряются при уменьшении страницы, JPEG-сжатии или разрезании объекта границей тайла.

Типичные проявления:

- `1ш1` читается как `1m1`;
- `ИГЭ-1` превращается в `ПГ-1.1`;
- теряются `DN`, `NO`, `NC`;
- подпись и объект попадают в разные фрагменты;
- линия исчезает или обрывается на границе зоны.

### Предложение

Внедрять изменения отдельными измеримыми экспериментами:

1. Direct PDF clip rendering для локальных зон.
2. Перекрытие тайлов порядка 10–18%.
3. Native raster profile с учётом исходного разрешения встроенного изображения.
4. PNG или автоматический выбор формата для тонких линий и коротких обозначений.
5. Fine deskew только при достаточной уверенности.
6. Специальный shrink/split retry при HTTP 413.
7. Выделение 3–6 смысловых зон по содержимому листа.
8. Fallback на равномерную сетку при низкой уверенности layout.

Смысловые зоны нельзя определять только по плотности: редкие длинные линии, стрелки и выноски также должны сохраняться.

### Что получает клиент

Система стабильнее читает те обозначения, которые инженер видит при увеличении PDF, и реже теряет объекты на границах фрагментов.

## 6. Этап 2. Ввести структуру наблюдений

### Проблема клиента

Система может написать, что на листе есть ИГЭ, насос или сеть, но не может показать, где именно найден факт и к какому объекту относится подпись.

### Предложение

Ввести промежуточный формат, не заменяя клиентский Markdown:

```text
Observation
  observation_id
  page_id
  region_id
  coordinate_space
  type
  class
  label_raw
  label_normalized
  bbox
  source_kind
  source_ref
  geometry_confidence
  label_confidence
  alternatives
  evidence_crop
  run_id
  status
```

Допустимые статусы:

```text
confirmed
conflicting
unresolved
```

Источники наблюдений:

- целый лист;
- смысловая зона;
- локальный crop;
- текстовый слой;
- геометрия PDF;
- локальный reader коротких кодов;
- reader условных знаков;
- reader линий.

Все bbox должны храниться в единой системе координат PDF. Нужно явно учитывать поворот страницы и преобразования между PDF, растром и crop.

### Что получает клиент

Каждый существенный вывод можно проверить по конкретному месту на листе. Конфликтующие чтения не маскируются случайным выбором.

## 7. Этап 3. Закрыть критические ошибки контрольных чертежей

Для разных типов чертежей нужны отдельные readers и правила связей. Один универсальный промпт не должен одновременно разбирать насосную, генплан и геологический разрез.

### 7.1. КР3 — геологический разрез

Проблема: опасная подмена `ИГЭ → ПГ`, при которой сюжет листа выглядит правдоподобно, но инженерная номенклатура неверна.

Нужно связывать:

```text
номер кружка → обозначение ИГЭ → слой → разрез/ось → положение относительно фундамента
```

Неподтверждённая замена номенклатуры должна блокироваться и выводиться как конфликт.

### 7.2. ОДИ — генеральный план

Проблема: система перечисляет коды `1а`, `1б`, `1е`, `1ш1`, `1ш2`, но не связывает их с конкретными объектами.

Нужно связывать:

```text
код → контур/объект → название из экспликации → положение → ближайшая подтверждённая сеть
```

### 7.3. ПБ — насосная пожаротушения

Проблема: система находит резервуары, насосы, арматуру, DN и NO/NC, но часто выдаёт их как несвязанный список.

Нужно восстанавливать минимальную цепочку:

```text
резервуар → линия → арматура → насос → сеть В2
```

DN и NO/NC должны относиться к конкретному участку или экземпляру арматуры.

### 7.4. КР1

Проблема: уже хороший результат может ухудшиться из-за новых правил, а текущий вывод содержит шум и петли.

Задача:

- сохранить полноту и ключевые факты;
- убрать повторы и мусор;
- не допустить регрессии связей ИГЭ, скважин и разрезов.

### Что получает клиент

Исправляются ошибки, способные привести к неправильному инженерному выводу, а не только опечатки и форматирование.

## 8. Этап 4. Объединить целый лист и локальные зоны

### Проблема клиента

PASS-A понимает общий смысл, локальные зоны читают детали, но результаты не образуют единого описания.

Например:

```text
целый лист → «насосная пожаротушения»
локальная зона → «насос Н1, DN200, затвор NO»
```

Сейчас эти сведения могут остаться разными строками без подтверждённой связи.

### Предложение

Добавить детерминированный fusion:

1. Объединение объектов по координатам, классу и меткам.
2. Устранение дублей соседних тайлов.
3. Сохранение конфликтующих вариантов.
4. Привязка подписи по совокупности признаков:
   - расстояние;
   - направление выноски;
   - общая линия;
   - принадлежность смысловой зоне;
   - отсутствие более сильного кандидата.
5. Запрет на привязку только по принципу «ближайший bbox».
6. Формирование краткого кармана подтверждённых фактов.

### Что получает клиент

Один компактный инженерный результат вместо общего описания и десятков несвязанных фрагментов. Полный PASS-B остаётся доступен как диагностический источник.

## 9. Этап 5. Легенда и условные обозначения

### Проблема клиента

Система может переписать легенду, но не умеет показать, где её знаки встречаются на основной части чертежа.

### Предложение

Начинать только с проверяемых классов:

- кружки ИГЭ;
- позиции арматуры;
- марки оборудования;
- марки сетей;
- стрелки направления;
- простые знаки колодцев и камер.

Формат результата:

```text
legend entry → instances[]
unmatched entries[]
unclassified instances[]
confusion pairs[]
```

Словарь строится только по текущему листу. Нельзя подставлять ГОСТ-название или класс из памяти модели, если он не подтверждён листом или предоставленным справочником.

### Что получает клиент

Не просто список легенды, а проверяемые соответствия: какой знак, сколько раз и где найден; что осталось неопознанным.

## 10. Этап 6. Линии и инженерные связи

### Проблема клиента

Наличие всех объектов не отвечает на главные вопросы: откуда приходит среда, через что проходит и куда уходит.

### Предложение

После стабилизации объектов добавить:

1. Векторные пути PDF.
2. CV-трассировку растра.
3. Классификацию junction/crossing.
4. Stitching линий между зонами.
5. Определение направления по стрелкам.
6. Привязку линии к объектам, арматуре и марке сети.

Необходимо различать:

- реальное соединение;
- пересечение без соединения;
- разрыв под подписью;
- стрелку;
- продолжение за границу зоны;
- арматуру внутри линии.

Первый целевой граф ограничивается насосной ПБ:

```text
резервуар → линия → арматура → насос → сеть В2
```

После его стабилизации можно переходить к генпланам и геологическим разрезам.

### Что получает клиент

Система отвечает не только «что есть на листе», но и «как связано», «откуда приходит» и «куда направлено».

## 11. Формат результата для клиента

Структурированная модель является внутренним источником истины. Клиентский Markdown остаётся основным читаемым представлением.

Рекомендуемые блоки:

```text
Что изображено
Найденные элементы
Подтверждённые связи
Не разобрано / конфликты
```

Пример ожидаемого результата:

```text
Что изображено
Схема насосной пожаротушения.

Найденные элементы
- два резервуара;
- основные насосы Н1 и Н2;
- сеть В2;
- затворы NO/NC.

Подтверждённые связи
- резервуары соединены со всасывающей линией насосов;
- после насосов поток направлен в сеть В2;
- на участке DN200 подтверждён затвор NO.

Не разобрано / конфликты
- позиция одного затвора читается неоднозначно;
- марка одной линии распознана как В2/B2.
```

## 12. Метрики и критерии продвижения

Recall/Key сохраняются как регрессионные показатели совместимости с `SVERKA_S_IDEAL.md`, но не являются единственным доказательством понимания чертежа.

Для каждого этапа нужно измерять:

- Recall и Key для полного и краткого результата;
- object precision/recall;
- правильность object ↔ label;
- false binding rate;
- relation precision/recall;
- unsupported relation rate;
- число критических подмен номенклатуры;
- ответы на 3–5 инженерных вопросов по листу;
- объём результата;
- chars per confirmed fact;
- дубли и петли;
- число API-ошибок;
- стоимость и время.

Этап принимается только если:

1. Улучшает медиану целевых метрик на актуальной сверке.
2. Не ухудшает худший из четырёх независимых прогонов сверх заранее установленного допуска.
3. Не увеличивает число неподтверждённых фактов и связей.
4. Не раздувает результат непропорционально приросту подтверждённых фактов.
5. Проходит hold-out.
6. Не использует подсказки по номеру известной страницы.
7. Не ухудшает КР1.
8. Не ухудшает существующие текстовый и табличный контуры.

До начала реализации необходимо зафиксировать числовые пороги для relation recall/precision, false binding rate, стоимости и времени.

## 13. Приоритеты первого цикла

1. Получить воспроизводимый baseline актуального production-профиля.
2. Устранить подмену `ИГЭ → ПГ`.
3. Повысить точность связи кодов ОДИ с объектами.
4. Восстановить основную цепочку потока ПБ.
5. Сократить клиентский результат относительно сырых ×5–×11.
6. Сохранить качество КР1.
7. Подтвердить результат на неизвестных чертежах.

## 14. Рекомендуемая последовательность реализации

```text
baseline и regression lock
  → render policy отдельными экспериментами
  → единая система координат
  → Observation schema
  → специализированные readers КР3 / ОДИ / ПБ
  → fusion и карман подтверждённых фактов
  → легенда и экземпляры
  → линии и ограниченный граф ПБ
  → расширение hold-out
```

Auto PASS-T, табличный passport, обычный OCR и межстраничный Document Graph в этот цикл не включаются, поскольку не дают прямого улучшения основного KPI распознавания чертежей.
