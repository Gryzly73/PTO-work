# Методика DWG Symbol Harness

Статус: рабочий норматив разработки.  
Область: комплекты `new_files/dwg`, включая подпапки и внешние ссылки.

## 1. Цель

Первая задача проекта — получить проверяемый каталог условных обозначений на
чертеже и их взаимосвязей:

1. извлечь элементы легенды;
2. найти экземпляры обозначений на листе;
3. связать экземпляры с легендой;
4. отдельно сохранить знаки, которых нет в легенде;
5. построить наблюдаемые геометрические и подтверждённые смысловые связи.

До появления нормативного справочника система не классифицирует неизвестные
обозначения по памяти модели. Неизвестный знак является нормальным результатом,
а ошибочно подтверждённый знак — дефектом.

## 2. Основные принципы

### 2.1. Комплект, а не отдельный файл

DWG анализируется вместе с XREF, шрифтами и изображениями. Неразрешённая внешняя
ссылка делает анализ `partial` или `blocked`; такой лист запрещено выдавать за
полный.

### 2.2. Fail-closed

Статус `confirmed` требует воспроизводимого доказательства. При недостатке
данных используются `probable`, `conflicting`, `unresolved` или `unclassified`.

### 2.3. Данные первичны, VLM вторична

Приоритет источников:

1. DWG INSERT, ATTRIB, layer, handle и векторная геометрия;
2. повторяющаяся взорванная геометрия;
3. растровое совпадение;
4. ближайшие подписи и пространственный контекст;
5. VLM-review только для уже выделенного неоднозначного случая.

### 2.4. Два вида пропусков

Нельзя объединять:

- экземпляр есть на листе, но отсутствует в легенде;
- пункт есть в легенде, но экземпляров на листе нет.

### 2.5. Связь должна иметь доказательство

`geometric_relation` фиксирует наблюдаемое соединение линией, выноской или
принадлежностью блоку. `semantic_relation` допустима только поверх наблюдаемой
связи и подтверждающей подписи либо явного направления.

## 3. Публичные sidecar-артефакты

Для каждого листа каталог `dwg_symbols/page_NNNN/` содержит:

- `legend_entries.json`;
- `symbol_instances.json`;
- `symbol_bindings.json`;
- `unrecognized_symbols.json`;
- `relationships.json`;
- `summary.json`.

Файлы создаются всегда. Нереализованная стадия представлена пустым `items`, а не
отсутствующим файлом. Это отличает «результатов нет» от «стадия не запускалась».

### 3.1. LegendEntry

Обязательные понятия: стабильный ID, лист, подпись, статус, источник,
координаты, сигнатура и уверенность.

### 3.2. SymbolInstance

Для DWG-базовой линии сохраняются:

- `sourceHandle`;
- `sourceSpace`;
- `blockName`;
- `layer`;
- координата на листе или в модели;
- ATTRIB;
- сигнатура определения блока;
- статус распознавания.

### 3.3. SymbolBinding

Привязка содержит экземпляр, пункт легенды, статус, confidence и массив
доказательств. Привязка без доказательств невалидна.

### 3.4. UnknownSymbolCluster

Нераспознанные экземпляры группируются по сигнатуре. В список попадает один
кластер с числом повторений и representative instance, а не сотни одинаковых
строк.

### 3.5. Relationship

Ребро содержит два стабильных ID, тип, направленность, статус и доказательства.

## 4. Этап H0 — аудит `new_files/dwg`

Текущий shallow-аудит обнаруживает 94 DWG-файла в семи верхнеуровневых
разделах. Это реестр входа, а не готовый test set: split и human-verified
разметка создаются отдельно.

Shallow-аудит не конвертирует файлы:

```powershell
python -m dwg_symbols audit new_files/dwg --out local_runs/dwg_audit.json
```

Deep-аудит конвертирует DWG и проверяет:

- `$INSUNITS`;
- layouts;
- типы сущностей;
- число INSERT;
- определения блоков;
- XREF и кандидатов разрешения;
- ошибки чтения.

### Docker на Windows

Воспроизводимый путь не зависит от локальной установки LibreDWG:

```powershell
.\scripts\dwg-harness-docker.ps1 build
.\scripts\dwg-harness-docker.ps1 verify
.\scripts\dwg-harness-docker.ps1 audit
```

Скрипт сначала собирает LibreDWG 0.14 из `Dockerfile.dwgtools`, затем backend с
локальным образом конвертера. Готовый GHCR-образ может требовать авторизацию,
поэтому локальная сборка является штатным fallback.

Результат записывается в `local_runs/dwg_audit.deep.json`. Каталог исключён из
Git и передаётся контейнеру через bind mount вместе с `new_files/dwg`.

```powershell
python -m dwg_symbols audit new_files/dwg --deep `
  --out local_runs/dwg_audit.deep.json
```

Коды `UNITS_UNSPECIFIED`, `XREF_UNRESOLVED`, `XREF_AMBIGUOUS` и
`DOCUMENT_READ_FAILED` являются блокерами для утверждения полноты.

## 5. Этап H1 — ground truth и scorer

Ground truth хранится отдельно от клиентских DWG. В репозиторий входит только
пример `dwg_symbols/fixtures/manifest.example.json`.

Разбиение выполняется по комплектам:

- `development` — разрешено использовать при разработке;
- `validation` — проверка порогов;
- `holdout` — итоговая оценка, без подстройки алгоритма.

Листы одного комплекта и одинаковые определения блоков нельзя распределять по
разным split: это создаёт утечку.

Ключ базового DWG-экземпляра:

```text
<sourceSpace>|<sourceHandle>
```

Пример: `modelspace|2AF`.

Проверка manifest:

```powershell
python -m dwg_symbols validate-gt path/to/MANIFEST.local.json
```

Оценка:

```powershell
python -m dwg_symbols score path/to/MANIFEST.local.json local_predictions
```

Scorer считает precision, recall и F1 отдельно для:

- экземпляров;
- привязок;
- нераспознанных экземпляров;
- связей.

Также отдельно считается `falseConfirmedBindings`.

## 6. Этап H2 — block baseline

Первый вертикальный срез извлекает видимые верхнеуровневые INSERT из modelspace
и layout. Для modelspace координата преобразуется через viewport в координаты
бумаги.

```powershell
python -m dwg_symbols extract-blocks drawing.dwg --page 1 `
  --out local_predictions/example-plan-sheet-1
```

На H2:

- INSERT является кандидатом, а не автоматически символом;
- XREF-вставки пропускаются и отражаются anomaly code;
- все кандидаты имеют `unresolved`;
- одинаковые определения блоков образуют unknown-кластеры;
- легенда, привязки и связи пока пусты.

Это намеренное ограничение. H2 проверяет координаты, идентичность и полноту
инвентаризации до добавления классификации.

## 7. Декомпозиция следующих стадий

### H3. Легенда

Локализация области, строки «значок + текст», точный текст, crop и векторная
сигнатура. Легенда сначала извлекается как самостоятельный каталог.

Текущая детерминированная реализация:

```powershell
python -m dwg_symbols extract-legends drawing.dwg --page 1 `
  --out local_predictions/example-plan-sheet-1
```

Команда сохраняет результат H2 и дополнительно:

- находит заголовки «Условные обозначения»/«Легенда» в текстовом слое DWG;
- выделяет устойчивые колонки подписей ниже заголовка;
- объединяет близкие строки в многострочный пункт;
- выделяет слева от подписи ячейку графического образца;
- клипирует реальные сегменты по границе ячейки, исключая охватывающие лист
  рамки и другие примитивы, чей bounding box только формально пересекает ячейку;
- строит нормализованную `legend-vector-v1`-сигнатуру без зависимости от
  handles и абсолютных координат;
- сохраняет SVG-crop в `legend_crops/` и ссылку на него в `LegendEntry`.

H3 не связывает найденные пункты с экземплярами на чертеже — это задача H4.
Пункт без векторного образца остаётся `unmatched`, а лист получает
`LEGEND_ENTRIES_WITHOUT_VECTOR_SIGNATURE`. Отсутствие заголовка фиксируется как
`LEGEND_NOT_FOUND`, а не интерпретируется как отсутствие легенды.

Проверка на трёх development-листах из `MANIFEST.local.json`:

- `kr1-geology-p1` — 23 пункта многоколонной геологической легенды;
- `tx-plans-p1` — 5 пунктов условных обозначений стен и перегородок;
- `kr1-plans-p1` — 5 пунктов условных обозначений стен и перегородок.

Для обоих планов сигнатура и SVG-crop созданы для всех пяти пунктов; на
геологическом листе один из 23 пунктов после точного клипирования не имеет
самостоятельного векторного сегмента и остаётся `unmatched`. Это результат
автоматического извлечения, а не ground truth: окончательные recall/precision
появятся только после ручной разметки manifest. При проверке отдельно исключены
колонки штампа, которые пространственно находятся рядом с легендой.

### H4. Resolver

Сопоставление по block definition, нормализованной геометрии, изображению,
ATTRIB и контексту. Глобальный NMS между разными типами запрещён.

Первый реализованный канал H4 — точное совпадение block definition:

```powershell
python -m dwg_symbols resolve-exact drawing.dwg --page 1 `
  --out local_predictions/example-plan-sheet-1
```

Алгоритм:

1. находит `INSERT`, точка вставки которого попала в `symbolBbox` пункта
   легенды;
2. сохраняет его `blockdef-v1` в `referenceSignatures`;
3. помечает сам образец как `role=legend_exemplar`, `status=reference`;
4. подтверждает полевые `INSERT` только при отношении
   «одна сигнатура → один пункт легенды»;
5. создаёт `SymbolBinding` с доказательством `exact_block_definition`;
6. заново строит unknown-кластеры только из неподтверждённых полевых
   экземпляров.

Одна сигнатура в нескольких пунктах, составная ячейка из нескольких block
definitions и пересечение областей легенды не дают автоматический `confirmed`.
Они фиксируются anomaly codes. Канал не пытается сопоставить взорванные линии и
штриховки и поэтому всегда добавляет `H4_EXACT_BLOCK_RESOLVER_ONLY`.

Результат на development-листах:

- `kr1-geology-p1`: 11 block-образцов легенды и 70 точных bindings;
- `tx-plans-p1`: 1 block-образец и 4 точных bindings;
- `kr1-plans-p1`: 1 block-образец и 4 точных bindings.

На геологическом листе остаётся `H4_LEGEND_EXEMPLAR_OVERLAP`: неоднозначные
образцы исключаются из доказательств, но требуют ручной проверки границ строк
H3.

Второй канал H4 сопоставляет взорванные линейные обозначения:

```powershell
python -m dwg_symbols resolve-geometry drawing.dwg --page 1 `
  --out local_predictions/example-plan-sheet-1
```

Поддерживаемый класс H4b — замкнутый четырёхугольный профиль линейного элемента.
Дескриптор инвариантен к повороту и длине и содержит:

- прямоугольную топологию;
- цвет;
- lineweight;
- наблюдаемую ширину на бумаге.

Одинаковые цвет и lineweight при единственном соответствующем пункте легенды
дают только `probable`, а не `confirmed`: ширина может изменяться между
viewport. В evidence сохраняются `linear-style-v1`, отношение ширины к образцу
легенды и длина найденного участка. Совпадение одного style с несколькими
пунктами легенды блокирует привязку.

Результат H4a + H4b:

- `kr1-geology-p1`: 70 `confirmed`, геометрических matches нет;
- `tx-plans-p1`: 4 `confirmed` и 8 `probable`;
- `kr1-plans-p1`: 4 `confirmed` и 8 `probable`.

На планах H4b нашёл по четыре участка двух типов перегородок. Два других
взорванных типа пока не имеют полевых замкнутых профилей с тем же style.
Числа bindings являются baseline, а не подтверждёнными метриками до заполнения
ground truth.

Третий канал H4 добавляет контекст слоя только для оставшихся пунктов:

```powershell
python -m dwg_symbols resolve-context drawing.dwg --page 1 `
  --out local_predictions/example-plan-sheet-1
```

H4c нормализует русские словоформы в подписи легенды и имени слоя, удаляет
общие слова (`стена`, `перегородка`, `панель`, `ГОСТ`) и требует уникального
пересечения значимого термина. Геометрия при этом всё равно должна быть
поддерживаемым замкнутым профилем. При одинаковом score у двух пунктов binding
не создаётся и фиксируется `H4_LAYER_CONTEXT_AMBIGUOUS`.

На обоих планах слой `БЛОКИ` однозначно сопоставился с пунктом «блоков
ячеистого бетона»:

- добавлено по 4 `probable` с evidence `layer_label_context`;
- итог каждого плана: 4 `confirmed` и 12 `probable`;
- геологический лист не получил контекстных совпадений;
- сэндвич-панели остаются нерешёнными: их полевые элементы находятся на общем
  слое наружных стен, что недостаточно для fail-closed привязки.

### H4d. Объединённая легенда DWG-файла

Локальная легенда листа остаётся главным источником. Дополнительно все листы
одного DWG можно обработать одной командой:

```powershell
python -m dwg_symbols review-file drawing.dwg `
  --id drawing-1 --out local_runs/file_review
```

Команда запускает H2-H4c для каждого layout и создаёт:

- листовые sidecars в `dwg_symbols/page_NNNN/`;
- `file_legend_catalog.json` с уникальными пунктами и provenance;
- `FILE_LEGEND_REPORT.md` с составом легенды и конфликтами;
- список межлистовых `probable`-кандидатов.

Пункты объединяются по нормализованной подписи, но исходное написание, номера
листов, crops и все сигнатуры сохраняются. Одна block-signature с разными
подписями является конфликтом и не используется. Уникальное точное совпадение
на другом листе остаётся рекомендацией: листовые bindings автоматически не
изменяются до ручной проверки и ground truth.

### H4e. Иерархическая легенда проекта

Все DWG/DXF комплекта объединяются с сохранением приоритета источников:

```text
лист → файл → раздел → проект → внешний стандарт
```

```powershell
python -m dwg_symbols review-project new_files/dwg `
  --out local_runs/project_legend
```

Проход является возобновляемым. Сначала для каждого файла проверяются тексты
всех листов; полный H2-H4c запускается только на листах с явным заголовком
легенды. Для каждого документа сохраняется `document_scan.json`, поэтому
повторный запуск продолжает незавершённый комплект. Размер и mtime исходного
файла входят в fingerprint: изменившийся DWG автоматически пересчитывается.
`--rebuild` принудительно пересчитывает всё.

Итог:

- `project_legend_catalog.json` — машиночитаемый проектный каталог;
- `PROJECT_LEGEND_REPORT.md` — состав по разделам, источники и конфликты;
- `documents/<file-id>/` — provenance и sidecars исходных листов.

Одинаковые подписи могут содержать несколько графических вариантов. Одна
блочная, геометрическая или векторная сигнатура, связанная с разными
подписями, получает `conflicting` и блокируется. Источники из каталогов
`Внешние ссылки` сохраняются с отдельным признаком, чтобы XREF-копия не
выдавалась за независимое подтверждение; пункт без основного файла получает
`external_only`. Без human annotation проектный каталог является источником
`probable`, а не ground truth.

Применение каталога ко всем листам выполняется отдельно:

```powershell
python -m dwg_symbols apply-project-legend new_files/dwg `
  local_runs/project_legend/project_legend_catalog.json `
  --out local_runs/project_application
```

Локальные H4 bindings имеют приоритет. Проектный resolver рассматривает только
оставшиеся unresolved `INSERT`, требует одну непротиворечивую block-signature
с независимым источником и всегда создаёт `probable` с evidence
`project_exact_block_definition`. Он не использует пункты `external_only` и не
обходит конфликты локальной легенды. Результаты записываются по каждому листу,
а общий итог — в `project_application_summary.json` и
`PROJECT_APPLICATION_REPORT.md`.

### H5. Неизвестные

Кластеризация неподтверждённых экземпляров, representative crops и очередь
ручной разметки. Позднее этот контракт подключается к ГОСТ-справочнику без
изменения основного pipeline.

### H6. Взорванные и линейные обозначения

Отдельные детекторы:

- повторяющиеся локальные подграфы;
- текстовые/SHX-глифы;
- линейные обозначения;
- штриховки и площадные зоны;
- OLE/IMAGE fallback.

### H7. Граф связей

Сначала наблюдаемые соединения, затем смысловые:

```text
источник → линия/сеть → арматура → оборудование → потребитель
```

### H8. Подробное описание

Описание строится из каталога объектов и графа, а VLM используется для
формулирования и review. Прямой пересказ изображения не является источником
ведомости.

## 8. Методика разметки

Начальный gold-набор: 8–12 листов, включая:

- ПЗ;
- ПЗУ;
- комплект с XREF;
- блочные обозначения;
- взорванные обозначения;
- линейные и площадные обозначения;
- лист без легенды;
- лист с неполной легендой.

Каждый лист размечают дважды: первичная разметка и независимая проверка.
Автоматически созданный baseline не получает статус `gold`.

## 9. Quality gates

До калибровки на реальном baseline используются начальные пороги:

- instance recall не ниже 0.90 на поддерживаемом классе;
- binding precision не ниже 0.95;
- `falseConfirmedBindings = 0`;
- отсутствие молчаливого truncation;
- отсутствие статуса `complete` при неизвестных единицах или XREF-пропусках.

Пороги меняются только вместе с зафиксированным объяснением и baseline diff.

## 10. Definition of Done первого milestone

Для 3–5 выбранных листов:

1. комплект проаудирован;
2. XREF и единицы имеют явный статус;
3. видимые INSERT имеют стабильные ID и координаты;
4. одинаковые блоки объединены в кластеры;
5. неизвестные сохранены отдельно;
6. scorer воспроизводимо сравнивает прогон с human-verified ground truth;
7. ни один кандидат не получает выдуманного названия.

Следующий milestone начинается только после ручной проверки block baseline.
