# Методика распознавания и расшифровки условных обозначений

**Статус документа:** описание фактически реализованного конвейера на 2026-08-25  
**Основной пакет:** `symbols/`  
**Интеграция:** opt-in через `PTO_SYMBOLS`

## 1. Назначение

Конвейер предназначен для:

1. поиска легенды на листе PDF;
2. извлечения строк «графический знак — текстовая расшифровка»;
3. поиска экземпляров знаков на поле чертежа;
4. группировки повторяющихся неизвестных обозначений;
5. сопоставления найденных типов со строками легенды;
6. сохранения подтверждённых, вероятных, конфликтных и нерасшифрованных
   результатов без потери координат и исходных изображений.

Главный принцип — **fail-closed**: недостаток доказательств приводит к
`probable`, `conflicting`, `unresolved` или остановке этапа, но не к
необоснованному `confirmed`.

Конвейер не выводит инженерные связи и не считает визуальное сходство само по
себе достаточным доказательством значения символа.

В проекте существуют два независимых контура:

- основной PDF → Markdown (`hf_api_bench.py`, `service/pipeline.py`) описывает
  лист, извлекает текст и таблицы;
- opt-in пакет `symbols/` создаёт проверяемый каталог легенды и экземпляров.

Успех или ошибка symbols-контура не меняет готовое Markdown-описание листа.
Scene graph, межлистовые инженерные связи, ГОСТ-классификатор и сверка с ТЗ в
текущую реализацию не входят.

## 2. Общая схема

```text
Страница PDF
  → детерминированный поиск легенды
      → при неудаче: ограниченная H5 VLM-помощь
  → геометрическая проверка области и строк легенды
  → создание проверенных шаблонов из строк легенды
  → поиск известных экземпляров шаблонов
  → фильтрация независимых open-set кандидатов
  → нормализация crops и визуальные подписи
  → кластеризация повторяющихся неизвестных форм
  → document-local matcher
  → консервативный resolver
      → при неоднозначности: ограниченная H6 VLM-проверка
  → page sidecars, Markdown, API и каталог документа
```

Основная точка входа — `symbols.pipeline.run_page_symbols()`. Этапы выполняются
последовательно для одной страницы. Ошибка symbols-конвейера изолирована от
основного VLM-описания листа в `service.worker`.

## 3. Координаты и артефакты

Все геометрические результаты хранятся в PDF points, а не в пикселях
конкретного рендера. Для каждого объекта сохраняются:

- стабильный ID;
- номер страницы;
- `bboxPdf`;
- исходный `rawCrop`;
- при наличии — `normalizedCrop`;
- источник обнаружения;
- confidence и evidence;
- статус обработки.

Страничные результаты находятся в:

```text
<run>/symbols/page_NNNN/
  legend_entries.json
  symbol_candidates.json
  symbol_types.json
  symbol_instances.json
  unclassified_symbols.json
  unmatched_legend_entries.json
  conflicts.json
  summary.json
  symbol_crops/
```

После обработки документа создаётся
`symbols/document_symbol_catalog.json`. Клиентская проекция формируется в
JSON и Markdown, но полные экземпляры и координаты остаются в sidecars.

## 4. Поиск и чтение легенды

### 4.1. Детерминированный поиск

`symbols.legend_layout` ищет компактную область легенды по совокупности
геометрических признаков:

- заголовок и рамка;
- регулярность строк;
- сочетание графики и текста;
- компактность и доля площади страницы;
- свободное пространство вокруг;
- исключение штампа, основной таблицы и большого массива чертежа.

Наличие одного заголовка или одной рамки не является достаточным. Область
должна пройти confidence- и geometry-gates.

`symbols.legend_rows` разделяет область на строки и проверяет:

- порядок строк сверху вниз;
- высоту и ширину строки;
- наличие зоны символа и зоны текста;
- отсутствие аномальных пересечений;
- информативность строки.

Строка получает один из статусов:

- `extracted` — символ и текст извлечены;
- `text_unreadable` — геометрия строки найдена, текст не прочитан;
- `unmatched` — текст легенды есть, но экземпляры на листе не найдены.

### 4.2. H5: VLM-помощь для легенды

H5 включается отдельно через `PTO_SYMBOLS_VLM=1` и вызывается только если
детерминированная легенда не найдена либо явно неполна.

VLM выполняет две ограниченные операции:

1. возвращает нормализованный bbox предполагаемой легенды;
2. возвращает строки с bbox символа, bbox текста, названием и confidence.

Ответ допускается только как строгий JSON. После VLM применяются проверки
координат, площади, порядка строк, количества строк и confidence. Невалидный
ответ отклоняется, а страница получает детерминированный fail-closed результат.

По умолчанию допускается не более двух вызовов на страницу, не более двух
областей и 80 строк. Минимальный confidence области — `0.70`, строки — `0.55`.

H5:

- не ищет экземпляры символов;
- не создаёт `confirmed`;
- не меняет основной Markdown листа при ошибке;
- ограничен по числу вызовов и строк;
- сохраняет `vlm_legend_trace.json`.

## 5. Шаблоны известных обозначений

Для каждой пригодной строки легенды `symbols.template_matcher` формирует
шаблон из зоны символа. До поиска проверяются:

- размер и aspect ratio;
- площадь чернил;
- контраст;
- информативность;
- отсутствие почти пустого или почти полностью залитого crop;
- согласованность компонента с границами строки.

Поиск выполняется в нескольких масштабах. Перекрывающиеся detections
дедуплицируются детерминированным NMS.

Текущие параметры: масштабы `0.75`, `1.0`, `1.25`; scale tolerance `0.22`;
порог итогового score `0.78`; dedupe IoU `0.5`.

Прямое совпадение с шаблоном текущей легенды создаёт только `probable`.
Оно не становится `confirmed`, пока resolver не найдёт независимое
документное доказательство.

## 6. Open-set кандидаты

Open-set нужен для обозначений, которые:

- не совпали с известным шаблоном;
- повторяются на листе;
- должны сохраниться как нерасшифрованный тип.

`symbols.candidate_detector` собирает raster connected components и vector
paths, после чего **до создания PNG** исключает:

- текст и прилегающую к нему геометрию;
- длинные линейные сети;
- штриховку;
- размерные засечки;
- одиночные примитивы;
- объекты вне допустимого размера и aspect ratio;
- слишком пустые или сплошные области;
- пересечения с уже найденными известными экземплярами.

Близкие примитивы сначала объединяются в локальный объект. После фильтрации
выполняются пространственная дедупликация, проверка бюджетов и только затем
создаются crops.

Актуальные основные параметры:

- размер кандидата: `6–45` PDF points;
- минимальный aspect ratio: `0.18`;
- dedupe IoU: `0.5`;
- порог сходства подписей: `0.9`;
- минимальный повтор для open-set типа: `2`.

## 7. Нормализация, подписи и кластеризация

Нормализованный crop кодируется подписью
`shape-topology-grid`, версия `2`. Подпись включает:

- бинарную карту чернил `24×24`;
- карту контурной топологии `24×24`;
- coarse fill по сетке `8×8`.

Сходство — нормализованное Hamming similarity совместимых подписей.

Одинаковые и близкие подписи объединяются в типы. Production-default —
эталонный `brute_force`; BK-tree остаётся экспериментальным. На сохранённом
stress-наборе он эквивалентен по разбиению, но устойчивое ускорение около
`4×` не достигает принятого release-gate `5×`, поэтому не включён по
умолчанию.

Кластеризация не присваивает значение из легенды. Она только сообщает, что
несколько crops, вероятно, представляют один визуальный тип.

## 8. Контекст и сопоставление с легендой

`symbols.matcher` сравнивает тип с каждой допустимой строкой легенды. Итоговый
score складывается из:

- визуального сходства — вес `0.80`;
- позиционного совпадения — `0.08`;
- подписи рядом — `0.08`;
- маркеров `DN`, `NO`, `NC` — `0.04`;
- связи с линией — `0.00`.

Линии сохраняются для аудита, но не являются классификационным доказательством.
Одиночные цифры и слишком короткие generic labels не усиливают решение.
Минимальное визуальное сходство для рассмотрения пары — `0.55`.

Контекст извлекается из текстового слоя страницы и индексируется
пространственно. На image-only скане такого evidence может не быть; тогда даже
сильное визуальное совпадение обычно остаётся `probable`.

## 9. Resolver и статусы доверия

`symbols.resolver` применяет следующие пороги:

- `probable_score = 0.62`;
- `confirmed_score = 0.75`;
- минимальное визуальное сходство для `confirmed = 0.88`;
- минимальное независимое semantic evidence = `0.50`;
- conflict margin = `0.06`.

Независимыми доказательствами считаются:

- `document_position`;
- `document_nearby_label`;
- `document_marker`.

### `confirmed`

Соответствие считается подтверждённым только при одновременном выполнении:

1. общий score не ниже `0.75`;
2. visual similarity не ниже `0.88`;
3. присутствует независимое evidence не ниже `0.50`;
4. нет близкого конкурирующего варианта.

Шаблон, линия или ответ VLM по отдельности не могут создать `confirmed`.

### `probable`

Есть лучший вариант легенды со score не ниже `0.62`, но не выполнены все
условия `confirmed`. Это гипотеза для review, а не достоверная расшифровка.
Количество `probable` нельзя выдавать как подтверждённую ведомость.

### `conflicting`

Несколько строк легенды имеют близкое визуальное/контекстное evidence:
разница score не превышает `0.06`. Автоматическая привязка снимается, варианты
сохраняются в `conflicts.json`.

### `unresolved`

Варианты существуют, но лучший score ниже порога `probable` либо evidence
недостаточно.

### `unclassified`

Повторяющийся визуальный тип найден, но подходящих строк легенды нет.

### `rejected`

Объект отклонён проверками качества или решением review.

Markdown показывает только `confirmed` как «расшифровано». `probable`,
`conflicting`, `unresolved` и `unclassified` остаются в разделе
нерасшифрованных.

## 10. H6: VLM-проверка неоднозначных типов

H6 включается отдельно через `PTO_SYMBOLS_VLM_REVIEW=1` после
детерминированного resolver.

Для review выбираются только:

- `conflicting`, `unresolved` и `unclassified` типы;
- типы минимум с двумя экземплярами;
- типы с уже вычисленным ограниченным списком строк-кандидатов;
- не более пяти типов на страницу по умолчанию.

VLM получает representative crop типа и crops только предложенных строк
легенды. Допустимый ответ — существующий ID строки либо `unresolved`.
Свободное название или неизвестный ID отклоняется.

H6:

- не рассматривает все `probable`;
- не создаёт новых строк легенды;
- может поднять статус максимум до `probable`;
- никогда не создаёт `confirmed`;
- кэширует ответ по модели, prompt и входным crops;
- сохраняет `vlm_review_trace.json`.

Таким образом, H6 — ограниченный арбитр между уже существующими вариантами,
а не самостоятельный распознаватель.

## 11. Каталог документа и ручные решения

`symbols.catalog` включает в подтверждённые записи каталога только bindings со
статусом `confirmed`. Остальные типы сохраняются в разделе unresolved, поэтому
каталог не повышает доверие автоматически и не является внешней библиотекой
символов.

`symbols.review` поддерживает append-only `review_decisions.json`. Решением
человека можно подтвердить или снять mapping, объединить или разделить типы,
пометить объект как несимвольный либо оставить его неразрешённым. Проекция
решений детерминирована; исходные page sidecars не переписываются.

## 12. Страничные статусы и fail-closed бюджеты

Страница symbols-конвейера получает:

- `complete` — все разрешённые этапы завершены;
- `no_valid_legend` — нет валидной области, строк или шаблонов;
- `partial` — часть результата сохранена, дальнейший этап остановлен бюджетом;
- `failed` — зарезервированный терминальный статус ошибки;
- `not_run` — symbols-анализ не запускался.

Текущие жёсткие бюджеты:

- строк легенды: `200`;
- компонентов шаблонов: `5 000`;
- template detections: `2 000`;
- компонентов кандидатов: `10 000`;
- кандидатов: `2 000`;
- crop-файлов: `4 000`;
- экземпляров: `2 000`.

Превышение бюджета не приводит к молчаливому усечению. Нормальный
`run_page_symbols()` сохраняет последний корректный этап, выставляет `partial`
и записывает anomaly code. Диагностический `run_profiled_page()` предназначен
для измерений и может пробросить `BudgetExceeded` вызывающему коду.

## 13. Интеграция и режимы

Флаги независимы:

```text
PTO_SYMBOLS=1             # детерминированный symbols-конвейер
PTO_SYMBOLS_VLM=1         # H5: помощь при поиске/чтении легенды
PTO_SYMBOLS_VLM_REVIEW=1  # H6: review неоднозначных типов
```

Рекомендуемая последовательность включения:

1. `PTO_SYMBOLS=1`, остальные флаги выключены;
2. H5 — только для сканов и страниц без читаемого text layer;
3. H6 — после оценки детерминированных конфликтов;
4. ручная проверка перед публикацией любых `probable`.

В service worker sidecars повторно используются только при совпадении
`runtime_profile.json`. Изменение H5/H6-конфигурации инвалидирует symbols-кэш,
но не заставляет повторно считать основное VLM-описание страницы.

## 14. Интерпретация результата

Безопасно сообщать пользователю:

- подтверждённые названия и количества только для `confirmed`;
- число вероятных гипотез отдельно как `probable`;
- конкурирующие варианты для `conflicting`;
- нерасшифрованные типы и их повторяемость;
- строки легенды без найденных экземпляров;
- статус страницы и anomaly codes.

Небезопасно:

- суммировать `probable` как фактическое оборудование;
- считать большое число повторов доказательством правильной классификации;
- повышать лимиты только ради завершения страницы;
- использовать H6 как источник нового свободного названия;
- смешивать `no_valid_legend` с фактом отсутствия обозначений на листе.

Практический признак проблемы — явно неправдоподобные количества одного типа.
Это обычно означает, что элементы оформления, сетки или повторяющейся
геометрии прошли candidate filters. Такой результат требует проверки crops и
дальнейшего усиления negative gates.

## 15. Проверка качества

В репозитории используются:

- синтетический CI с известной легендой, известными и неизвестными знаками;
- negative fixtures для текста, таблиц, линий и штриховки;
- property/equivalence тесты кластеризации;
- воспроизводимые baseline JSON без timing-полей в digest;
- opt-in customer fixtures через `symbols/fixtures/MANIFEST.local.json`;
- отдельные dev, holdout, negative и page-35 regression роли.

Основные команды:

```powershell
py -3 -m pytest -q
py -3 -m symbols.validate_gt --self-check
```

Customer KPI не считаются пройденными, если локальный manifest и GT не
установлены. Holdout используется только для отчёта и не должен участвовать в
настройке порогов.

## 16. Текущее состояние и ограничения

Реализованы:

- детерминированные S3–S8;
- fail-closed gates и бюджеты;
- H5 VLM-помощь для легенды;
- H6 ограниченный review;
- sidecars, Markdown, API и каталог;
- fault isolation и resume в service worker.

Остаются ограничения:

- на плотных scanned/CAD-листах candidate detector всё ещё может пропускать
  большое число повторяющихся несимвольных элементов;
- image-only страницы часто не дают независимого semantic evidence, поэтому
  результат остаётся `probable`;
- H6 не обязан разрешать конфликт и корректно возвращает `unresolved`;
- оптимизированная кластеризация пока не прошла release-gate `5×`;
- customer KPI/holdout нельзя заявить без локального GT.

Следовательно, текущий режим — **контролируемый opt-in для извлечения
проверяемых гипотез и ручного review**. H7 release-gate ещё не закрыт, поэтому
это не автономное формирование достоверной ведомости оборудования.

## 17. Карта реализации

- `symbols/pipeline.py` — оркестрация страницы;
- `symbols/legend_layout.py` — область легенды;
- `symbols/legend_rows.py` — строки легенды;
- `symbols/template_matcher.py` — известные шаблоны;
- `symbols/candidate_detector.py` — open-set предложения;
- `symbols/visual_signature.py` — подпись v2;
- `symbols/cluster.py` — кластеризация;
- `symbols/matcher.py` — visual/context scoring;
- `symbols/resolver.py` — статусы и конфликты;
- `symbols/vlm/legend.py` — H5;
- `symbols/vlm/review.py` — H6;
- `symbols/artifacts.py` — sidecars;
- `symbols/markdown.py` — пользовательская проекция;
- `symbols/catalog.py` — каталог документа;
- `symbols/review.py` — append-only ручные решения;
- `symbols/baseline.py` — профили и воспроизводимость;
- `symbols/gates.py` — бюджеты и anomaly codes;
- `service/worker.py` — fault isolation, resume и API-интеграция.

Спецификация каталога ниже является исходным проектным документом: модель
сущностей и ядро S1–S8 реализованы, но описанные там идеальный review UI,
межлистовые связи и использование глобального каталога как источника
