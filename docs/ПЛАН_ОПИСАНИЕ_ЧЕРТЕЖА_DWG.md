# План: описание чертежа по DWG (легенда и привязка)

Задача — **анализ чертежа**, не таблицы и не копия `ИДЕАЛ_*.md`.

Нужно описание в том же сценарии, что у эталона: что на листе, из чего состоит, где лежит, как связано, что означает знак. Формат эталона **не копировать**: без OCR-прозы про «розовую штриховку», без таблиц ФМХ, без цветовой вёрстки ячеек.

Цифры и подписи — из векторного DWG. ГОСТ, которого на листе нет, не подставлять из памяти модели.

Это получится **не в полном соответствии с ИДЕАЛ**, а с нашей спецификой: текст знака из файла точнее, чем «[символ глины]»; проза про сваи и цвета — нет, пока не подключим VLM (в этот план не входит).

---

## 1. Цель и критерий готовности

По markdown **без картинки** можно ответить на инженерный вопрос по листу. Пример для геологии: «под осью 7 на разрезе XII–XII — ИГЭ-2».

Словарь легенды без привязок к полю — ещё не готово. Это инвентарь, не описание чертежа.

В отчёт анализа идут четыре блока (как в `УСЛОВНЫЕ_ОБОЗНАЧЕНИЯ_В_ИДЕАЛ.md`, но из DWG):

1. **Паспорт** — уже даёт `stamp.py` / `dwg_sheets`: шифр, лист, стадия, название.
2. **Ключ легенды** — кроп + подпись с листа (или из каталога раздела, см. §3).
3. **Содержание** — знаки **по виду и оси** (только `confirmed`).
4. **Пропуски** — знаки без `confirmed`, явно.

`probable` остаётся очередью review, не ведомостью.

Таблицы ФМХ, цвета колонок, штамп как «отчёт», печать DWG→PDF, классификатор ГОСТ «с памяти» — **не делаем**.

В проекте уже три разных контура. Их не дублировать.

| Уже есть | Не делать снова |
|---|---|
| Текст, слои, штамп, масштаб — `dwg_sheets.py` | Второй «PASS-B» в отчёте знаков |

| VLM-проза по PDF (`sheet_aware.py`, ИДЕАЛ) | Тот же пересказ «Т-образные фундаменты» по preview |

## 3. Легенда листа и общая легенда папки

### 3.1. Три уровня, не один глобальный словарь

Один каталог на все 94 DWG **нельзя**: у КР — ИГЭ, у ТХ — оборудование, у ПОС — стройгенплан. Смешение даст ложные `confirmed`.

```
лист  →  раздел (папка)  →  комплект
```

| Уровень | Откуда | Когда применять |
|---|---|---|
| **Лист** | Блок «Условные обозначения» в этом DWG (`sourceKind: dwg_vector_legend`) | Всегда первый. Если блок полный — каталог раздела не трогать |
| **Раздел** | Самый полный лист той же папки / той же темы (`project_legend_catalog`) | Лист без легенды или с урезанной (типично ИГР КР2–4 берут ИГЭ с КР1-геологии) |
| **Комплект** | Не строить | Разные марки (КР / ТХ / ПОС / ИОС) не склеивать |

Практически для текущего комплекта:

- **КР, геология + ИГР.** Мастер — `10.1 … Геологические разрезы.dwg` (КР1). ИГР КР2–4 — потребители. Это уже видно в прогоне: каталог приходит с КР1.
- **КР, планы.** Свой словарь (стены, оси, отверстия). Не ИГЭ.
- **ТХ.** Свой словарь. Фикстура `tx-plans-p1` уже в манифесте, но в тот же срез, что геология, не класть.
- **ПОС / ИОС.** Позже, свои каталоги.
- **ПЗУ.** Легенда границ в самом файле возможна; генплан — в XREF, которых нет. Общую легенду ПЗУ не собирать, пока нет `_Ссылки`.
- **ПБ, ОДИ, АР.** DWG в `new_files/dwg` нет. Каталог из PDF — другая задача, не этот план.

ПЗ `.docx`, лицензии PDF, `.dst`, `.dwl` — не источник знаков.

### 3.2. Как строить каталог раздела (без составителя)

Пока нет ответа «какой файл — мастер», правило эвристическое и **узкое**:

1. Внутри одной папки раздела найти листы с заголовком «Условные обозначения» / достаточным числом строк `dwg_vector_legend`.
2. Взять самый полный (для КР-геологии это КР1, лист 1).
3. Ключ склейки: нормализованная подпись **и** визуальная сигнатура (блок / штрих / кружок с номером). Одинаковый текст + тот же знак = одна запись, не два распознавания.
4. Конфликт (один номер ①, разный текст на двух листах) — **не затирать**. Писать в пропуски: «каталог расходится, лист A vs лист B».
5. На целевом листе сначала своя легенда, потом недостающие строки из каталога раздела. Не наоборот.

Это и есть «общая легенда по листам папки»: не один JSON на весь `dwg/`, а **каталог на тему раздела**, с явным `sourceTexts` (какой DWG дал строку).

### 3.3. Что каталог сам по себе не закрывает

На ИГР сейчас типичная картина: каталог с КР1 есть, `confirmed` на поле — 0, сотни `probable`. Общая легенда снимает повтор словаря. Описание чертежа появляется только после привязки экземпляр → строка.

## 4. Диапазон ГОСТ

Препятствия и вывод «есть ли смысл анализировать ГОСТ сейчас» — [`ПРЕПЯТСТВИЯ_РАСПОЗНАВАНИЯ_ГОСТ.md`](ПРЕПЯТСТВИЯ_РАСПОЗНАВАНИЯ_ГОСТ.md).

ГОСТ в проекте уже используется **как геометрия оформления**, не как классификатор знаков: штамп 21.101 (`stamp.py`), форматы 2.301, высоты шрифта 2.304 (`dwg_sheets.py`). Это оставляем.

Для **знаков** ГОСТ — закрытый справочник кандидатов, не «модель знает норматив». Номер ГОСТ в отчёт — только если он написан у знака в DWG.

### 4.1. Можно пытаться (узко, после типа листа)

| ГОСТ | Тип листа | Что даёт | Условие |
|---|---|---|---|
| **21.302** | Геология, ИГР | Штрих грунта, скважина, стратиграфическая / литологическая граница, консистенция | Паттерн **однозначен** и на листе нет своей подписи, которая ему противоречит |
| **21.201** | Планы КР | Проёмы, лестницы, типичные элементы здания | Только если знака нет в легенде листа и паттерн не путается с узлом/выноской |
| **21.205 / 21.206** | ТХ, ИОС (сети) | Арматура, трубы, марки систем | Слой уже несёт марку (`!!!В1`) — ГОСТ не переименовывает, только уточняет тип знака |
| **21.204** | ПЗУ, генплан | Границы, озеленение, транспорт | **Заблокировано** отсутствием XREF; без `_Ссылки` не начинать |

Уже прочитанные с листа имена слоёв («!!!В1», «!!!К1») сильнее ГОСТ-имени «водопровод»: марка проектная, ГОСТ её не знает.

### 4.2. Не пытаться сейчас

- Классификатор «с памяти» (запрет проекта: `sheet_aware.py`, `measure_output.py`).
- ГОСТ 21.205 по PDF пожарки (`01.pdf`, 0 `confirmed`) — нет DWG в `9 - ПБ`.
- СП / таблицы свойств грунтов — другая задача (текст/таблицы).
- Подмена проектного ИГЭ-1 именем грунта из 21.302: номер ИГЭ — **проектный**, не код ГОСТ.
- При неоднозначном паттерне (в ИДЕАЛ два состояния грунта = «пустой прямоугольник») — пропуск, не ГОСТ-имя.

### 4.3. Практическое правило статуса

- Подпись с листа совпала с геометрией → `confirmed`, ГОСТ не нужен.
- Геометрия совпала с **одним** паттерном ГОСТ, подписи нет, тип листа известен → максимум `probable` + пометка «кандидат ГОСТ …». В пользовательский отчёт не идёт.
- Два паттерна ГОСТ или конфликт с легендой листа → `unresolved` / пропуск.

Без библиотеки эталонных паттернов (её нет без составителя или ручной разметки) этап ГОСТ по 21.302 — **после** стабильного каталога КР1, не вместо него. Первый цикл harness ГОСТ не добавляет.

## 5. Запрос к составителю — отдельная задача

Сейчас этих сведений **нет**. Запрос не блокирует этапы A–C по геологии КР1 (файл самодостаточен). Он блокирует ПЗУ, полноту планов со ссылками и превращение ГОСТ-кандидатов в `confirmed`.

Этим планом запрос **не выполняется**. Это отдельный вход: комплект от составителя → тогда отдельный срез harness.

### 5.1. Что запросить (чеклист, не делать в этом плане)

1. **Пакет XREF** — `_Ссылки` / файлы, на которые ссылаются листы. Без них генплан ПЗУ в DWG не из чего читать (`docs/ОГРАНИЧЕНИЯ_XREF.md`).
2. **Какой DWG — мастер легенды** по каждому разделу (геология, сети, планы). Пока угадываем по полноте блока.
3. **CAD-стандарт слоёв и блоков** — какие слои официальные, какие блоки = знак легенды, какие взорваны в примитивы.
4. **Каким ГОСТ реально пользуются** (21.302 «как в книге» или корпоративная штриховка).
5. **Соответствие layout ↔ лист альбома**, если окно вида смотрит мимо модели (уже есть такие листы в ИОС).
6. **Недостающие разделы DWG** — ПБ, ОДИ, АР: будут ли файлы или только PDF.
7. **Смысл цвета / типа линии**, если это не ГОСТ, а CTB/корпоратив.
8. **Масштаб видовых окон** там, где `$INSUNITS` и рамка расходятся.

Пока ответа нет — не заполнять `expected` в `MANIFEST.local.json` выдумкой и не повышать ГОСТ-кандидата до `confirmed`.

### 5.2. Ограничения, которые этим планом не снимаются

Пока составитель не ответил:

- Общая легенда раздела — эвристика «самый полный лист папки». Ошибка мастера даст системный сдвиг на всех ИГР.
- Штрих «как в ГОСТ 21.302» и штрих бюро могут совпасть внешне и значить разное — остаётся `probable` или пропуск.
- Листы из ссылок (ПЗУ и аналоги): в разборе только рамка и локальные объекты; печать того же DWG в PDF дыру не закрывает.
- Имена блоков/слоёв могут быть `Layer1` / `HATCH` — по ним знак не опознать.
- Декор и знак легенды геометрически неразличимы без библиотеки блоков.
- Листы `ИДЕАЛ_19` (ПБ) и `ИДЕАЛ_21` (ОДИ) из `new_files/dwg` не описать: файлов нет.
- `ИДЕАЛ_11` не эталон (шум таблиц).

Это не «потом допишем в том же цикле».

## 6. Подход Harness (как исполнять, не «переписать конвейер»)

Код разбора знаков уже гоняется как **фикстуры**, не как «все 94 DWG сразу». Так и оставляем.

### Что уже есть

- Список листов: `dwg_symbols/fixtures/MANIFEST.local.json` — `id`, путь DWG, номер листа, пустой `expected` (разметка человеком ещё не сделана). Сейчас в манифесте: `kr1-geology-p1`, `tx-plans-p1`, `kr1-plans-p1`.
- Срез прогона: `local_runs/<имя>/selection.json` — какие фикстуры взять в этот запуск и зачем (`selectionReason`).
- Выход: `local_runs/<имя>/` — `REPORT.md`, `statistics.json`, на каждую фикстуру `review.json` и `dwg_symbols/page_NNNN/` (`legend_entries.json`, кропы, привязки).

Примеры срезов, которые уже совпадают с планом:

- `local_runs/review_ideal_kr1/selection.json` — только `kr1-geology-p1`;
- `local_runs/review_ideal_igr/selection.json` — три ИГР КР2–4.

### Правило цикла

Один цикл = **один срез** (лучше один лист, максимум три ИГР с одной целью).

1. Зафиксировать `selection.json`: какие `id`, какой вопрос цикла (например: «склеиваются ли три типа границы» или «есть ли `confirmed` на ИГР»).
2. Прогнать тот же harness, что уже пишет `local_runs/` (не новый скрипт «на все файлы»).
3. Смотреть не картинку целиком, а артефакты:
   - `legend_entries.json` — каталог: `sourceKind` (`dwg_vector_legend` / `project_legend_catalog`), `label`, кроп;
   - `review.json` — `legendEntries`, `confirmed` / `probable`, `bindings`, `bindingEvidence`, `anomalyCodes`;
   - `REPORT.md` — сводка по листу.
4. Сравнить с эталоном **только смысл**: те же названия грунтов и те же номера ИГЭ на разрезе. Не сверка «слово в слово» с ИДЕАЛ (там OCR и петли).
5. Пока `confirmed` на целевом листе не устойчив и пропуски не перечислены — **не добавлять** планы, ТХ, ПЗУ в тот же срез.
6. Пустые `expected` в манифесте не заполнять выдумкой. Когда человек подтвердит привязки — тогда GT. До этого мерить прогон против прошлого прогона и против списка легенды в `ИДЕАЛ_08` / `_10`.

Не раздувать манифест «на всякий случай». Новый лист — новая строка в `selection.json` и отдельная папка `local_runs/`, когда предыдущий цикл закрыт.

## 7. Этапы и как их гонять в harness

### Этап A — каталог легенды листа

**Вопрос цикла:** полный ли словарь с листа, не слиплись ли строки.

- Фикстура: `kr1-geology-p1`.
- Смотреть `legend_entries.json`: ориентир — 23 пункта, подписи как в блоке «Условные обозначения» `ИДЕАЛ_08`.
- Починить (когда будете менять код — отдельная задача): три типа линии границ в одной `label`.
- Для ИГР: убедиться, что каталог приходит с пути КР1-геологии (`sourceTexts` указывает на тот DWG). Это уже видно в `review_ideal_igr`.

ГОСТ не добавлять. Номер ГОСТ — только если он написан у знака в DWG.

### Этап B — привязка к полю (главное)

**Вопрос цикла:** экземпляр на разрезе = строка каталога.

- Тот же `kr1-geology-p1`: разобрать, почему много `confirmed` и улика вроде `exact_block_definition` — это образец «как должно».
- Затем срез как `review_ideal_igr`: на ИГР сейчас `probable` сотни, `confirmed` 0. Цикл не «набрать probable», а поднять `confirmed` или явно пометить «не прочитано».
- В пользовательское описание идут только `confirmed`. `probable` — очередь review, не ведомость слоёв.

Без закрытого B этап C не начинать.

### Этап C — узкий отчёт описания

Собрать из sidecar четыре блока (паспорт / ключ / содержание по осям / пропуски).
Карта листа (`sheet_map`) — по желанию: где легенда, где виды.
Не верстать таблицы грунтов и не звать VLM.

### Этап D — общая легенда раздела

Отдельный срез, не смешивать с отладкой привязки:

- Построить каталог КР-геологии из мастера.
- Прогнать ИГР КР2–4: легенда не перечитывается, только поле.
- Конфликты номеров — в пропуски.
- Планы КР и ТХ — **свои** каталоги, новые срезы.

### Этап E — тот же тип листа дальше

Повторить B на `kr3-igr-p1`, затем КР2/КР4.
Планы КР/ТХ — новый срез и **свой** каталог, не ИГЭ.
XREF из `Внешние ссылки` — отдельный цикл, когда дойдёте до планов **и** будет пакет ссылок (задача §5).

### Этап F — ГОСТ как справочник (после D)

Только 21.302 на геологии, только однозначный паттерн, статус не выше `probable`, пока составитель не подтвердит стандарт. В пользовательский отчёт не входит.

## 10. Порядок работ

1. Цикл A на `review_ideal_kr1` (уже почти готов) — зафиксировать каталог и список дефектов словаря.
2. Цикл B на том же листе — эталон привязки.
3. Цикл B на `review_ideal_igr` / сначала один `kr3-igr-p1`.
4. Этап C — отчёт из готовых sidecar.
