### 1. Предупреждения листа и источник его содержимого

(внутри цикла `for (const page of await fetchPages(...))`).

Имя поля `warnings` у нас и у вас совпадает буквально — оно и задумано так,
чтобы правка была в одно слово.

```diff

+    warnings: page.warnings ?? [],
```

Тип ответа страницы — там же, рядом (`type BackendPage`):

```diff

+  trust?: {
+    level: "dwg" | "layer" | "vlm" | "none";
+    title: string;      // человеческая формулировка, годится как подсказка

+    checked: boolean;
+    total: number;
+    found: number;

+  } | null;
```

**Зачем.** Сейчас каждый лист подписан «Модель», даже когда модель не
вызывалась вовсе — а у чертежа DWG и у листа с исправным текстовым слоем текст

### 2. Листы с дырами — в ленте, рядом с ошибками

**Файлы:** `src/lib/process-document.ts` (тип `BackendJob` и патч документа),
`src/types.ts` (`DocumentRecord`).

У задания появился словарь `pageWarnings` — брат `pageErrors`. Разница в
смысле: `pageErrors` — листа нет вовсе; `pageWarnings` — лист есть и лежит в
`pagesDone`, но с дырами. Например: часть фрагментов модель не прочитала
(обрыв провайдера), или у листа нет текстового слоя и всё содержимое получено
по изображению.

```diff
 type BackendJob = {
   …
   pageErrors: Record<string, string>;
+  pageWarnings: Record<string, string>;   // { "7": "3 фрагмента листа не прочитаны…" }
 };
```

```diff

   pageErrors: current.pageErrors ?? {},
+  pageWarnings: current.pageWarnings ?? {},
```

Плюс поле в `DocumentRecord` (`src/types.ts`) рядом с `pageErrors`. В ленте
листов у вас уже рисуется значок для листов из `pageErrors` — сюда просится
второй, другого цвета.

**Зачем.** Лист с дырами выглядит готовым и читается как готовый. Пока это
видно только внутри самого листа (плашка из пункта 1), но не в ленте — то есть
инженер узнаёт о проблеме, только открыв лист.

### 3. Подозрительные числа — необязательно, но дёшево

**Файлы:** `src/lib/process-document.ts`, `src/components/review-pane.tsx`.

Поле `page.numbers`: мы берём все числа из описания, написанного моделью, и
ищем каждое в текстовом слое и таблицах листа. Не найденные — кандидаты в
галлюцинации. Из текста они не удаляются, только помечаются.

```jsonc
"numbers": {
  "checked": true,
  "total": 20,        // чисел в описании модели
  "found": 20,        // из них нашлись в документе
  "precision": 100.0,
  "suspect": []       // не нашлись — вот эти перепроверить
}
// null — проверять нечем: нет текстового слоя, или это лист чертежа (модели не было)
```

**Зачем.** Выдуманная марка насоса от настоящей глазами не отличается — это
главный риск всего проекта. Показать список рядом с текстом листа стоит
вечера, а инженеру даёт точку приложения внимания.

### 4. Перезапуск фронтенда роняет идущие прогоны

**Файл:** `src/lib/storage.ts`, функция `resetStuckDocuments` (и место её
вызова в `GET /api/documents`).

Документ считается зависшим, если его нет в множестве `running` — а оно живёт
в памяти процесса Next.js. После любого деплоя фронта множество пустое, и
ровно через `STUCK_AFTER_MS` (5 минут) все считающиеся документы получают
статус ошибки и текст «Обработка прервалась. Нажмите „Повтор“». Бэкенд в это
время продолжает считать как ни в чём не бывало.

Утром 28.08 это выглядело так: комплект загружен в 06:18, фронт запулен и
перезапущен, в 06:23 оба документа помечены ошибкой с нулём страниц. Задания
на бэкенде были живы всё это время.

```diff
 // resetStuckDocuments уже возвращает список id, которые пометил ошибкой —
 // достаточно спросить бэкенд, не жив ли прогон, и вернуть документ в работу.

 const stuck = await resetStuckDocuments(activeDocumentIds());
+for (const id of stuck) {
+  const job = await findPipelineJob(id);          // pipeline.ts, уже есть
+  if (job?.status === "processing" || job?.status === "queued") {
+    runInBackground(processDocument(id));         // подхватит через findExistingJob
+  }
+}
```

**Зачем.** Сейчас любой деплой фронта во время работы выглядит для
пользователя как потеря нескольких часов счёта. Данные при этом целы —
«Повтор» подцепляется к тому же заданию и забирает готовое без пересчёта, — но
об этом знаем мы, а не инженер, который видит красное.

### 5. Удаление документа не снимает задание с бэкенда

**Файлы:** `src/app/api/documents/[id]/route.ts` (DELETE),
`src/lib/storage.ts: deleteDocument`.

`deleteDocument` убирает свою запись, файл и байты PDF — и всё. Конвейеру
никто ничего не говорит, задание остаётся в очереди и продолжает считаться.
Сегодня это заметили только потому, что файл лежит в общей папке `uploads`: он
исчез, и задание упало само. Это побочный эффект, а не отмена — задание на
файл из другого места считало бы дальше.

```diff
 // в DELETE-маршруте документа, перед deleteDocument(id):
+const job = await findPipelineJob(id);
+if (job) {
+  await fetch(`${PIPELINE_URL}/jobs/${job.id}?purge=true`, { method: "DELETE" });
+}
 const removed = await deleteDocument(id);
```

Маршрут `DELETE /jobs/{id}` уже есть: он снимает задание, а с `?purge=true`
ещё и чистит папку прогона, чтобы результаты удалённого документа не занимали
место.

**Зачем.** Удалённый документ может считаться ещё часы и тратить деньги у
провайдера. Плюс он занимает единственную модельную полосу очереди — то есть
тормозит документы, которые нужны.

### 7. Имена файлов из ZIP приезжают кракозябрами

**Файл:** `src/lib/drawing-kit.ts` (`extractDrawingKitFromZip`, там где
берётся `baseName(path)`).

Проводник Windows пишет имена в архив в кодировке cp866 и не ставит флаг UTF-8
(бит `0x800`). `fflate` читает такие имена как latin1, и
«1. Жуковский I _ СП.dwg» превращается в `1. ãª®¢áª¨© I _ .dwg` — с
управляющими символами внутри. Работать не мешает, но выглядит как поломка, и
документ потом не найти поиском.

```ts
// перекодировать имя, если оно состоит из latin1-байтов:
function fixZipName(name: string): string {
  if (!/[\u0080-\u00FF]/.test(name)) return name;   // ASCII или уже UTF-8
  const bytes = Uint8Array.from(name, (ch) => ch.charCodeAt(0) & 0xff);
  return new TextDecoder("ibm866").decode(bytes);   // ibm866 — он же cp866
}
```

**Зачем.** Имя файла — это то, по чему инженер узнаёт лист в списке. Плюс мы
сводим DWG и PDF одного раздела по основной надписи, и читаемое имя источника
идёт в отчёт.

## Что приходит от бэкенда сейчас

Схема страницы — 8. Поля `markdown`, `extractedText`, `kind`, `pageNumber` не
менялись; три новых — `trust`, `warnings`, `numbers`. Всё, что в них,
продублировано строками внутри самого `markdown` («Надёжность»,
«Предупреждения», «Проверка чисел») — так что модель-сверщик и инженер видят
одно и то же даже без правок в UI.

```jsonc
GET /jobs/{id}/pages?pages=1,2,3   →   { "pages": [ … ] }

{
  "pageNumber": 1,
  "kind": "text",                     // drawing | text | table | mixed
  "markdown": "# Лист 1\n\n## Лист дословно (из PDF, в порядке исходника)…",
  "extractedText": "…",
  "trust": {
    "level": "layer",                 // dwg | layer | vlm | none
    "title": "высокая — текст и таблицы взяты из текстового слоя PDF дословно…",
    "warnings": []
  },
  "warnings": [],                     // то же, что pageWarnings задания для этого листа
  "numbers": { "checked": true, "total": 20, "found": 20, "precision": 100.0, "suspect": [] },
  "tables": ["| Обозначение | Наименование |\n|---|---|\n…"],
  "schema": 8
}

GET /jobs/{id}   →   { …, "pageErrors": {}, "pageWarnings": {}, "modelPages": 0 }

GET /health      →   { …, "queue": { "queued": 0, "processing": 1, "done": 4, "error": 0, "canceled": 0 },
                            "currentJobs": { "model": "job-id", "vector": null } }
```

**Про уровни доверия.** `dwg` — текст прочитан из данных чертежа, модель не
вызывалась. `layer` — текст и таблицы взяты из текстового слоя PDF дословно,
моделью написано только «Описание листа». `vlm` — текстового слоя нет, всё
содержимое прочитано по изображению: числа и марки нужно сверять с оригиналом.
`none` — с листа ничего не извлечено.
