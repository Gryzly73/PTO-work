# Техническое задание: логика обработки информации

Документ снят **от обратного** с действующей техдокументации продукта (`README.md`, `КАК_ЭТО_РАБОТАЕТ.md`, `CLAUDE.md`, `service/README.md`, `ДЛЯ_ФРОНТЕНДА.md`) и с правил, зашитых в конвейер (`SYSTEM_VLM`, промпты `sheet_aware.py`, `service/convert.py`).

Это ТЗ **слоя извлечения** (PDF → машиночитаемый текст). Интерфейс пользователя **не нормируется**: внешний вид, вёрстка экранов и сценарии кликов — на усмотрение клиента. Нормируется только контракт данных и поведение обработки.

> Не путать два «ТЗ». **ТЗ стройки** — требования заказчика к объекту; с ним должен сверяться второй слой продукта, который ещё не написан. **Это ТЗ** — требования к системе извлечения содержимого проектной документации.

---

## 1. Назначение

Система должна превратить комплект проектной документации (сотни–тысяча страниц PDF: пояснительные записки, ведомости, планы, схемы) в машиночитаемый Markdown, по которому можно:

- задавать вопросы к содержанию листов без исходного PDF;
- в дальнейшем сопоставлять извлечённый текст с ТЗ стройки.

Слой сверки с ТЗ стройки **в объём этого документа не входит**. Он зависит от слоя извлечения: выдумка на извлечении делает сверку ложноположительной.

Бизнес-контекст (из `README` / `КАК_ЭТО_РАБОТАЕТ`): цикл «проверка ПД → замечания → правки» у ПТО заказчика занимает порядка 1–1.5 месяца на комплект ~1000 страниц. Извлечение — обязательный первый шаг автоматизации этого цикла.

## 2. Границы

### 2.1. Входит

| ID | Требование |
|---|---|
| FR-IN-1 | Приём векторного CAD-PDF русской проектной документации |
| FR-IN-2 | Постраничная обработка с паспортом листа, текстом/таблицами из слоя и словесным описанием чертежа |
| FR-IN-3 | Очередь комплектов, прогресс по листам, возобновление после сбоя и перезапуска процесса |
| FR-IN-4 | Выдача готовых листов по мере готовности (не только целиком в конце) |
| FR-IN-5 | Детерминированная починка битого ToUnicode по **тому же** документу |
| FR-IN-6 | Детерминированная сборка таблиц по сетке линий и координатам слов |
| FR-IN-7 | Метрики полноты и достоверности против текстового слоя того же PDF |

| OUT-2 | Сверка комплекта с ТЗ стройки и список замечаний | второй слой, не начат |

### 2.3. Клиент

Клиентом может быть браузер, CLI, другой сервис. Он сам решает, как показывать прогресс и текст. К обработке это не относится, кроме контракта в §8.

## 3. Вход и выход

### 3.1. Вход

- Формат: PDF проектной документации, как правило векторный, из CAD.
- Содержание: текст, таблицы расчётов и ведомостей, чертежи планов и схем.
- Объём: ориентир — до ~1000 страниц; лимит загрузки по HTTP — 400 МБ (`PTO_MAX_UPLOAD_MB`).
- Язык: русский; шифры и обозначения — кириллица и смешанные коды (В1, ХСА, ИГЭ и т.п.).
- Сканы: вторичны. Если текстовый слой есть и читаем, OCR не заменяет слой.

### 3.2. Выход на лист (минимум)

Каждый обработанный лист обязан содержать:

1. **Паспорт:** тип `text | table | plan | scheme | mixed`, геометрия, признаки слоя.
2. **Описание (VLM):** что изображено, из чего состоит, где расположено, как связано — только по тому, что видно на листе.
3. **Текст и таблицы из текстового слоя PDF**, если слой читаемый (в том числе после починки ToUnicode).
4. **Явный пропуск**, если факт с картинки не разобран: писать «неразборчиво» / опускать, а не подставлять «типовое» значение.

Структура описания чертежа (целевой каркас промпта):

- ЧТО ИЗОБРАЖЕНО
- ИЗ ЧЕГО СОСТОИТ (в т.ч. легенда словами, экспликация, штамп)
- ГДЕ РАСПОЛОЖЕНЫ ЭЛЕМЕНТЫ
- КАК СВЯЗАНЫ
- полный читаемый текст, не попавший в блоки выше

Тест пригодности (не формальный автотест): по выгрузке листа можно отвечать на инженерные вопросы без PDF.

### 3.3. Правило источников (обязательное)

| Источник | Что берётся | Чего нельзя |
|---|---|---|
| Текстовый слой PDF (+ сетка таблиц по координатам) | числа, наименования, шифры, строки таблиц | подменять слоем «вычитывание» картинки моделью, если слой исправен |
| VLM по рендеру листа | сюжет чертежа, связи, расположение, смысл схемы, значки словами | числа и нормы из знаний модели; ГОСТ/СП/СНиП/ТУ, которых нет на листе |
| Tesseract | угол поворота (OSD); вспомогательно штамп | полностраничное распознавание как основной текст |

Если слой исправен и достаточно длинный — **запрещено** гонять нарезку листа на фрагменты ради повторного вычитывания текста (`--layer-aware` / `PTO_LAYER_AWARE`).

Итоговый текст для человека и для клиента: описание VLM + слой/таблицы. Фрагменты тайлов (PASS-B) в выдачу по умолчанию **не входят** (`PTO_INCLUDE_FRAGMENTS=0`). Сырой вывод конвейера (PASS-0/A/B) сохраняется в прогоне и доступен отдельным маршрутом.

### 3.4. Артефакты прогона

Контракт файлов (и CLI, и HTTP):

```
hf_runs/<stamp>_<model>_…/
  pages/page_NNNN.md      ← PASS-0 / PASS-A / PASS-B; ломать секции нельзя
  out.md                  ← сборка «## Страница N»
  frontend/page_NNNN.json ← опционально, кэш листа для клиента
```

Инструменты `compare_to_etalon.py`, `build_ios2_md.py`, скоринг читают тот же формат независимо от точки входа.

## 4. Принципы качества

Эти правила — часть логики, не «пожелания к промпту».

| ID | Правило |
|---|---|
| Q-1 | **Пропуск лучше галлюцинации.** Нет на листе — не писать. Пропущенную строку видно; выдуманную марку оборудования от настоящей глазами не отличить. |
| Q-2 | Любое число в ответе модели должно быть **напечатано на изображении** (либо взято из слоя кодом). Не вычислять недостающие величины. |
| Q-3 | Запрещено добавлять из знаний модели ссылки на ГОСТ/СП/СНиП/ТУ, номера пунктов, «типовые» температуры, напоры, диаметры, нормы. Прочитать ГОСТ, **напечатанный на листе**, — допустимо. |
| Q-4 | Кириллица не подменяется латиницей (`В1` ≠ `B1`, `ХСА` ≠ `XCA`, `ИГЭ` ≠ `IGE`). |
| Q-5 | Графические значки описываются **словами** по-русски. Эмодзи и юникод-заменители ГОСТ запрещены. |
| Q-6 | Подсказки, завязанные на номер страницы тест-сета (`zone-hints`), на произвольных PDF **выключены**. |
| Q-7 | Неопределённость модели не должна выглядеть как факт документа. |
| Q-8 | Не перечислять голые номера подряд без названий объектов; не дублировать повторяющиеся метки десятки раз — уникальный список + указание на повтор. |
| Q-9 | Приоритет — **корректный контекст** (точный текст + словесное описание), а не pixel-perfect вёрстка таблиц. |
| Q-10 | Улучшения качества проверяются на **невиданном** чертеже. Подгонка промпта под конкретный эталон запрещена как метод «прогресса». |

Легенда на листе: конвейер **просит** выписать каждый знак словами. Это не детектор легенды и не замкнутый словарь для второго прохода. Привязка «этот экземпляр на чертеже = этот пункт легенды» в текущем объёме не требуется, но и не должна имитироваться догадками.

## 5. Обработка одной страницы

Последовательность. Платный вызов модели — только там, где детерминированного слоя недостаточно.

```
PDF-страница
  → [1] паспорт: геометрия + слой → тип листа, бюджет рендера, якоря
  → [2] текст слоя; битый ToUnicode → подстановка, выведенная по этому документу
  → [2б] таблицы: линии сетки + слова в ячейки по центру; штамп комплекта — не таблица
  → [2в] при необходимости поворот листа (OSD)
  → [3] один запрос VLM на описание целого листа (PASS-A)
  → [3б] нарезка / доп. зоны (PASS-B) — только если слой непригоден
        или лист — плотный чертёж без опоры на слой
  → [4] чистка петель (повторы строк, пустые ряды, арифметические прогрессии)
  → [5] запись листа; ошибка листа не роняет весь комплект
```

### 5.1. Паспорт и тип листа

Тип (`text` / `table` / `plan` / `scheme` / `mixed`) влияет на промпт и разрешение рендера, **не** на отдельный классификатор символов.

Ориентиры разрешения (из действующего конвейера): план — до ~3200 px, текстовый лист — ~1800–2000 px. Мелкий рендер теряет подписи; чрезмерный — дороже и чаще зацикливается.

Роутинг «текст → одна модель, чертёж → другая» **не обязателен**. Механика паспорта для него уже есть; реализация роутинга — вне текущего объёма.

### 5.2. Текстовый слой и deglyph

- Исправный слой — источник истины для букв и цифр.
- Порча ToUnicode трактуется как подстановочный шифр 1:1 по документу, не как «нет текста».
- Отображение глиф→буква подбирается по читаемым листам **того же файла**.
- Короткого совпадения недостаточно (омонимы вроде `?ата` → «Дата»/«лата»): нужны два независимых подтверждения либо достаточно длинное слово.
- Подстановка применяется только при высоком покрытии (в коде: порядка 90% символов / 85% слов). Иначе слой **нельзя** выдавать клиенту как точный текст (`extractedText` пустой).

Шифр документа, если на данном листе слой мёртв, допускается подсказать с **других листов того же комплекта** с явной пометкой источника. При нескольких разных шифрах в файле — не подсказывать.

Известное ограничение слоя (не дефект конвейера): дефисы и слэши в шифрах часто нарисованы графикой и **отсутствуют в слое как символы**. Шифр вида `28-ХСА-1/25-ПЗ` лежит как отдельные токены. Метрику «коды» на таких листах не использовать как единственный критерий качества.

### 5.3. Таблицы

1. Сетка ячеек — по линиям листа (MuPDF / `page.find_tables()`).
2. Слово кладётся в ячейку **по центру** глифа, не по краю (иначе протекает в соседнюю строку).
3. Двухъярусные шапки разворачиваются в нормальные строки.
4. Рамка основной надписи (штамп) **не является** содержательной таблицей. Признак: сетка повторяется на ≥30% листов комплекта и покрывает ≥85% площади — отбрасывается. Правило должно работать на произвольном комплекте, без ручной подгонки «на глазок».

Для листа-таблицы допускается отдельный запрос «перенеси таблицу как в исходнике» вместо нарезки (`--table-pages`). Повёрнутые листы разворачиваются автоматически.

Если фрагмент вернулся петлёй пустых ячеек — table-rescue: повтор с повышенным разрешением, при неудаче — горизонтальная полоса листа целиком.

### 5.4. VLM

- Основная модель: `Qwen/Qwen3-VL-32B-Instruct` (`qwen3vl-32b`). Запасные и дисквалифицированные — каталог в `README.md` / `HF_MODEL_CANDIDATES.md`. Не возвращать дисквалифицированные (латинизация кириллицы, выдуманные штампы и марки).
- Модель должна быть совместима с последующим локальным запуском на **4×A16 (~61 GB VRAM, TP=4)**.
- Полностраничный DeepSeek-OCR и аналоги через API, дающие петли и мусор, не использовать как основной путь.
- Текстовая LLM-«пересборка» черновика поверх union **не** является обязательным шагом: измерено, что она сжимает, а не улучшает; объединение источников — детерминированным кодом.

### 5.5. Тайлинг (PASS-B)

Нарезка увеличивает читаемость мелких подписей и **ломает контекст целого листа**, чаще провоцируя выдумки. Поэтому:

- при исправном слое шаг не запускается;
- зональные кропы по фиксированным долям листа (тест-сет) на чужих PDF не включать;
- данные тайлов остаются в файле прогона; в клиентский markdown по умолчанию не попадают.

## 6. Обработка комплекта (очередь)

| ID | Требование |
|---|---|
| FR-JOB-1 | Единица работы — **лист**, не весь PDF одним вызовом. |
| FR-JOB-2 | Одна активная задача на документ; состояние очереди на диске, переживает перезапуск процесса. |
| FR-JOB-3 | После рестарта готовые `page_NNNN.md` не пересчитываются; досчитываются только недостающие. |
| FR-JOB-4 | Keep-going: упавший лист в `pageErrors`, остальные считаются. Документ в `error`, только если не вышел ни один лист. |
| FR-JOB-5 | Отмена проверяется **между** листами; текущий лист досчитывается. |
| FR-JOB-6 | По умолчанию листы идут **последовательно** (`PTO_PAGE_CONCURRENCY=1`). Параллель — опция: быстрее, но может нарушить порядок выдачи. Страницы комплекта бывают связаны (шифр, deglyph по документу). |
| FR-JOB-7 | PDF между клиентом и конвейером не обязан передаваться телом запроса: клиент кладёт файл в согласованный каталог, конвейер читает по пути из белого списка (`PTO_ALLOWED_PDF_ROOTS`). |
| FR-JOB-8 | Режимы `real` и `mock` не смешивают очереди, тома и результаты. Страницы mock помечены так, чтобы их нельзя было принять за вывод модели. |
| FR-JOB-9 | Новые документы можно ставить в очередь, пока идёт другой прогон; одновременно обрабатывается один документ. |
| FR-JOB-10 | Деплой и обновление сервиса не уничтожают тома с очередью и `hf_runs`. |

Масштаб: ориентир 1000 страниц, часы работы в `real`. Простой при обновлении не должен обнулять прогресс.

В режиме `real` страницы уходят стороннему провайдеру, пока нет локального инференса. Это ограничение контура, не требование «всегда слать наружу».

## 7. Контракт для клиента (без UI)

Клиенту достаточно уметь:

1. Создать задачу: multipart с файлом **или** JSON `{path, originalName, projectId, documentId, pages}`.
2. Опрашивать статус: сколько листов готово, текущий лист, шаг обработки, ошибки, `usage`.
3. Забирать готовые листы пачками (`after=N`) и выборочно (`pages=1,5,7`).
4. Получить один лист, сырой PASS-0/A/B, весь документ одним markdown.
5. Отменить задачу; после рестарта клиента — найти задачу по `documentId` и **не** начинать прогон заново.
6. Досчитать недостающие (`retry`) или начать с нуля (`retry?reset=true`).

Формат листа для клиента:

```json
{ "pageNumber": 1, "kind": "drawing", "markdown": "# Лист 1…", "extractedText": "…" }
```

- `kind`: `plan`/`scheme` → `drawing`; иначе `text` / `table` / `mixed`.
- `extractedText` — текстовый слой, **только если читаемый**.
- Шапка markdown **обязана** содержать устойчивый маркер `**Файл:**`. Без него известный клиент перегенерирует заглушку и затирает результат.
- Состав markdown: читаемое описание + слой; без свалки тайлов, если не включён явный флаг фрагментов.

Аутентификация: опциональный общий секрет `PTO_API_TOKEN`; заголовок `X-PTO-Token`. `/health` — без секрета.

Маршруты (норматив текущего HTTP-слоя): `GET /health`, `POST /jobs`, `GET /jobs`, `GET /jobs/{id}`, `GET /jobs/{id}/pages`, `GET /jobs/{id}/pages/{n}`, `GET /jobs/{id}/pages/{n}/raw`, `GET /jobs/{id}/markdown`, `POST /jobs/{id}/cancel`, `POST /jobs/{id}/retry`, `DELETE /jobs/{id}`.

Диапазон страниц — тот же синтаксис, что в CLI: `1,3,5`, `35-41,44-49`, `all`.

## 8. Проверка качества извлечения

Это **не** сверка с ТЗ стройки. Три шкалы смешивать нельзя.

| Шкала | Чем | Зачем |
|---|---|---|
| Против текстового слоя | `score_vs_pdftext.py` | полнота слов/чисел; **достоверность чисел** (числа выгрузки, которых нет в документе) — детектор галлюцинаций без ручного эталона |
| Против ручного эталона | `compare_to_etalon.py` | грубая полнота и ключевые фразы; есть не для всех страниц |
| Глазами | HTML: PDF слева, выгрузка справа | оранжевое — потерянное, красное — написанное сверх документа |

Обязательные оговорки:

- Секции, уже взятые из слоя, в замер «качества VLM» не смешивать (иначе метрика даёт 100% сама с собой). Флаг `--vlm-only`.
- VLM недетерминированна: разброс двух прогонов одной страницы может быть десятки пунктов. Вывод по одному прогону не считается доказательством; ориентир дисциплины — медиана из ≥4 и худшее значение (`LOOP_LEDGER.md`).
- Перед интерпретацией метрики проверять, нет ли в выводе ошибок API (пустые/ошибочные страницы обнуляют полноту).
- Цифры, полученные на одном комплекте (ИОС2), не переносятся на другой документ без повторного замера.

Интерпретация низкой полноты **описания VLM** при высокой достоверности: ожидаемо, если цифры взяты из слоя. От модели нужен смысл и связи, не повторное вычитывание таблиц.

| ID | Требование |
|---|---|

## 10. Критерии приёмки слоя извлечения

Комплект считается извлечённым приемлемо, если одновременно:

1. На каждый запрошенный лист есть запись: markdown описания и/или слой, либо явная ошибка листа без обрыва всего комплекта.
2. Читаемый текстовый слой (после deglyph) не подменяется молча «картиночным» пересказом чисел.
3. Содержательные таблицы собраны геометрией; рамки штампа не выданы как ведомости.
4. В описании чертежа нет ГОСТ/норм/марок, которых нет на листе; значки словами; кириллические шифры не латинизированы.
5. Клиент получает листы с `**Файл:**`, корректным `kind` и пустым `extractedText` на кракозябрах.
6. Повторный запуск той же задачи не пересчитывает уже готовые листы.
7. Скоринг против слоя на текстово-табличных страницах показывает высокую достоверность чисел; полнота итогового документа (слой + описание) существенно выше полноты «только VLM».

Пороговые проценты из одного комплекта (ИОС2: полнота итога 99.6%, достоверность чисел 97.5%, 0 нечитаемых из 49) — **ориентир**, не догма приёмки на новом PDF. На новом комплекте пороги задаются отдельным замером.
